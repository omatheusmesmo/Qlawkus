# Owner approvals

The opt-in approval gate for tool calls.

Behavior and configuration are documented for users in `site/content/approvals.adoc`, which is the source of truth. This page keeps the implementation rationale and the traps worth knowing before changing the code.

## Owner approvals (`client/runtime/.../approval`)

**Owner approvals (`client/runtime/.../approval`)** - Opt-in gate for the `@QlawTool` tools named in `qlawkus.approval.tools` (empty by default, so nothing changes until one is named).
`ApprovalToolExecutor` sits in `QlawToolProvider`'s chain under the context bridge and under the meters: a gated call is recorded as an `ApprovalRequest` (canonical arguments, SHA-256 binding over tool name and arguments, redacted preview, requester and conversation) and the model is told it has NOT run.
`ApprovalService` owns the state machine: every transition is a compare-and-set through the `ApprovalStore` SPI, an approval re-checks the binding before running the stored arguments exactly once, a restart turns an `APPROVED` or `EXECUTING` request into `NEEDS_REVIEW` without replaying it, and a 60s sweep expires pending requests.
The default `FileApprovalStore` writes one JSON file per request under `qlawkus.agent.state.root/approvals`; `store.pg.PgApprovalStore` (the `approval_request` table, `V11`; the decision is a compare-and-set under a row lock in `ApprovalRequestRepository`) and `store.pg.HybridApprovalStore` (files decide, the table mirrors, and a mirror failure never undoes a recorded decision) follow `qlawkus.cognition.backend`.
`ApprovalGate.pendingCount()` is the read the console overview uses.
Decisions are owner-only and never reachable from a tool: `/approve` and `/deny` in messaging (read before the model, allowlisted), `/api/admin/approvals` (`@Authenticated`), and the console page.
Approval outcomes resume the originating conversation through `ApprovalResumeListener` on the interactive workload; expiry and review notify the chat without a model turn.
Tools declared on `AgentService` and remote MCP contributor tools are not gated (resume rebuilds `@QlawTool` executors by name only).
A tool is gated by `qlawkus.approval.tools` or by any `ApprovalRequirement` bean (`ApprovalPolicy` combines both); `qlawkus-tools-skill-hub` (`SkillHubApprovalRequirement`: install, update, publish) `qlawkus-tools-mcp-client` (`McpApprovalRequirement`: `configureMcpConnection`) request it while their `approval-mode` is `hitl`, and `client`'s `SkillScriptApprovalRequirement` gates `runInstalledSkillScript` (always, unless `qlawkus.skill-scripts.installed-require-approval` is off) and both script tools when `runCommand` is gated, and the permission matrix (below) adds `ask` cells on top. Calendar `updateEvent` and `deleteEvent` and Drive `trashFile` are no longer `ApprovalRequirement` beans: `CalendarPermissionDefaults` (cells `calendar` UPDATE and DELETE, off with `qlawkus.google.calendar.require-approval=false`; the tools also take the event's current title so the approval prompt is readable and a wrong id is refused) and `GoogleDrivePermissionDefaults` (cell `drive` DELETE, switch `qlawkus.google.drive.trash-needs-approval`) suggest matrix defaults instead. Those tools write only inside `ApprovedExecution` (a thread-local marker `ApprovalService.runTool` sets), so a model-supplied `confirm` is ignored.
Buttons: `CdiApprovalNotifier` fires `ApprovalPromptEvent` for PENDING requests, `messaging`'s `ApprovalPromptDeliveryListener` calls `MessagingProvider.sendApprovalPrompt` (Telegram inline keyboard, Discord `ActionRow`; default false falls back to the text notice), and a press becomes the typed `/approve <id>` or `/deny <id>` from the pressing user through `MessagingOrchestrator` (`ApprovalCallbacks`), so the allowlist and the compare-and-set apply and the model is never involved.
A Telegram webhook callback needs the configured secret header (403 otherwise).
Slack has no buttons (no interactivity endpoint).
Documented in `site/content/approvals.adoc`.

## Access classes (`client/runtime/.../tool/access`, `ToolAccessScanner` in `client/deployment`)

Step 1 of #607. The class only describes a tool; the permission matrix below is what reads it.
`ClientProcessor.toolAccess` runs `ToolAccessScanner` over the combined Jandex index: every `@Tool` method (own and inherited) of a `@QlawTool` class gets an `AccessClass` from, in order, `@ToolAccess` on the method, `@ToolAccess` on the bean, the leading camelCase word of the method name (`AccessClassInference`), else `EXECUTE` with source `FALLBACK`.
The result is written to `target/qlawkus-tool-access.tsv`, summarised in the log, and baked into the `ToolAccessRegistry` synthetic bean through `ToolAccessRecorder` (parallel lists, so it is bytecode-serializable and needs no reflection natively). `ToolAccessRegistry.classOf(tool)` returns `EXECUTE` for a name it does not know, which is what a remote MCP tool will be until step 4.
Traps: the scan reads only the index, so a tool is classified by its declared name (`@Tool(name = ...)` when given, else the method name) and a build-time `IllegalStateException` fails the build on a duplicate name; `@ToolAccess` is for names that lie, not a tag every tool must carry (16 of the 87 tools carry one today: verbs such as `upload`, `apply`, `configure`, `make` and `modify` are ambiguous, and `heartbeatStatus` leads with a noun); keep the verb table small and add a verb only when every tool starting with it agrees.
The scanner tests need `@QlawTool` fixtures that must not be indexed by the `@QuarkusTest` application of `client/deployment` (they would become beans and join the tool catalog), so they live in `integration-tests/tool-access`, a plain JUnit module with no Quarkus application and nothing to build natively. It also holds the snapshot (`tool-access.snapshot`: tool, class, source) over every extension that declares tools; add the extension's runtime artifact to its pom when a new one declares tools, and refresh with `-Dqlawkus.tool-access.update=true`, reviewing the diff.
Documented in `site/content/approvals.adoc`.

## Permission matrix (`client/runtime/.../permission`)

Step 2 of #607. One cell is (group, `AccessClass`) and holds `PermissionLevel` ALLOW, ASK or DENY. `PermissionMatrix` is an immutable resolver over three inputs: the configured state, the runtime state and the `PermissionDefaults` beans of the extensions. `resolve(tool)` returns the level plus the layer that decided (`Layer`), which `explain` shows. Order: exact tool, group+operation cell, operation default, extension suggestion, built-in ALLOW; within a level runtime beats config. Unknown tools are EXECUTE and in group `external` (`ToolGroups`).
Extension suggestions (`PermissionDefaults`) apply only where no explicit operation default exists. Do not make them a layer above the preset: a preset must be able to replace them, and `trusted` would otherwise be unable to loosen Calendar and Drive.
Read and write are split on purpose. `PermissionPolicy` (`@Startup`, implements `ToolPermissions`) holds the live matrix and is what `ApprovalPolicy`, `ApprovalService` and `QlawToolProvider` read. `PermissionService` is the only writer. Keeping them apart avoids a CDI cycle (ApprovalService needs the policy, the service needs the ApprovalGate).
`ApprovalPolicy.requires` is `matrix == ASK || reasonFor(...).isPresent()`: a matrix ALLOW never lifts `qlawkus.approval.tools` or an `ApprovalRequirement`. `deny` is applied in `QlawToolProvider` next to the quarantine, and `ApprovalService.runTool` re-checks it so a request approved after its tool became DENY fails without running.
Tighten versus loosen is decided by comparing resolved matrices (`PermissionService.loosens`): every cell, operation default and known tool is compared before and after, so a preset or reset is classified by what it does, not by its name. Only `Actor.mayLoosen` (the authenticated REST admin) applies a loosening directly. A chat actor gets an `owner-action:permissions` approval request instead.
Owner actions (`OwnerAction` SPI, `PermissionChangeAction`) are how an approval applies something that is not a tool. The reserved prefix `owner-action:` is refused by `ApprovalService.requestApproval`, which is the only path the model-facing executor uses, so the model cannot forge one; `requestOwnerAction` is on `ApprovalGate` for the service only. `ApprovalRequest.isOwnerAction()` is `@JsonIgnore`: the file store reads with strict deserialization and a derived getter would otherwise be written as an unknown field. `CdiApprovalNotifier` announces the outcome of an owner action in the chat and does not resume the model.
Stale approvals: the pending request carries the level the cell had when it was asked (`from`) for a cell or tool change, or the state revision for a preset or reset. `applyApproved` throws if the live value differs, and the approval becomes FAILED.
Persistence is files only (`PermissionStateFile` `state.json`, `PermissionAuditLog` `audit.json`, under `qlawkus.agent.state.root/permissions`), written through Jackson tree nodes and an atomic move, so there is nothing to register for reflection. A Postgres mirror was deliberately not added: the state is a few small documents, it must work in the database-free distribution, and a mirror would add a second source of truth for little gain. `qlawkus.permissions.*` (`PermissionsConfig`, `PermissionConfigReader`) is the configured layer; a bad operation or preset name fails the start.
Frontends: `PermissionAdminResource` (`/api/admin/permissions`, `@Authenticated`, actor `admin-api:<user>`) and messaging `PermissionCommands` (`/permissions`, handled in `MessagingOrchestrator` before the model and after the allowlist). Both only call `PermissionService`. No `@Tool` references it, and `PermissionEnforcementTest` pins that.
The `app/` distribution ships `qlawkus.permissions.default.delete=ask` and `default.send=ask` as configuration only. Mutation-check precedence, the `mayLoosen` guard, the `owner-action:` refusal, the stale check and the denied-after-approval check when touching them; each has a test that fails without it.
Documented in `site/content/approvals.adoc`.
