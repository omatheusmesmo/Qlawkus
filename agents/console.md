# Console

The admin console and its optional extensions.

Behavior and configuration are documented for users in `site/content/console.adoc`, `site/content/voice.adoc` and `site/content/skills.adoc`, which is the source of truth. This page keeps the implementation rationale and the traps worth knowing before changing the code.

## console/

**`console/`** - Optional Quarkus extension (`deployment/` + `runtime/`, capability `console`) serving a server-rendered admin UI at `/console` (Qute + HTMX, no Node, `@Authenticated` reusing the app's Basic+Argon2id mechanism).
Read views inject the `client` SPIs directly; every mutating action is driven from the page by HTMX against the existing `/api/admin/*` endpoints, never re-implemented in a console resource.
The shared layout (`templates/console/base.html`) groups the navigation into Agent, Knowledge and System (`data-nav-group`; each group always holds a core page, so none is ever empty, and optional entries stay gated by `ConsoleFeature` beans) with `aria-current` on the active page and a skip link; below 900px the sidebar is a top bar and the nav a drawer driven by `console.js` (focus trap, Escape, backdrop; `ConsoleShellTest` pins the structure).
Theme is a `system|light|dark` radiogroup in the layout nav (`data-theme-choice`, driven by `console.js`, stored in `localStorage` key `qlawkus-theme`): the synchronous (non-deferred) `theme.js` in the head sets `data-theme` before the stylesheet loads (never an inline script: the console serves none, and `ChatConsoleTest` pins that), the tokens already carry the `[data-theme]` selectors, and one `:is(a, button, input, select, textarea, summary, [tabindex]):focus-visible` rule is the only focus ring.
`ThemeToggleTest` pins the markup and `browser/a11y-check.mjs` runs axe-core (`AXE_PATH` to `axe.min.js`) in both themes, so a new page or colour that drops under 4.5:1 fails it.
Action feedback is shared in `console.js` and the `base.html` layout: the `#qk-toasts` polite live region with `window.qlawkusToast(text, "ok"|"error")` (the one announced channel, the inline result nodes carry no live role), an `htmx:beforeRequest`/`afterRequest` pair that disables the used control and marks it `.is-busy` + `aria-busy`, and a server error body `{error, field}` that sets `aria-invalid`, `aria-describedby` and focus on the named field (or the only text field of the form); scripts that do not use HTMX call `qlawkusToast` themselves.
`FeedbackComponentsTest` pins the parts and `browser/feedback-check.mjs` the behavior.
Forms use one component set in `console/app.css` (`.field`/`.field-label`/`.field-hint`, the controls `.input`/`.select`/`.textarea`, `.field-check`, `.field-group`, `.actions`) and buttons use `.btn` with `btn-primary|secondary|danger` (+ `btn-sm`), including the ones `mcp.js` builds; per-page field rules are not allowed, and `FormComponentsTest` fails on a control or button without the shared classes and on a surviving per-page rule, while `integration-tests/console/browser/forms-check.mjs` checks for horizontal overflow down to 320px.
Destructive actions never use `hx-confirm` or the native `confirm`: the layout holds one `<dialog id="qk-confirm">` driven by `confirm.js`, which holds an HTMX request on `htmx:confirm` until a control's `data-confirm-action`/`data-confirm-target`/`data-confirm` are agreed to, and offers `window.qlawkusConfirm(...)` (a promise) to scripts that build their own controls; `ConfirmationDialogTest` fails on any `hx-confirm` or on a `hx-delete` missing the three attributes, and `integration-tests/console/browser/confirm-check.mjs` exercises focus, Escape, backdrop and confirm in a browser.
Pages: the onboarding wizard (first-run setup), management (`/console/memory`, `/console/skills`, `/console/cognition`; the skills page links the install panel of the optional `console-skill-hub` extension only when that extension is present), the full configuration editor (`/console/config`, see [composition.md](composition.md)), whose search, changed and phase filters, collapsible sections and section index are the client-side `console/config.js` over rows the server already rendered (the page marks each row `data-changed`, `data-owner` and `data-phase`, and `ConfigSourceLabel.isOwnerSource` decides which sections start open, so the distribution's own defaults never open one; a saved override counts at once through `RuntimeToggleWriter` and the staged document, since the running value only moves after a restart; the state lives in the URL hash; `integration-tests/console/browser/config-check.mjs` is the browser check), and the schedule page (`/console/schedule`, listing agent-created tasks from `DynamicTaskScheduler` with status, destination and next run, and cancelling through `DELETE /api/admin/scheduled-tasks/{id}`; also listing the 5 background jobs - memory review/curation, episodic consolidation, skill curation/lifecycle - with cron/last-run/next-run read from the live `io.quarkus.scheduler.Scheduler`, so they always match what is actually registered; each job carries an explicit `@Scheduled(identity = ...)` for this lookup.
The job registry itself - label, cron property, trigger endpoint - is static in `ScheduleConsoleResource` by necessity: no framework metadata links a job to the config property holding its cron, so it cannot be derived from `ConfigMetadataIndex`).
Cron is `RUN_TIME` like every other scheduler property, so editing it reuses the same `/api/admin/runtime-toggles` endpoint the config editor uses (applies on next restart, not live - `@Scheduled` resolves its cron property expression once at boot); triggering a job now hits its existing `/api/admin/*` endpoint, including a new `POST /api/admin/memory/consolidate` added alongside `/review` and `/curate` so all 5 jobs are triggerable uniformly.
The overview's Observability card is the only outbound reference: `ConsoleConfig` (`qlawkus.console.grafana-url`, `Optional<String>`, `RUN_TIME`) feeds `ObservabilityLinks`, which turns a plain http(s) Grafana base URL into the dashboard link (uid pinned to `examples/observability/grafana/qlawkus-agent.json` by a test) plus Explore on the `prometheus`/`tempo`/`loki` datasource uids `grafana/otel-lgtm` provisions, and yields nothing for an unset or non-http(s) value.
The overview's cards (`OverviewConsoleResource`, one `/console/overview/*` fragment per card, each polled by HTMX only while the tab is visible) read what the agent already exposes and add no admin endpoint: Health lists every `@Readiness` check through `ReadinessSource` (the only class touching the health API, registered by `ConsoleProcessor` only when `Capability.SMALLRYE_HEALTH` is present, so health stays `<optional>`; `ConsoleResource` hides the card when the bean is not resolvable); `ReadinessViews` reads only an `error`/`*Error` entry, the `degraded` store list and the pending-migration count from a check's data, never the rest, bounds the reason through `FailureSummary`/`SecretRedactor`, and turns a throwing check into its own `DOWN` row; Upcoming merges the `ScheduleConsoleResource.JOBS` registry with active `DynamicTaskScheduler` tasks (`UpcomingRuns` keeps the earliest three); Last redeploy reuses `RedeployRunView`; Approvals reads `ApprovalGate.pendingCount()` and the gated tool names from `ApprovalConfig`, never a request's arguments; Memory reads journal count, skill count and fact sources from the store SPIs; Model renders `client`'s `ModelChainStatus` (each tier's breaker through the read-only `CircuitBreakerMaintenance.currentState`, the permanent-failure streaks from `PermanentFailures`, and the interactive tier that answered last from `ServedTier`) through `ModelChainView`.
Every card goes through one wrapper that turns a failed read into a 200 `data-card-error` fragment with a bounded, redacted reason, because HTMX keeps the last good content when a poll fails.
Every instant a console view carries is a `TimeLabel` (ISO value, exact local reading, zone id from `DynamicTaskScheduler.zone()`) rendered through the one `console/time.html` fragment as `<time data-relative>`, which `time.js` turns into a relative label with `textContent` only.
The chat page (`/console/chat`, `ChatConsoleResource` + one vanilla `chat.js`, no library) does not re-implement chat either: the browser POSTs to the existing `/api/chat` SSE endpoint with `fetch` + a stream reader (HTMX's SSE extension cannot POST) and so shares whatever conversation that endpoint resolves (the shared one while `qlawkus.agent.shared-context` is on).
Model text is only ever inserted with `textContent`, never `innerHTML`; the minimal markdown is built node by node.
`/api/chat` keeps its unnamed text `data:` events and adds named `tool-start` / `tool-end` / `done` events produced by `agent.AgentStream` (built on the AI service's `Multi<ChatEvent>`, so it sees tools declared on `@RegisterAiService` as well as `@QlawTool` ones, never their results); each tool event is also a `ToolActivityEvent` CDI event with the conversation id for channels that only observe.
The detail level is the shared `agent.ToolProgress` vocabulary (`off|status|preview|verbose`), sent by the page from `qlawkus.console.chat.tool-progress` (`ConsoleConfig`, `RUN_TIME`) so the endpoint itself omits what a mode hides.
`console/deployment`'s `ConsoleProcessor` registers the runtime's `@Path` resources via `AdditionalBeanBuildItem` since the jar is not an implicit CDI bean archive on its own.
It also asks Qute for a value resolver for every record in the console package (`TemplateDataBuildItem`): a template reads a record by reflection in a JVM but a native image has none, so an unresolved view answers 500 there; `ConsoleTemplateTypesTest` pins it.
The visual tokens (light and dark values, between the `qlawkus-tokens` markers) are one block copied byte for byte into `console/.../console/app.css` and `site/web/app.css`, with Manrope self-hosted under each `fonts/` directory (no CDN, the console may run air-gapped); `DesignTokensTest` fails on drift, on a text pair under 4.5:1 in either theme, and on any remote font or import.

## console-voice/

**`console-voice/`** - Optional Quarkus extension (`deployment/` + `runtime/`, capability `console.voice`) adding a live voice session to the console at `/console/voice`.
The page is vanilla (no library): `console/voice.js` is the state machine and controls, `console/voice-orb.js` draws the canvas visual (listening follows the input AnalyserNode spectrum, speaking the playback AnalyserNode, reduced motion a static ring), and `console/voice-capture.js` is the AudioWorklet that captures PCM; the browser sends binary frames over the WebSocket `/console/voice/ws` (`VoiceSocket`, `@Authenticated`, with `VoiceOriginCheck` refusing any Origin that is not the console's own).
Each finished utterance (or typed message, `text`) becomes a turn: the utterance is wrapped as WAV and transcribed through the messaging `VoiceTranscriptionService.transcribe(audio, mime, hint)`, which requests `verbose_json` so the detected language returns with the text; the answer runs through `AgentStream` on the chat conversation, is cut into sentences (`SentenceSplitter`) and spoken in order through `VoiceSpeech` (default `TtsRouterSpeech`, buffered).
Languages share the core `ReplyLanguageResolver` with text channels; `LanguageTracker` supplies the displayed recognition summary, and an explicit selector choice forces the language for recognition and the reply.
The selected reply language is also passed to TTS, whose own provider fallback never rewrites the reply text.
One worker per session keeps text, audio and closing events in order, and a new utterance, typed message or interrupt supersedes the turn: its agent subscription is cancelled and late events are dropped.
Budgets live under `qlawkus.console.voice.*` (`VoiceSessionLimiter` caps sessions per owner).
Audio is never stored or logged; logs carry language codes, never text.
The Voice navigation entry is a `ConsoleFeature` bean named `voice`, read by the console's `ConsoleNavigation`, so the entry is absent when the extension is.
Docs: the live voice section of `site/content/voice.adoc`; the browser check is `integration-tests/console-voice/browser/voice-check.mjs` against `fake-providers.mjs`.

## console-skill-hub/

**`console-skill-hub/`** - Optional Quarkus extension (`deployment/` + `runtime/`, capability `console.skill-hub`) adding the skill install panel at `/console/skills/install`.
It depends on `console` and `qlawkus-tools-skill-hub`; neither depends on it, so the hub works without the console and the console without the hub.
The skills page links to the panel only when `ConsoleNavigation.hasFeature("skill-hub")` finds the `SkillHubConsoleFeature` bean, so the link is absent without the extension.
The page renders the installed skills (name, recorded source, install time, update and uninstall actions) through `SkillInstallConsoleResource`, which reads `SkillStore` only.
Every install, listing, update and uninstall is driven from `skill-install.js` (vanilla, `fetch` against `/api/admin/skills/install*`, `hx-delete` for uninstall and `hx-post` for update) against the hub's authenticated endpoints; the script renders every reply with `textContent`, never markup.
`ConsoleSkillHubProcessor` registers the page and feature bean with `AdditionalBeanBuildItem`.
Docs: the install panel section of `site/content/skills.adoc`.
