= Quick Start
:page-title: Quick Start
:page-description: Get Qlawkus running in minutes

== Prerequisites

* Docker -- the only requirement for the containerized run modes below; their images compile the whole project in-container
* JDK 25 and Maven -- only for dev mode (`quarkus:dev`) and building from source directly
* An `LLM_API_KEY` for your chosen provider (e.g. NVIDIA from https://build.nvidia.com/) -- only needed for the production profile, not for dev mode

== Clone and run

[source,bash]
----
git clone https://github.com/omatheusmesmo/qlawkus.git
cd qlawkus
mvn install -pl client -am -DskipTests
mvn -pl app -am quarkus:dev
----

IMPORTANT: Dev mode runs from the repository root, as above. The composition generator resolves
capabilities from the reactor, so the reactor has to be in the build for `agent.yml` to keep
governing the pom. See xref:composition.adoc#_dev_mode_reload[Composition > dev-mode reload].

Dev Services auto-provision PostgreSQL (pgvector) and Ollama via Testcontainers. No `.env` required.

The agent starts on `http://localhost:8080`. In dev mode, Flyway resets all databases on every restart.

TIP: The first build takes a few minutes. Subsequent starts are much faster.

== Try it out

[source,bash]
----
curl -X POST http://localhost:8080/api/chat/sync -u qlawkus:dev \
  -H 'Content-Type: application/json' -d '{"message":"Hello, who are you?"}'
----

== Other run modes

The containerized modes build the whole reactor *inside* Docker (a multi-stage
build on the Red Hat UBI OpenJDK image), so they need only Docker -- no host JDK
or Maven. The `run.sh` helper wraps Docker Compose; run `./run.sh --help` for the
full list of modes and actions.

NOTE: The first in-container build downloads the full dependency tree, so it takes
a few minutes. A cached Maven repo (a BuildKit cache mount) makes later builds fast.

=== Prebuilt images

Each release publishes three images to GitHub Container Registry, starting with the
next release (0.9.4 was released before publishing existed, so it has none):

[source,bash]
----
docker pull ghcr.io/omatheusmesmo/qlawkus:latest           # JVM (default)
docker pull ghcr.io/omatheusmesmo/qlawkus:latest-devtools  # JVM plus git and gh
docker pull ghcr.io/omatheusmesmo/qlawkus:latest-native    # GraalVM native
----

`latest` follows the newest release. A version tag (for example `0.9.5`, with the
same suffixes, such as `0.9.5-native`) pins a release, which is what a reproducible
deployment should use.

Pick the variant by what the agent has to do:

* JVM (no suffix): the default.
* Devtools (`-devtools`): the JVM image plus `git` and `gh`, for the code-review tools.
  See the devtools section below.
* Native (`-native`): a GraalVM binary on the micro base, for a smaller footprint and
  faster startup. It has no package manager, so there is no devtools variant, and the
  code-review tools that shell out to `git` and `gh` cannot run in it.

The Compose files still build from source. The prebuilt images are for running the
container directly, as the reference Kubernetes deployment does
(`examples/redeploy/k8s/deployment.yaml`); they need the same environment the Compose
file sets (datasources, `LLM_KIND`, `LLM_API_KEY`, the admin password hash).

=== Local Docker (Ollama + PostgreSQL)

Self-contained, no external API key required.

[source,bash]
----
./run.sh local
----

Exposes `http://localhost:8742`. An `ollama-init` one-shot container pulls the models on first start.

=== Production Docker (bring your own LLM + PostgreSQL)

Set `LLM_API_KEY` in `.env`. The Compose files ship `LLM_KIND=nvidia`; override `LLM_KIND` to pick another provider (the app's own default kind is `openai`).

[source,bash]
----
echo "LLM_KIND=nvidia"      >> .env   # or openai, deepseek, mistral, groq, xai, openrouter
echo "LLM_API_KEY=nvapi-xxxx" >> .env
./run.sh prod
----

The container maps host port *8742* to container `8080` (the Google OAuth redirect URI expects 8742).

For the native image (faster startup, lower memory; the native compile is heavy -- minutes and several GB of RAM):

[source,bash]
----
./run.sh native
----

=== Devtools image (git and gh)

The code-review tools shell out to `git` and `gh` (`gh pr review`), and the base
JVM image ships neither. Build the `devtools` variant to get both:

[source,bash]
----
QLAWKUS_IMAGE_VARIANT=devtools ./run.sh prod   # or local; also settable in .env
----

It is the same image plus `git` (from the UBI repos) and `gh` (from GitHub's
official RPM repo, at its latest release). That costs 175 MB on disk (791 MB
for the base, 966 MB for devtools; 242 MB and 286 MB of content), which is why
it is opt-in. `gh` still needs a GitHub token to act (`GH_TOKEN` in the container environment) and a checked-out
repository in the workspace. Build tools such as Maven or npm are not included.

The variant is JVM only: the native image runs on the Quarkus micro image, which
has no package manager, so `./run.sh native` refuses it. Without the variant the
tools do not fail silently: they answer that the binary is not on the PATH and
point at this image. To check an image you built, run
`scripts/check-devtools-image.sh <image>`.

TIP: `./run.sh prod logs` follows the app logs and `./run.sh prod down` stops the stack.

== Authentication

All HTTP endpoints require authentication. The bundled `app` verifies HTTP Basic against an *Argon2id* password hash, database-free (see xref:secrets.adoc[Secrets]). In dev mode (`quarkus:dev`) the credentials are **`qlawkus` / `dev`**, from a hash baked into the `%dev` profile. Any non-dev run is fail-closed: the app refuses to boot until you provide an Argon2id hash of your own password, under the keystore alias `qlawkus.admin.password-hash` or the environment variable `QLAWKUS_ADMIN_PASSWORD_HASH`. The username defaults to `qlawkus` (`qlawkus.admin.username`).
