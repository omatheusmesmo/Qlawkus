= Operations
:page-title: Operations
:page-description: Probes, readiness checks and cost estimation - what the agent reports about itself and what it deliberately does not.

Qlawkus reports on itself through the standard MicroProfile Health endpoints. This page covers what each probe answers, what each check actually asserts, and - just as importantly - what is not checked yet.

== The three probes

[cols="1,3"]
|===
|Endpoint |Answers

|`/q/health/ready`
|Should this instance receive traffic right now? Everything on this page reports here.

|`/q/health/live`
|Is this process broken beyond recovery? Deliberately narrow, see below.

|`/q/health/started`
|Has boot finished? Used as the startup probe.
|===

**Readiness and liveness are not the same question, and conflating them causes outages.** If your model provider goes down, this instance should leave the load balancer (readiness) but must not be killed (liveness): a restarted pod meets the same provider, so a liveness check that consulted the model would turn the provider's incident into a crash loop here.

For that reason the model is reported on readiness only.

The startup probe exists separately because JVM and native boot times differ by an order of magnitude. Putting the wait there rather than in `initialDelaySeconds` on the other probes means a slow JVM start is not mistaken for a hung process, while a native image begins serving as soon as it is up.

== What each check asserts

`qlawkus-model`:: Reads the state of the chat and embedding circuit breakers. Reports DOWN only when a breaker is OPEN **and** no fallback is configured - with a fallback available the agent can still answer, so it stays in rotation. The state is read through a read-only lookup, so polling readiness never generates provider traffic and can never trip or promote a breaker as a side effect.

It also reports a provider that keeps giving a permanent answer: a retired model (410), a revoked key (401 or 403) or a wrong model name (404). Those are never retried and never reach the fallback, so no breaker opens, yet every turn fails. After `qlawkus.model.permanent-failure.threshold` consecutive such answers (default 3) on the chat or embedding call of a user-facing turn, the check goes DOWN whatever the fallback setting, with `chatError` or `embeddingError` naming the status. One success clears it. The DOWN verdict lapses after `qlawkus.model.permanent-failure.window` (default 5 minutes) without a new failure, so the instance can receive the request that proves the provider is back; if it is not, the next failure takes the check straight back DOWN. Background jobs are reported as data and never change the status. A permanent embedding failure also never falls back to the secondary provider, since its vectors live in a different space: the turn fails instead of recalling silently worse.

`qlawkus-cognition`:: Checks that the agent can run a turn: it reads the persona (`soul`), the owner profile (`owner`) and the skill index (`skills`, only while `qlawkus.skills.enabled` is on), which every system message is built from, and proves working memory (`workingMemory`) is writable, since every turn appends to it. Any of those failing reports DOWN, with the reason under that key. On an instance that can serve, it also proves `facts`, `episodic` (the journals), `skills`, `soul` and `owner` can be written; when one cannot, the agent still answers but stops learning, so the check stays UP, lists the stores under `degraded` (comma-separated) and gives each reason under the store's key. The agent is single-instance, so DOWN means nobody answers, which is why only the turn path may cause it. Every probe goes through the store SPIs, so the same check is correct on `markdown` (one byte written to a dot-prefixed probe file in the store's root, then deleted), `pgvector` (the server is asked whether the session could write, without writing) and `hybrid` (both). This is what catches the mistake a container makes easy and silent: a state volume mounted read-only or with the wrong ownership, which every read passes.

`qlawkus-secrets-keystore`:: Reports whether a keystore that was meant to be present actually is. Keystore resolution is lenient by design - an absent keystore contributes nothing and the agent boots on your `.env`, which is what lets a fresh install start with no ceremony. Setting `qlawkus.secrets.keystore-password` is you stating that a keystore *is* expected, so a missing file at that point is a misconfiguration (typically a volume that did not mount) rather than a fresh install, and the check reports DOWN. With no password configured the feature is inert and the check stays UP. A wrong password needs no check: the agent fails to boot outright. The check reports how many secrets it holds and never an alias or a value, because `/q/health/ready` is unauthenticated.

`qlawkus-migrations`:: Present only when the `cognition-pgvector` extension is on the classpath. Answers whether the schema is at the version this build expects, which the built-in datasource check does not: a pod pointed at a database behind on migrations connects fine, passes readiness, and then fails at query time. Under the shipped default (`quarkus.flyway.migrate-at-start=true`) the agent applies its own migrations before serving, so this reports UP on every poll. It earns its place where that is turned off - the application has no DDL rights and a DBA applies migrations out of band, or a rolling deploy puts a pod carrying newer migrations in front of a database that has not been upgraded. There the pod stays out of rotation and flips to ready on its own once the schema catches up.

A database-free distribution has no `qlawkus-migrations` check at all rather than one that passes vacuously. Checks that are meaningful on only one backend ship with that backend.

== What is not checked

Worth stating plainly rather than leaving to be discovered:

* **A full disk on Postgres.** The pg probe asks whether the session may write; only an actual write would show the database is out of space.
* **Space at flush time on the markdown stores.** The probe writes one byte but does not sync it, so a volume that only refuses at flush still passes.
* **A volume that was never mounted.** If the deployment leaves the mount out (a Compose file without the volume, say), the store roots are created in the container's writable layer, so the probe passes on storage that will not survive the container. An empty volume and a missing one look the same from inside.
* **Exact privileges for each statement.** The pg probe checks the DML each table's store issues (INSERT, UPDATE, DELETE as applicable); it does not exercise triggers, row-level security policies or constraints.

The markdown probe creates and deletes a file in each store root on every poll. In a root that is synced or git-versioned (the hybrid facts, journals and skills), that bumps the directory's modification time and wakes inotify watchers every few seconds. The probe file is deleted in the same call; where deletes fail, the one fixed-name file is reused, so at most one is ever left.

== Wiring the probes

Both deploy paths read the same endpoint on purpose, so they agree on what "serving" means.

Kubernetes - see `examples/redeploy/k8s/deployment.yaml`:

[source,yaml]
----
readinessProbe:
  httpGet: { path: /q/health/ready, port: 8080 }
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /q/health/live, port: 8080 }
  periodSeconds: 10
startupProbe:
  httpGet: { path: /q/health/ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30
----

Docker Compose:

[source,yaml]
----
healthcheck:
  test: ["CMD", "curl", "-fsS", "http://localhost:8080/q/health/ready"]
  interval: 15s
  timeout: 5s
  retries: 3
  start_period: 60s
restart: unless-stopped
----

Health is an optional capability. A distribution that leaves `quarkus-smallrye-health` out has no health endpoints, and the probes fall back to a plain TCP check on the port.

[NOTE]
====
Qlawkus runs as a single instance by design: one agent serving one owner. The persona and owner profile are singletons, and the scheduled jobs (consolidation, curation, skill lifecycle) assume they are the only writer, so two processes on the same state would race the stores and run every nightly job twice.

The agent enforces this rather than relying on the deployment: at boot it takes an exclusive lock on `<qlawkus.agent.state.root>/.instance.lock` and holds it until shutdown. A second instance pointed at the same state fails to start, naming the process that holds it. That is also what you see when a test or dev-mode run shares the state root of a running agent; give it its own `qlawkus.agent.state.root`.

That decides the rollout strategy. The reference Deployment uses `replicas: 1` with `strategy: Recreate`, because a surge rollout starts the new pod while the old one still holds the state: on another node it hangs on the volume attach, on the same node it would be a second writer. The cost is a short gap in service per rollout.

The lock is per host, which matches a ReadWriteOnce volume. It does not stop two instances on different hosts that share only a database (a `pgvector` backend with no shared state volume); keep those to one instance by deployment.
====

== Telemetry

Metrics and tracing arrive as a composable capability rather than a hand-edited dependency. Select it in `agent.yml`:

[source,yaml]
----
build-time:
  default: disabled
  except:
    - observability
----

The build then puts the `qlawkus-observability` extension on the classpath, and a Prometheus scrape endpoint appears at `/q/metrics`. The agent's model meters need no instrumentation: `langchain4j_aiservices_timed` and `_counted` (tagged with the AI service, method, result and exception), plus `gen_ai_client_token_usage` split by `input` and `output`, follow the https://opentelemetry.io/docs/specs/semconv/gen-ai/[GenAI semantic conventions] and appear from the registry's presence alone.

Prometheus is what this distribution ships, not a locked choice. Exclude it and add `quarkus-micrometer-registry-otlp` or any other registry the ordinary Maven way.

=== Two independent levels of control

Selecting the capability decides whether the code is in the binary. Whether it runs is a separate, runtime decision:

[cols="1,2"]
|===
|`observability` in `agent.yml` |Applies at the next build - the pom generator adds or removes the dependency.
|`quarkus.micrometer.enabled`, `quarkus.otel.sdk.disabled` |Applies at the next restart, and both are editable from the console or `PUT /api/admin/runtime-toggles`.
|===

So a locked-down distribution omits telemetry at the module level, and an operator can still silence it at runtime without a rebuild.

=== Tracing ships off in the extension, on in the stack

The extension sets `quarkus.otel.sdk.disabled=true`. Upstream enables the SDK with the traces exporter pointing at OTLP on `localhost:4317`, so selecting the capability with no collector listening would log export failures in a loop for someone who only wanted metrics. Turn it on once you have a collector:

[source,properties]
----
quarkus.otel.sdk.disabled=false
quarkus.otel.exporter.otlp.endpoint=http://collector:4317
----

Both are runtime properties, so this is a toggle and a restart rather than a rebuild. With the SDK on, log records go out over the same OTLP connection as the spans, each stamped with its trace and span (`quarkus.otel.logs.enabled`, which the extension sets because it is fixed at build time).

Metrics need no such gate: a Prometheus registry only exposes a scrape endpoint and reaches out to nothing.

=== The bundled stack

The Compose stacks (`./run.sh prod`, `native` and `local`) bring up that collector themselves: an `lgtm` service running https://github.com/grafana/docker-otel-lgtm[`grafana/otel-lgtm`], one container holding an OpenTelemetry Collector, Prometheus, Tempo, Loki and Grafana. The agent services set the two properties above, pointing at `http://lgtm:4317`, so nothing else needs turning on.

[cols="1,2"]
|===
|Signal |Path

|Traces |OTLP to the collector, stored in Tempo
|Logs |OTLP to the collector, stored in Loki with `trace_id` and `span_id`
|Metrics |Prometheus scrapes `/q/metrics` on the agent's private port 9000 (see below)
|===

Grafana is on http://localhost:3000, and the console's Overview links to it (the stacks set `QLAWKUS_CONSOLE_GRAFANA_URL`, see xref:console.adoc#_observability_links[Console]), with the Qlawkus dashboard provisioned as its home page (the same `examples/observability/grafana/qlawkus-agent.json` the build checks against the metrics, mounted rather than copied). The Tempo and Loki data sources are linked both ways, so a trace opens its logs and a log line opens its trace.

Set `GRAFANA_ADMIN_PASSWORD` in `.env` before the first start:

[source,bash]
----
echo "GRAFANA_ADMIN_PASSWORD=$(openssl rand -base64 18)" >> .env
----

The image grants every anonymous visitor the Admin role, so the stack turns anonymous access off, and the container refuses to start without the password rather than fall back to `admin`/`admin`. The agent does not depend on it: with `lgtm` down, the agent keeps serving and only the telemetry is lost. Grafana reads the password only when it first creates its database, so changing it later takes the CLI, pointed at the data directory the image uses (without `GF_PATHS_DATA` it resets a different, empty database and reports success):

[source,bash]
----
docker compose exec -w /otel-lgtm/grafana -e GF_PATHS_DATA=/data/grafana/data lgtm \
  ./bin/grafana cli admin reset-admin-password '<new password>'
----

Then put the same value in `.env`, which the next recreate of the container checks.

Data lives on the `qlawkus_lgtm-data` volume. Upstream describes the image as meant for development, demo and testing, and points production at a managed backend; Qlawkus is single-instance by design, so one container on the same host is a fair fit. A deployment that outgrows it points `QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT` at its own collector and scrapes port 9000 from its own Prometheus, with no change to the agent.

The image tag is pinned in `docker/lgtm/compose.yml` and bumped by Dependabot. `docker/lgtm/prometheus.yaml` is the image's own file plus the agent's scrape job, so a bump also means re-copying the image's version of it.

=== Reading a turn as a trace

With tracing on, every tool call in a ReAct turn is its own span under the turn, so a slow answer shows how many tools ran, in what order, and which one stalled, and a tool's own HTTP calls nest under it. The tools declared on the AI service get that span from quarkus-langchain4j; the `@QlawTool` extension tools (Google Workspace, Skill Hub, shell, code review and the rest) get an identical one from the agent, so both read the same and one query finds them all:

* span name `langchain4j.tools.<tool name>`
* `gen_ai.operation.name=execute_tool`, `gen_ai.tool.name`, `gen_ai.tool.call.id`, `gen_ai.tool.type=function`
* status ERROR, with the exception recorded, when the tool throws or returns an error result

Tool arguments and results stay out of the span by default, since either can carry what the owner said. The upstream switches cover both kinds of tool: `quarkus.langchain4j.tracing.include-tool-arguments` and `quarkus.langchain4j.tracing.include-tool-result`, both runtime properties.

=== Logs that join their trace

Selecting the capability also switches the console to JSON, one object per line, which is what a container log pipeline can parse and query. `quarkus:dev` and test runs keep the readable format; turn JSON off in a deployment with `quarkus.log.console.json.enabled=false`, a runtime property.

Each entry carries the MDC, and that is where the trace ids live: a line logged while a span is current has `mdc.traceId` and `mdc.spanId`. Find the slow turn in the trace, then filter the logs on its `traceId`, and the two are one investigation. This works on the shipped configuration, before any collector exists: `quarkus.otel.sdk.disabled=true` stops spans from being exported, not from being created, so the ids still reach the logs.

=== What the INFO log says

At INFO the agent writes a short account of what it did, and never what was said. The startup summary comes first: three lines naming the provider, the primary, secondary and Ollama fallback models, the embedding model and dimension, the cognition backend, observability and self-observation switches, and the messaging channels whose token is configured (a channel is named, its token never is).

Each turn ends with one line, whatever channel it came from (REST, Discord, Telegram, the startup reflection):

----
Agent turn channel=telegram conversation=qlawkus-shared workload=interactive outcome=ok tier=primary duration=2310ms tools=2 [searchMemories,remember] facts=3 tokens=1204/233
----

`tier` is the model that produced the reply (`primary`, `secondary` or `fallback`), or `unknown` when the path does not report it. `tools` is the count and the names, `facts` is how many memories active memory injected, and `tokens` is `unknown` when the provider did not report them. A turn that was cut short by an error or a disconnect ends with `outcome=error` or `outcome=cancelled`.

Each `@QlawTool` call ends with one line that names the tool and says how it went:

----
Tool call searchMemories outcome=ok duration=41ms
----

Background jobs (memory review, memory curation, episodic consolidation, skill curation and lifecycle) log a start and an end with their counts, whether the scheduler or the admin endpoint started them:

----
Job memory-review finished duration=812ms removed=3 threshold=0.92
----

A job that fails logs one warning with the exception class, not its message.

Each messaging channel adds lines for what it received and what it sent. An accepted message logs once with its kind and a length (characters for text, bytes for voice); a sender outside the allowlist logs one warning with the provider and user id. A reply logs once, after the platform accepted every part, with the number of parts and the send time; a failed delivery logs one warning with the exception class. Voice logs the transcription and the synthesis:

----
Message accepted provider=telegram chatId=123456 userId=789 kind=text length=42
Reply delivered provider=telegram chatId=123456 parts=2 kind=text elapsedMs=318
Reply delivery failed provider=telegram chatId=123456 kind=text sentParts=0 of 1 exception=ClientWebApplicationException elapsedMs=212
Voice transcribed engine=whisper audioBytes=48213 elapsedMs=1270 outcome=ok
Speech synthesized provider=openai language=pt chars=180 elapsedMs=940 outcome=ok
----

The messaging lines carry `channel` (the provider) and `conversation` (the memory id) as MDC fields on that line only, so a reply sent from a worker thread still has them.

The turn and tool lines also carry `channel`, `conversation`, `workload` or `tool` as MDC fields, which the JSON console writes as `mdc.channel`, `mdc.conversation`, `mdc.workload` and `mdc.tool` next to `mdc.traceId`. The fields are set for the duration of the turn or tool call and cleared afterwards, and the same values appear in the message text, so a plain-text search finds them too (`|= "channel=telegram"`, `|= "Tool call searchMemories"`).

What the agent writes at INFO never includes message text, reply text, prompts, extracted facts, skill bodies, tool arguments or tool results. Those go to DEBUG only, so turning on DEBUG for a category is a deliberate act that brings the content back into the log. Structured identifiers (a conversation id, a tool name, a skill name, a count) are INFO; anything the owner or the model wrote is not.

=== What the agent measures about itself

The meters above arrive from upstream. These are the ones Qlawkus emits itself, because no upstream extension can see them: they describe the cognition subsystem, which is specific to this agent.

[cols="1,2,1"]
|===
|Meter |What it answers |Tags

|`qlawkus.retrieval.queries` +
`qlawkus.retrieval.facts` +
`qlawkus.retrieval.score` +
`qlawkus.retrieval.duration`
|Did active memory inject anything this turn, how much, and at what similarity. The score distribution is what separates "nothing relevant existed" from "everything landed just under `min-score`".
|`outcome`

|`qlawkus.embedding.facts` +
`qlawkus.embedding.segments` +
`qlawkus.embedding.oversized`
|Whether facts are embedding, and how far the chunker is fanning them out. A fact that never embeds is the failure that leaves an orphaned markdown file behind.
|`outcome`

|`qlawkus.job.duration` +
`qlawkus.job.items`
|Whether a scheduled job is getting slower or quietly processing nothing. The console already shows cron and last run; this is the series behind it.
|`job`, `outcome`

|`qlawkus.model.fallback` +
`qlawkus.model.circuit.state`
|How often the primary provider was abandoned, and the breaker state right now. The `tier` label says which tier was switched to: `secondary` (the same-provider model) or `fallback` (Ollama). The gauge reports `0` closed, `1` half-open, `2` open, and is published from startup so a healthy agent still has a series.
|`surface`, `tier` (fallback counter only)

|`qlawkus.tool.invocations` +
`qlawkus.tool.duration`
|Which tool is failing, rather than that some tool is. Covers the tool extensions; the built-in memory and skill tools are registered directly on the AI service and are not counted here.
|`tool`, `outcome`

|`qlawkus.store.operations` +
`qlawkus.store.duration`
|What the `markdown` / `pgvector` / `hybrid` switch actually costs, per store and per operation. Readiness polls appear here too, as `operation="verifyWritable"` (and `load` / `index`), so a degraded store records a failure on every poll; filter on `operation` when charting traffic.
|`store`, `backend`, `operation`, `outcome`

|`qlawkus.redeploy.runs` +
`qlawkus.redeploy.phase.duration` +
`qlawkus.redeploy.last.success.age`
|Whether redeploys are succeeding, which phase they fail in, how long each phase takes, and how long it has been since one last worked. The redeploy restarts the agent mid-run, so these are read from the persisted redeploy history (see xref:composition.adoc#_reporting_each_run[reporting each run]) rather than counted in memory; a restarted instance publishes the totals its predecessor reached. `outcome` on the duration is the phase's own, so a build that failed is not a slow successful one. The age gauge is `NaN` before the first success.
|`outcome`, `failed_phase` (`none` on a success); `phase`, `outcome`
|===

A Grafana dashboard for all of these, plus the upstream turn and model meters, ships under `examples/observability/grafana/qlawkus-agent.json`. It is versioned with the code and checked against it: the build fails when a panel queries a series the agent does not publish, or when a meter is charted nowhere.

The instrumentation lives in `qlawkus-client` and compiles against the Micrometer API, which opens no socket and exports nothing. With the `observability` capability deselected there is no registry bean, every meter call is a no-op, and nothing is published: telemetry is omitted at module level, not merely silenced by a flag.

=== The agent reading its own telemetry

Everything above is written for a person at a dashboard. The `self-observe` capability hands the same signals to the agent, so "why was my last answer slow", "which tool failed today" or "did memory recall anything" are questions it can answer by looking rather than guessing. It adds four tools:

[cols="1,1,2"]
|===
|Tool |Backend and API |Returns

|`queryMetrics(promql, lookback)`
|Prometheus `/api/v1/query`, or `/api/v1/query_range` when a lookback is given
|One line per series: its value now, or over the lookback its point count and minimum, maximum and last value (at most 60 points per series are evaluated).

|`findTraces(traceql, lookback)`
|Tempo `/api/search`
|Trace ids with root span, service, start and duration, plus the first few matching spans.

|`getTrace(traceId)`
|Tempo `/api/traces/<id>`
|A span tree: each span's name, duration and error status, depth-first in start order. Never the raw OTLP JSON.

|`queryLogs(logql, lookback)`
|Loki `/loki/api/v1/query_range`
|Log lines newest first, each with its timestamp and level.
|===

The tools exist to read, so the boundary is what makes them safe to hand to a model:

* *Read only.* Each call is one `GET` to a backend's query API. The tools never talk to Grafana, whose API could change dashboards or users, and never follow a redirect.
* *No SSRF.* The base URLs come from configuration only. The model supplies a query string, which travels URL-encoded as a single parameter value, so it cannot change the host, the path or the other parameters; a trace id must be hex before it becomes part of a path.
* *Bounded.* A lookback is clamped to `max-window`, and the result says so. That alone does not bound PromQL or LogQL, whose range selectors and `offset` read back from every evaluated point, so a query whose `[range]` or `offset` exceeds `max-window`, or uses the `@` modifier, is refused before any request. At most `max-results` series, traces, spans or lines come back, with a count of what was left out; each log line is cut at 1000 characters, the whole result at `max-chars`, and a backend answer over 4 MiB is refused.
* *Each call times out.* A request that runs past `timeout` is reported as too expensive and is not retried: against a query API a timeout means the query is heavy, and retrying it is the load the timeout prevents. A 429, a 5xx or a refused connection is retried, as for every HTTP client in the agent. A 400 is not, and the backend's own error comes back so the model can fix its query.
* *Data, not instructions.* Logs carry text from Discord or Telegram, and span names and labels carry tool names, so every result arrives inside a `<telemetry-data source="...">` block that opens with a warning to treat it as data. Any `<telemetry-data` or `</telemetry-data` inside the data is defused first, and newlines inside a log line are flattened, so a line cannot close the block and go on as if the tool were speaking.
* *What a span was given stays out.* `getTrace` shows only an allow-list of attributes that describe what a span did (tool and model names, token counts, HTTP method and status, database operation, error type). Tool arguments and results never appear, even when tracing is configured to record them.

The capability is off unless turned on, and a tool whose backend URL is unset says so instead of failing:

[source,properties]
----
qlawkus.self-observe.enabled=true
qlawkus.self-observe.prometheus-url=http://lgtm:9090
qlawkus.self-observe.tempo-url=http://lgtm:3200
qlawkus.self-observe.loki-url=http://lgtm:3100
----

`max-window` (default `6h`), `max-results` (`50`), `max-chars` (`8000`) and `timeout` (`10s`) are the bounds above; all are runtime properties, so the console or `PUT /api/admin/runtime-toggles` can change them. The Compose stacks set the four lines above against the bundled `lgtm` service, so the tools work there with no further setup. A locked-down distribution leaves `self-observe` out of `agent.yml`, and the tools are not in the binary at all.

=== Keep the scrape endpoint private

The scrape output carries token usage, provider and model names, and - once cost estimation is on - what the agent is spending. This distribution serves it on the Quarkus management interface, port 9000, and never on the public port, while health stays public for the probes:

[source,properties]
----
quarkus.management.enabled=true
quarkus.smallrye-health.management.enabled=false
----

Both are build-time properties. The scrape on 9000 takes no credential, deliberately: every authenticated identity in this distribution is the admin, so a credential for Prometheus would be the admin one, sitting in plaintext next to the Argon2id hash meant to protect it. The boundary is the network instead. Compose never publishes 9000, and the reference Kubernetes Deployment names it `management` so it can be kept out of any Service that leaves the cluster.

If you build your own distribution, either keep the same split or put `/q/metrics` behind whichever auth mechanism you wired in. The extension deliberately imposes no policy, because the mechanism is the integrator's choice.
