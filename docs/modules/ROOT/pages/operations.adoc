= Operations
:page-title: Operations
:page-description: Probes, readiness checks and cost estimation - what the agent reports about itself and what it deliberately does not.

Qlawkus reports on itself through the standard MicroProfile Health endpoints. This page covers what each probe answers, what each check actually asserts, and - just as importantly - what is not checked yet.

== The three probes

[cols="1,3"]
|===
|Endpoint |Answers

|`/q/health/ready`
|Should this instance receive traffic right now? Everything on this page reports here.

|`/q/health/live`
|Is this process broken beyond recovery? Deliberately narrow, see below.

|`/q/health/started`
|Has boot finished? Used as the startup probe.
|===

**Readiness and liveness are not the same question, and conflating them causes outages.** If your model provider goes down, this instance should leave the load balancer (readiness) but must not be killed (liveness): a restarted pod meets the same provider, so a liveness check that consulted the model would turn the provider's incident into a crash loop here.

For that reason the model is reported on readiness only.

The startup probe exists separately because JVM and native boot times differ by an order of magnitude. Putting the wait there rather than in `initialDelaySeconds` on the other probes means a slow JVM start is not mistaken for a hung process, while a native image begins serving as soon as it is up.

== What each check asserts

`qlawkus-model`:: Reads the state of the chat and embedding circuit breakers. Reports DOWN only when a breaker is OPEN **and** no fallback is configured - with a fallback available the agent can still answer, so it stays in rotation. The state is read through a read-only lookup, so polling readiness never generates provider traffic and can never trip or promote a breaker as a side effect.

`qlawkus-cognition`:: Loads the persona and the owner profile, which the agent needs to build a system message at all. It goes through the store SPIs rather than touching files or tables, so the same check is correct on `markdown`, `pgvector` and `hybrid`. This is what catches the mistake a container makes easy and silent: a state volume mounted with the wrong ownership.

`qlawkus-secrets-keystore`:: Reports whether a keystore that was meant to be present actually is. Keystore resolution is lenient by design - an absent keystore contributes nothing and the agent boots on your `.env`, which is what lets a fresh install start with no ceremony. Setting `qlawkus.secrets.keystore-password` is you stating that a keystore *is* expected, so a missing file at that point is a misconfiguration (typically a volume that did not mount) rather than a fresh install, and the check reports DOWN. With no password configured the feature is inert and the check stays UP. A wrong password needs no check: the agent fails to boot outright. The check reports how many secrets it holds and never an alias or a value, because `/q/health/ready` is unauthenticated.

`qlawkus-migrations`:: Present only when the `cognition-pgvector` extension is on the classpath. Answers whether the schema is at the version this build expects, which the built-in datasource check does not: a pod pointed at a database behind on migrations connects fine, passes readiness, and then fails at query time. Under the shipped default (`quarkus.flyway.migrate-at-start=true`) the agent applies its own migrations before serving, so this reports UP on every poll. It earns its place where that is turned off - the application has no DDL rights and a DBA applies migrations out of band, or a rolling deploy puts a pod carrying newer migrations in front of a database that has not been upgraded. There the pod stays out of rotation and flips to ready on its own once the schema catches up.

A database-free distribution has no `qlawkus-migrations` check at all rather than one that passes vacuously. Checks that are meaningful on only one backend ship with that backend.

== What is not checked

Worth stating plainly rather than leaving to be discovered:

* **Writability is not proven.** The cognition check reads the persona and profile; it does not establish that the agent can write. A volume mounted read-only, or owned by the wrong uid with world-readable files, passes readiness and then fails on the first `remember`.
* **Four of the six stores are not consulted.** Facts, skills, episodic journals and working memory are not part of readiness today. An instance that cannot write working memory currently reports ready.

Both are tracked in https://github.com/omatheusmesmo/Qlawkus/issues/310[issue #310], along with the decision each needs first: how to prove writability without polluting the stores on every poll, and which stores should block readiness rather than count as degraded-but-serving.

== Wiring the probes

Both deploy paths read the same endpoint on purpose, so they agree on what "serving" means.

Kubernetes - see `examples/redeploy/k8s/deployment.yaml`:

[source,yaml]
----
readinessProbe:
  httpGet: { path: /q/health/ready, port: 8080 }
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /q/health/live, port: 8080 }
  periodSeconds: 10
startupProbe:
  httpGet: { path: /q/health/ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30
----

Docker Compose:

[source,yaml]
----
healthcheck:
  test: ["CMD", "curl", "-fsS", "http://localhost:8080/q/health/ready"]
  interval: 15s
  timeout: 5s
  retries: 3
  start_period: 60s
restart: unless-stopped
----

Health is an optional capability. A distribution that leaves `quarkus-smallrye-health` out has no health endpoints, and the probes fall back to a plain TCP check on the port.

[NOTE]
====
The reference deployment runs `replicas: 1`, and that is architecture rather than an omission in the example. The persona and owner profile are singletons and the markdown stores write to one volume, so a second replica either fails to schedule or corrupts that state - and every replica would run the same nightly jobs against the same stores. See https://github.com/omatheusmesmo/Qlawkus/issues/297[issue #297].
====

== Telemetry

Metrics and tracing arrive as a composable capability rather than a hand-edited dependency. Select it in `agent.yml`:

[source,yaml]
----
build-time:
  default: disabled
  except:
    - observability
----

The build then puts the `qlawkus-observability` extension on the classpath, and a Prometheus scrape endpoint appears at `/q/metrics`. The agent's model meters need no instrumentation: `langchain4j_aiservices_timed` and `_counted` (tagged with the AI service, method, result and exception), plus `gen_ai_client_token_usage` split by `input` and `output`, follow the https://opentelemetry.io/docs/specs/semconv/gen-ai/[GenAI semantic conventions] and appear from the registry's presence alone.

Prometheus is what this distribution ships, not a locked choice. Exclude it and add `quarkus-micrometer-registry-otlp` or any other registry the ordinary Maven way.

=== Two independent levels of control

Selecting the capability decides whether the code is in the binary. Whether it runs is a separate, runtime decision:

[cols="1,2"]
|===
|`observability` in `agent.yml` |Applies at the next build - the pom generator adds or removes the dependency.
|`quarkus.micrometer.enabled`, `quarkus.otel.sdk.disabled` |Applies at the next restart, and both are editable from the console or `PUT /api/admin/runtime-toggles`.
|===

So a locked-down distribution omits telemetry at the module level, and an operator can still silence it at runtime without a rebuild.

=== Tracing ships off

The extension sets `quarkus.otel.sdk.disabled=true`. Upstream enables the SDK with the traces exporter pointing at OTLP on `localhost:4317`, so selecting the capability with no collector listening would log export failures in a loop for someone who only wanted metrics. Turn it on once you have a collector:

[source,properties]
----
quarkus.otel.sdk.disabled=false
quarkus.otel.exporter.otlp.endpoint=http://collector:4317
----

Both are runtime properties, so this is a toggle and a restart rather than a rebuild.

Metrics need no such gate: a Prometheus registry only exposes a scrape endpoint and reaches out to nothing.

=== What the agent measures about itself

The meters above arrive from upstream. These are the ones Qlawkus emits itself, because no upstream extension can see them: they describe the cognition subsystem, which is specific to this agent.

[cols="1,2,1"]
|===
|Meter |What it answers |Tags

|`qlawkus.retrieval.queries` +
`qlawkus.retrieval.facts` +
`qlawkus.retrieval.score` +
`qlawkus.retrieval.duration`
|Did active memory inject anything this turn, how much, and at what similarity. The score distribution is what separates "nothing relevant existed" from "everything landed just under `min-score`".
|`outcome`

|`qlawkus.embedding.facts` +
`qlawkus.embedding.segments` +
`qlawkus.embedding.oversized`
|Whether facts are embedding, and how far the chunker is fanning them out. A fact that never embeds is the failure that leaves an orphaned markdown file behind.
|`outcome`

|`qlawkus.job.duration` +
`qlawkus.job.items`
|Whether a scheduled job is getting slower or quietly processing nothing. The console already shows cron and last run; this is the series behind it.
|`job`, `outcome`

|`qlawkus.model.fallback` +
`qlawkus.model.circuit.state`
|How often the primary provider was abandoned, and the breaker state right now. The gauge reports `0` closed, `1` half-open, `2` open, and is published from startup so a healthy agent still has a series.
|`surface`

|`qlawkus.tool.invocations` +
`qlawkus.tool.duration`
|Which tool is failing, rather than that some tool is. Covers the tool extensions; the built-in memory and skill tools are registered directly on the AI service and are not counted here.
|`tool`, `outcome`

|`qlawkus.store.operations` +
`qlawkus.store.duration`
|What the `markdown` / `pgvector` / `hybrid` switch actually costs, per store and per operation.
|`store`, `backend`, `operation`, `outcome`
|===

The instrumentation lives in `qlawkus-client` and compiles against the Micrometer API, which opens no socket and exports nothing. With the `observability` capability deselected there is no registry bean, every meter call is a no-op, and nothing is published: telemetry is omitted at module level, not merely silenced by a flag.

=== Protect the scrape endpoint

The scrape output carries token usage, provider and model names, and - once cost estimation is on - what the agent is spending. This distribution keeps it behind the same credential as the admin API, while leaving health open for the probes:

[source,properties]
----
quarkus.http.auth.permission.metrics.paths=/q/metrics
quarkus.http.auth.permission.metrics.policy=authenticated
----

Prometheus supports `basic_auth` in its scrape configuration, so collection is unaffected. If you build your own distribution, apply the equivalent for whichever auth mechanism you wired in - the extension deliberately imposes no policy, because the mechanism is the integrator's choice.

== Cost estimation

An agent that runs jobs overnight on its own spends money while nobody is watching, so cost per job and per channel is a number you want before the invoice rather than after.

`quarkus-langchain4j` already reports token counts. Supplying a price turns them into the `gen_ai.client.estimated_cost` metric:

[source,properties]
----
qlawkus.cost.enabled=true
----

It is **off by default on purpose**. An estimate is indistinguishable from a measurement once it reaches a dashboard, so a default price would be a confident wrong number. Enter your real rates before switching it on; see the `qlawkus.cost` section of xref:config-reference.adoc[Configuration] for the properties.

If your billing is not a flat per-token rate - tiered pricing, a committed-spend contract, or a self-hosted model that costs nothing per call - supply your own `CostEstimator` bean and it is consulted first.
