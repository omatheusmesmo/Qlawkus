= Console
:page-title: Console
:page-description: The optional server-rendered admin UI - first-run setup, chat with the agent, plus memory, skills, cognition, config and schedule management.

The console is an optional server-rendered admin UI at `/console`. It is a first-run setup wizard and a set of management pages over the agent's existing admin API - memory, skills, cognition, configuration, and the background schedule. It is built with Qute templates and https://htmx.org[HTMX], so it needs no Node build and no separate frontend.

The console never re-implements admin logic. Its read views inject the same SPIs the agent uses (`FactStore`, `SkillStore`, the live Quarkus `Scheduler`, the config-metadata index); every mutating action is driven from the page by HTMX against the existing `/api/admin/*` endpoints. So the UI and the API can never drift, and anything the console does is equally scriptable with `curl`.

== Enabling and reaching it

The console is the composition capability `console`. It ships in the reference `app` (it is in the baked `agent.yml`), so a stock build already serves it; a slimmed distribution can leave it out (see xref:composition.adoc[Composition]). When present, browse to `/console` - `http://localhost:8080/console` in dev mode, or `http://localhost:8742/console` for the containerized run.

Every console page is `@Authenticated` and carries no login of its own: it reuses whatever mechanism the app already enforces on `/api/admin/*`. In the bundled distribution that is HTTP Basic over an Argon2id credential (`qlawkus` / `dev` in dev mode; see xref:secrets.adoc[Secrets]). Add `quarkus-oidc` to the app and the console is behind SSO with no console-side change.

== First-run setup wizard

On first boot the agent cannot yet talk to an LLM, so the Overview shows a setup banner linking to the wizard at `/console/setup`. The wizard writes nothing itself: it orchestrates the same primitives documented elsewhere - the keystore writer (secrets, applied on restart) and the composition admin service (a staged manifest, applied on the next rebuild).

It is split into two phases by the closed-world boundary, because some steps only make sense once a capability has actually been compiled in:

[cols="1,3",options="header"]
|===
|Phase |Steps

|*A - before a rebuild* |The LLM base URL, chat model and API key (saved to the keystore), and the capability selection (staged as an `agent.yml` manifest). These are all you need to get the agent talking and to choose what to build next.
|*B - after a rebuild* |The interactive steps a capability unlocks once it is baked in: a bot token for each messaging adapter that is present, and Google authorization for the Google Workspace tools. Each Phase B step is shown only for a capability the running app already carries.
|===

So a typical bring-up is: run the wizard's Phase A, rebuild and redeploy with the staged manifest (see xref:composition.adoc#_the_restart_contract[the restart contract]), then return to the wizard for Phase B on the capabilities you turned on.

== Management pages

[cols="1,3",options="header"]
|===
|Page |What it does

|*Overview* (`/console`) |A live status panel - app version, the baked composition posture and capability set, and a server clock that ticks on every HTMX poll to show the refresh is live. Hosts the first-run setup banner, and, once `qlawkus.console.grafana-url` is set, an Observability card (see below).
|*Chat* (`/console/chat`) |Talk to the agent. The page is a server-rendered shell with one small script (`/console/chat.js`, no build step, no library): the browser calls the existing `POST /api/chat` server-sent-events endpoint and streams the reply into the page, so the console adds no chat logic of its own. See <<_chat,Chat>> below.
|*Memory* (`/console/memory`) |The most recent facts, the fact sources in use, and the episodic journals. Review, curate and purge are HTMX calls to `/api/admin/memory/*`. See xref:memory.adoc[Memory].
|*Skills* (`/console/skills`) |The current skill index. Pin, delete, curate and the lifecycle sweep call `/api/admin/skills/*`. See xref:skills.adoc[Skills].
|*Cognition* (`/console/cognition`) |Reconcile and migrate between the markdown and pgvector representations, over `/api/admin/cognition/*`. Shown only when the `cognition.pgvector` capability is baked in (the console does not depend on that extension - it reads the manifest to decide). See xref:storage.adoc[Storage].
|*Config* (`/console/config`) |The full configuration editor: one section per documented config root, generated from the same `quarkus-config-doc` metadata that builds xref:config-reference.adoc[the config reference], never a hand-maintained list. Each property shows its live effective value and a short source label (`application.properties`, `env`, `keystore`, `default`, ...; the full source name is the tooltip); secrets never appear. Apply routes by config phase - `RUN_TIME` properties to `/api/admin/runtime-toggles` (apply on restart), `BUILD_TIME` ones to `/api/admin/config-overrides` (staged, apply on the next rebuild) - and the outcome shows in a banner at the top of the page. See xref:composition.adoc#_the_configuration_editor[Composition > the configuration editor].
|*Schedule* (`/console/schedule`) |The five background jobs (memory review, memory curation, episodic consolidation, skill curation, skill lifecycle). Each row's effective cron and previous/next fire times come from the live Quarkus `Scheduler`, looked up by the explicit `@Scheduled(identity = ...)` each job declares, so the schedule shown always matches what is actually registered. The job list itself - label, cron property, trigger endpoint - is a static registry in the page: nothing in the framework links a job to the config property holding its cron. Editing a cron reuses the `RUN_TIME` runtime-toggle path; triggering a job now hits its manual `/api/admin/*` endpoint. Below the jobs, a read-only panel shows the last redeploy the external loop reported (outcome, failed phase, per-phase durations, last success); there is nothing to trigger there, since the redeploy runs outside the app.
|===

=== Chat

`/console/chat` streams the agent's reply as it is written. Enter sends, Shift+Enter adds a line, and the send button stays disabled while a reply streams. An error line reports a 401, a server error, or a lost connection. Replies get light formatting (paragraphs, bold, inline code, fenced code blocks, lists) built node by node from plain text, so nothing a model writes is ever parsed as HTML. Each reply has a relative timestamp and a copy button, and the view follows the reply until you scroll up.

*Which conversation.* The page sends no memory id: `/api/chat` picks it, so the console is the same conversation as every other channel. With `qlawkus.agent.shared-context.enabled` on (the default, and on in the bundled app) that is the shared conversation also used by Discord and Telegram, so a thread started in the console can continue there. With it off, the console shares the REST API's own conversation.

*Tool activity.* While the agent works, each tool call shows as a compact card in the reply: the tool name, a spinner while it runs, then a check or cross and its duration. `POST /api/chat` carries this as named server-sent events next to the plain text events existing clients read (`tool-start`, `tool-end`, and a closing `done` with the tool count, duration and token usage when the provider reports it). Tool results are never in the stream; arguments are capped at 300 characters. How much the page shows is one setting:

[source,properties]
----
qlawkus.console.chat.tool-progress=preview
----

[cols="1,3",options="header"]
|===
|Value |Shown

|`off` |No cards, only a "N tools, Xs" summary line under the reply.
|`status` |The tool name and its duration.
|`preview` (default) |Adds the first 40 characters of the arguments.
|`verbose` |Adds the arguments (up to 300 characters) in a collapsible detail.
|===

The page sends the mode with each message, so the endpoint itself leaves out whatever the mode hides. It is a `RUN_TIME` property, editable from the Config page. Once a reply finishes, its cards fold into one "N tools, Xs" line per run of consecutive tool calls, which expands on click.

A note the Config and Schedule pages surface: when a property's effective value already comes from a source that outranks the runtime-toggle override file (an environment variable, `.env`, or a `-D` flag), the page warns that saving there will not take effect until that higher-priority source is removed - so a silent no-op is caught in the UI rather than by trial and error.

== Observability links

The console does not embed telemetry, it links to it. Set `qlawkus.console.grafana-url` (environment variable `QLAWKUS_CONSOLE_GRAFANA_URL`) to the address Grafana has *from the operator's browser* - not the in-network `lgtm:3000` the agent uses - and the Overview gains an Observability card with four links, each opening in a new tab:

* the Qlawkus dashboard, `<grafana-url>/d/qlawkus-agent` (the uid of `examples/observability/grafana/qlawkus-agent.json`, which a test pins);
* Grafana Explore on Prometheus, Tempo and Loki, selecting the data sources the `grafana/otel-lgtm` image provisions under the uids `prometheus`, `tempo` and `loki`. They are reached through Grafana because it is the only port the bundled stack publishes.

With nothing configured the card is absent. Only a plain `http` or `https` URL is accepted, without credentials, query or fragment: anything else is ignored with a warning (the value is not echoed, since a URL can carry credentials) and the agent still boots, because a cosmetic link must not take a single-instance agent down. A sub-path such as `https://ops.example.com/grafana` is kept. The Compose stacks set it to `http://localhost:3000`; override it in `.env` when Grafana is reached by another name.
