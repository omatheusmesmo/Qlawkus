= Quick Start
:page-title: Quick Start
:page-description: Get Qlawkus running in minutes

== Prerequisites

* Docker -- the only requirement for the containerized run modes below; their images compile the whole project in-container
* JDK 25 and Maven -- only for dev mode (`quarkus:dev`) and building from source directly
* An `LLM_API_KEY` for your chosen provider (e.g. NVIDIA from https://build.nvidia.com/) -- only needed for the production profile, not for dev mode

== Clone and run

[source,bash]
----
git clone https://github.com/omatheusmesmo/qlawkus.git
cd qlawkus
mvn install -pl client/deployment -am -DskipTests
mvn -pl app -am quarkus:dev
----

IMPORTANT: Dev mode runs from the repository root, as above. The composition generator resolves
capabilities from the reactor, so the reactor has to be in the build for `agent.yml` to keep
governing the pom. See xref:composition.adoc#_dev_mode_reload[Composition > dev-mode reload].

Dev Services auto-provision PostgreSQL (pgvector) and Ollama via Testcontainers. No `.env` required.

The agent starts on `http://localhost:8080`. In dev mode, Flyway resets all databases on every restart.

TIP: The first build takes a few minutes. Subsequent starts are much faster.

== Try it out

[source,bash]
----
curl -X POST http://localhost:8080/api/chat/sync -u qlawkus:dev \
  -H 'Content-Type: application/json' -d '{"message":"Hello, who are you?"}'
----

== Other run modes

The containerized modes build the whole reactor *inside* Docker (a multi-stage
build on the Red Hat UBI OpenJDK image), so they need only Docker -- no host JDK
or Maven. The `run.sh` helper wraps Docker Compose; run `./run.sh --help` for the
full list of modes and actions.

NOTE: The first in-container build downloads the full dependency tree, so it takes
a few minutes. A cached Maven repo (a BuildKit cache mount) makes later builds fast.

=== Prebuilt images

Each release publishes three images to GitHub Container Registry, starting with the
next release (0.9.4 was released before publishing existed, so it has none):

[source,bash]
----
docker pull ghcr.io/omatheusmesmo/qlawkus:latest           # JVM (default)
docker pull ghcr.io/omatheusmesmo/qlawkus:latest-devtools  # JVM plus git and gh
docker pull ghcr.io/omatheusmesmo/qlawkus:latest-native    # GraalVM native
----

`latest` follows the newest release. A version tag (for example `0.9.5`, with the
same suffixes, such as `0.9.5-native`) pins a release, which is what a reproducible
deployment should use.

Pick the variant by what the agent has to do:

* JVM (no suffix): the default.
* Devtools (`-devtools`): the JVM image plus `git` and `gh`, for the code-review tools.
  See the devtools section below.
* Native (`-native`): a GraalVM binary on UBI Minimal for a smaller footprint and
  faster startup. It includes util-linux for interactive PTY sessions.
  Code review requires a distribution that also supplies `git` and `gh`.

When running the native executable directly on Linux, install util-linux
(`/usr/bin/script`) and coreutils (`/usr/bin/stty` and `/usr/bin/tty`) for PTY sessions.

The Compose files still build from source. The prebuilt images are for running the
container directly, as the reference Kubernetes deployment does
(`examples/redeploy/k8s/deployment.yaml`); they need the same environment the Compose
file sets (datasources, `LLM_KIND`, `LLM_API_KEY`, the admin password hash).

=== Local Docker (Ollama + PostgreSQL)

Self-contained, no external API key required.

[source,bash]
----
./run.sh local
----

Exposes `http://localhost:8742`. An `ollama-init` one-shot container pulls the models on first start.

=== Production Docker (bring your own LLM + PostgreSQL)

Set `LLM_API_KEY` in `.env`. The Compose files ship `LLM_KIND=nvidia`; override `LLM_KIND` to pick another provider (the app's own default kind is `openai`).

[source,bash]
----
echo "LLM_KIND=nvidia"      >> .env   # or openai, deepseek, mistral, groq, xai, openrouter
echo "LLM_API_KEY=nvapi-xxxx" >> .env
./run.sh prod
----

The container maps host port *8742* to container `8080` (the Google OAuth redirect URI expects 8742).

For the native image (faster startup, lower memory; the native compile is heavy -- minutes and several GB of RAM):

[source,bash]
----
./run.sh native
----

=== Devtools image (git and gh)

The code-review tools shell out to `git` and `gh` (`gh pr review`), and the base
JVM image ships neither. Build the `devtools` variant to get both:

[source,bash]
----
QLAWKUS_IMAGE_VARIANT=devtools ./run.sh prod   # or local; also settable in .env
----

It is the same image plus `git` (from the UBI repos) and `gh` (from GitHub's
official RPM repo, at its latest release). That costs 175 MB on disk (791 MB
for the base, 966 MB for devtools; 242 MB and 286 MB of content), which is why
it is opt-in. `gh` still needs a GitHub token to act (`GH_TOKEN` in the container environment) and a checked-out
repository in the workspace. Build tools such as Maven or npm are not included.

The variant is JVM only: the native image runs on the Quarkus micro image, which
has no package manager, so `./run.sh native` refuses it. Without the variant the
tools do not fail silently: they answer that the binary is not on the PATH and
point at this image. To check an image you built, run
`scripts/check-devtools-image.sh <image>`.

TIP: `./run.sh prod logs` follows the app logs and `./run.sh prod down` stops the stack.

=== What `up` checks, and upgrading PostgreSQL

Before it builds, `./run.sh <mode> up` checks that host ports 8742, 5432 and 3000 are free (or held by the service of the same stack it would reuse). The JVM and native app services share 8742: if the other mode is running the script prints the `docker stop` command, or `--replace` stops only that container. A container of another Compose project, or a process outside Docker, is only reported. After the start it waits for `/q/health/ready` (`QLAWKUS_READY_TIMEOUT`, 300 seconds by default), prints each service with its state and URL, and exits non-zero with the last log lines when the agent never becomes ready. If a failed start left a container with a stale DNS resolver, `./run.sh <mode> up --recreate` recreates only the app container.

The stacks run PostgreSQL 19 on the volume `qlawkus_postgres`; the PostgreSQL 17 volume was `qlawkus_pgdata`. A major version cannot read another's data files, so starting over an old install would create an empty database. `up` therefore refuses while `qlawkus_pgdata` holds data and `qlawkus_postgres` does not exist:

[source,bash]
----
./run.sh prod down           # the old volume must not be in use
./run.sh migrate-postgres    # dump, restore, compare row counts in every table
./run.sh prod up
----

The old volume is only read and is kept as the rollback (start the previous Compose files on it to go back). The dumps stay in `~/.local/state/qlawkus/pg-migration-<timestamp>`. To start with an empty database on purpose, run `docker volume create qlawkus_postgres` first.

== Authentication

All HTTP endpoints require authentication. The bundled `app` verifies HTTP Basic against an *Argon2id* password hash, database-free (see xref:secrets.adoc[Secrets]). In dev mode (`quarkus:dev`) the credentials are **`qlawkus` / `dev`**, from a hash baked into the `%dev` profile. Any non-dev run is fail-closed: the app refuses to boot until you provide an Argon2id hash of your own password, under the keystore alias `qlawkus.admin.password-hash` or the environment variable `QLAWKUS_ADMIN_PASSWORD_HASH`. The username defaults to `qlawkus` (`qlawkus.admin.username`).

== Finding files and searching text

The core agent supplies `globFiles` and `grepFiles` without requiring `rg`, `fd`, a database,
or a network capability. Both use the configured workspace as the default search directory.
Relative paths are resolved from that workspace, and results are sorted by workspace-relative path.
With `qlawkus.workspace.restrict-to-workspace=true` (the default), search paths cannot leave it.
Disabling that restriction explicitly permits outside paths, which are reported as absolute paths.

`globFiles` accepts a required `pattern`, an optional directory `path`, and an optional result
`limit` (default 500). Globs support `*`, `?`, `[abc]`, `[!abc]`, ranges and whole-segment `**`.
For example, `**/*.java` includes Java files at the search root and at any directory depth;
`*.java` matches only files directly in that directory. Use `/` between glob segments.

`grepFiles` accepts a required regex `pattern`, optional file/directory `path`, optional file glob
`include`, `ignoreCase`, `literal`, `context`, and `limit` (default 100 matching lines).
An include such as `*.java` matches that basename at any depth. Match lines use
`path:line:text`; context lines use `path-line-text`, without duplicating overlapping context.
Set `literal=true` to search exact text containing regex punctuation.

Regex matching uses https://github.com/google/re2j[RE2/J] to avoid catastrophic backtracking.
It supports groups, alternation, repetition and character classes; lookaround and backreferences
are rejected explicitly. It is not the full Java/PCRE regex dialect. Regexes apply to individual
lines, not across newline boundaries.

Both tools respect nested workspace `.gitignore` files through
https://github.com/eclipse-jgit/jgit[JGit]'s ignore parser. Deeper rules and later matching rules
win. As in Git, a child cannot be re-included while its parent directory remains ignored.
This also applies when a subdirectory is selected explicitly. Global Git excludes and
`.git/info/exclude` are not read: searches do not consult configuration outside the workspace.
The `.git` entry is always omitted. Symbolic links, including links to paths inside the workspace,
are never followed. Content and ignore files are opened through anchored `SecureDirectoryStream`
handles with `NOFOLLOW_LINKS` on every component, including concurrent parent replacements.
Filesystems without secure directory access have those reads skipped instead of using an unsafe fallback.
An unreadable, non-UTF-8, binary, oversized or symlinked `.gitignore` causes that directory to
be skipped, so missing rules never expose files by accident.
JGit's wildcard matching uses backtracking, so ignore files also have a conservative complexity
budget: 512 non-comment rules, 1024 characters per rule, at most two whole-segment `**` components,
and at most two `*` characters in another segment (including adjacent stars). Matched paths are
limited to 4096 characters, 128 components and 255 characters per component. A directory whose rules exceed this
budget is skipped rather than partially applying its ignore rules. Glob queries themselves use
the linear-time engine and do not have this wildcard-complexity restriction.

`qlawkus.shell.glob.enabled` and `qlawkus.shell.grep.enabled` disable each tool. Their `max-results`
settings cap a requested `limit`. The shared `qlawkus.shell.search.*` properties bound visited
entries (50000), depth (64), time (5 seconds), output (32000 characters), bytes per file (1 MiB),
and total bytes read (16 MiB, including ignore files). Ignore files are additionally limited to
64 KiB each. The deadline is cooperative between filesystem operations and lines; an operating
system filesystem call can take longer. A reached limit always adds a truncation notice.

Grep skips binary, malformed-encoding, unreadable and oversized files and reports the count.
It uses `qlawkus.file.encoding` (UTF-8 by default), preserves line numbers across LF/CRLF/CR,
and strips a leading text BOM for searching. Lines over 65536 characters are skipped and counted;
returned line text is capped at `qlawkus.shell.search.max-line-length` (4000), with a marker.
Context is capped at `qlawkus.shell.search.max-context-lines` (5 on each side).
When the matching-line limit is reached, grep returns the final allowed context and stops;
its notice indicates that the rest of the search was not performed, rather than promising more matches.
