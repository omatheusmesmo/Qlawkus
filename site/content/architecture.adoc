== Reply language across channels

`ReplyLanguageResolver` is shared by streamed REST/console chat, synchronous AI-service calls,
the messaging agent runner and live voice. A decision supplies one ISO language code to
`AgentReplyStyle`; `SoulEngine` adds it to the system prompt for text as well as speech. Voice uses
that same result for TTS and passes the prepared turn into the stream without classifying it again.
The owner's message and conversation transcript remain unchanged.

When enabled with `qlawkus.reply-language.enabled`, the default decision implementation calls the
already registered chat-model chain, with the same NVIDIA and Ollama configuration used for fact
extraction. The classification is stateless and tool-free, bounded to 2000 input characters, and
isolated on the `decision` workload. Distributions may replace the `ReplyLanguageDecision` SPI.
The 256-entry conversation cache stores codes only; it provides context for ambiguous messages and
does not override a clear language change. Manual choices win. Model failures retain the prompt rule
to answer the owner's current language rather than copying the language of stored profile text,
retrieved documents or tool results. The reference app enables model-assisted selection.

== Workspace file reads

`readFile` can read a numbered page instead of sending a whole file to the model.
For example, these tool arguments request lines 101 through 200:

[source,json]
----
{"path":"src/main/java/App.java","offset":101,"limit":100}
----

Offsets start at 1. Providing either `offset` or `limit` enables paging; omitted
offsets start at 1, and omitted limits use `qlawkus.file.read.max-lines-per-page`
(default 2000). Requested limits are capped at that maximum. Returned lines use
`101|content` notation, and a truncated page names the next offset to request.
Individual lines are capped at `qlawkus.file.read.max-line-length` (default 2000
characters) and marked when shortened. Pages also respect the existing read-size
budget for numbered content; continuation and truncation markers are additional metadata.
Reads stream through the file without loading it or an oversized line into memory.

Omit both parameters to keep the original full-file format, including its line
endings. Both forms enforce workspace confinement and reject binary files; valid
text in the configured encoding, including Portuguese UTF-8 text, is readable.

== Exact file edits

`editFile` changes an existing workspace text file without asking the model to rewrite it.
Supply `path`, `oldText` and `newText`, or an ordered `edits` array of those text pairs:

[source,json]
----
{"path":"src/main/resources/application.properties","edits":[
  {"oldText":"feature.enabled=false","newText":"feature.enabled=true"},
  {"oldText":"timeout=10s","newText":"timeout=20s"}
]}
----

Matching is exact: indentation and spaces are never guessed. A missing or ambiguous match
rejects the entire call before writing. Use more surrounding text to select one occurrence,
or set `replaceAll=true` to replace every non-overlapping occurrence for every edit. Edits are
validated in order against the in-memory result of the preceding edit, then committed together.
An empty `newText` deletes the matched text; an empty `oldText` is refused. Up to 50 edits are
accepted in one call.

The configured `qlawkus.file.encoding` is used with strict decoding and encoding. UTF-8 BOMs
are preserved. For files with uniform line endings, LF/CRLF in the supplied arguments is
converted to the existing ending; existing file content is never globally normalized. Mixed
line-ending files use the arguments exactly as supplied. Binary or invalid text is refused.
The existing read/write byte limits apply, with a 16 MiB ceiling for each file read or written.

The tool returns a unified diff with three context lines around the changed region. Distant
edits share one hunk, so the preview can include unchanged lines between them. The response is
bounded by `qlawkus.file.edit.max-diff-chars` (default 12000, clamped to 512 to 64000); a truncated
preview is explicitly marked and is not a complete patch. The edit itself is fully applied.
Set `qlawkus.file.edit.enabled=false` to disable this tool.

== Multi-file patches

`applyPatch` applies several workspace operations in one tool call. The model sends a
`Begin Patch` / `End Patch` envelope: `Add File:` (path then full content), `Update File:`
(same exact `<<<SEARCH` / `===` / `>>>` blocks as `editFile`), `Delete File:`, and
`Move File:` with a following `To:` line. Operations run in order; the first failure stops
the batch and leaves any earlier writes on disk. Each changed file contributes a bounded
unified diff in the response, reusing `qlawkus.file.edit.max-diff-chars`.
Set `qlawkus.file.patch.enabled=false` to disable this tool.

Paths resolve from the configured workspace. Canonical path checks reject symlink escapes.
Calls editing the same canonical path are serialized within the process. The file identity,
modification time and bytes are checked again before the atomic replacement, which also
preserves POSIX permissions. A detected external modification aborts the edit. This recheck
is not an inter-process compare-and-swap: another program should not write the same file during
an edit. Filesystems without atomic replacement are refused, preserving the original file.

=== Measuring exact-match failures

Exact matching is a deliberate first step rather than a silent fuzzy fallback. Each call
emits `FILE_EDIT | outcome=matched|no_match|ambiguous|...` with edit/replacement counts only;
file paths, file content and search/replacement text are not logged by this tool. In Grafana
Explore with the existing Loki datasource, compare outcomes over representative conversations:

[source,logql]
----
sum by (edit_outcome) (count_over_time({service_name="qlawkus"} |= "FILE_EDIT | outcome="
  | regexp "outcome=(?P<edit_outcome>[a-z_]+)" [1h]))
----

Adapt the stream selector to your deployment labels. Divide `no_match` plus `ambiguous` by
those failures plus `matched` to measure the exact-match rejection rate before considering a
fuzzy strategy. A rejected batch is counted once even if earlier replacements would have matched.

== Tool discovery

By default the model receives the full tool catalog. Set
`qlawkus.agent.tool-search.enabled=true` and restart to enable semantic Tool Search
on the REST/streaming `AgentService`.
The model initially receives a search tool; discovered tools become available in
later tool-calling rounds. This includes extension tools from `QlawToolProvider`.

Search uses the existing embedding model, with upstream's embedding cache. It saves
tool descriptions in the initial request, but adds a search round and embedding
work. Keep it opt-in until token usage, latency and tool selection have been
compared on representative conversations. `AgentService` selects its supplier
explicitly: no global `ToolSearchStrategy` bean changes other AI services through
auto-detection. The declarative messaging `QlawkusAgent` retains the full catalog:
the Quarkus agentic integration does not yet propagate the upstream tool-search
supplier to its generated AI service. Enabling this option does not change
Discord or Telegram's tool selection.

Both agents share one ceiling of 100 sequential tool calls per turn, so a messaging turn can chain as many tool rounds as a REST turn. The declarative `QlawkusAgent` cannot take the limit as an annotation attribute, so it reads `quarkus.langchain4j.ai-service.max-tool-executions`, which Qlawkus publishes from the same constant at a low config ordinal. Setting that property in `application.properties`, a config file or the environment changes the messaging agent's ceiling only; `AgentService` keeps the value in its annotation.

Memory recall and the skill index are still injected automatically. Tool discovery
changes how the model chooses an action, not how it receives relevant memories.

== Bounded specialist delegation

The optional `specialists` capability ships a durable catalog with the reference distribution. Use *Specialists* in the authenticated console to create, edit, disable or remove an entry. The main agent can call `createSpecialist`, `listSpecialists` and `runSpecialists` from an owner conversation. Catalog changes apply immediately and persist in `specialists.json` under `qlawkus.agent.state.root`.

Specialists receive an explicit text snapshot and return evidence to the caller. Runs accept one or two entries and choose the sequence or parallel pattern at invocation time. The second worker in a sequence receives the first successful result alongside the original snapshot. Parallel workers independently receive the original snapshot. The runner uses the Quarkus virtual-thread executor and LangChain4j chat models. It allows one active run, a 45-second shared deadline, a 4 KiB snapshot and at most 256 requested output tokens per worker.

The owner selects permitted model tiers through `qlawkus.specialists.allowed-models`. The default permits `default`, which follows the agent's normal model chain (the primary model, then the secondary, then the local Ollama fallback), and `fallback`, which pins the local model. `primary` and `secondary` pin one provider model and stay off until the owner permits them. A specialist created without a tier uses `default`. To reduce the execution budget, configure `qlawkus.specialists.timeout-seconds` and `qlawkus.specialists.max-output-tokens`.

=== Evaluation

The design keeps Qlawkus single-owner and single-instance. The owner-facing agent chooses a fixed, read-only workflow and passes explicit snapshots to each specialist. The specialists receive only their assigned snapshot and fixed instructions. They return evidence, an outcome, and any approved artifact handles to the parent, which remains responsible for the reply, persona and owner profile.

Use the upstream LangChain4j workflow builders to compose specialists. Keep each model call in the batch workload, with dedicated concurrency slots and a shared deadline. A parent model call releases its model permit before a tool starts delegation. Workers use an isolated, temporary prompt and a fixed read-only operation. They receive no durable conversation store, tool registry, delivery destination or delegation callback.

The evaluation lives in the client extension tests. The programmatic LangChain4j builders assemble a sequence or parallel workflow from a validated runtime plan on the JVM. A plan supplies a name and instructions for each approved role. The roles select the input and keep the same execution permissions. The build still owns the Java implementation, declarative agent registrations and installed model adapters.

The prototype allows two workers, one model call per worker and depth one. Each worker checks a 2 KiB snapshot limit, requests at most 128 output tokens and validates a reported total of at most 1,024 tokens. The parent combines successful results alongside timeout, cancellation and validation outcomes. Only approved artifact handles supplied by the parent reach the result.

Successful delegation introduces two model requests and two small temporary snapshots. The deterministic fixture completes with 46 reported tokens across both calls. Running the requests in parallel reduces the wait only when the model and provider can serve both concurrently. The same `ChatModel` contract can use the configured local model. Measure latency, token reporting and cancellation behavior on representative local models and check the programmatic builders in a native image before enabling an optional composition capability.

See the link:https://docs.langchain4j.dev/tutorials/agents/[LangChain4j programmatic workflows] and link:https://docs.quarkiverse.io/quarkus-langchain4j/dev/agentic.html[Quarkus LangChain4j Agentic guide]. Quarkus Flow also documents a link:https://docs.quarkiverse.io/quarkus-flow/dev/concepts-agentic-langchain4j.html[runtime workflow builder] in preview.

Prefer an optional Quarkus extension when the specialist catalog, management or execution policies have a lifecycle that operators can configure independently. That extension owns plan validation and tool registration, and the reference app selects it through composition. If production delegation only composes the existing executor and shares its lifecycle, a package in `client` is sufficient. Keep shared interfaces as small as the actual callers require.

== Memory

The defining idea is two deliberate choices that set Qlawkus apart from agents that paste their whole memory into the system prompt:

* *Injected, not tool-called.* Relevant memory is retrieved and added automatically before every reply, so recall never depends on the model choosing to call a search tool.
* *Retrieved, not dumped.* Active memory uses Retrieval-Augmented Generation (RAG): only the facts relevant to the current turn are injected (query-relevant top-K), never the entire store. The prompt stays small and the per-turn cost stays roughly constant as memory grows.

See xref:memory.adoc[Memory] for the full treatment of this approach.

* *Persona* - the agent's own `Soul` (mood, focus, identity), rendered into the system prompt. Persisted by a pluggable `SoulStore` (markdown `soul.md` or a Postgres table) on the same `qlawkus.cognition.backend` switch.
* *Owner profile* - a `UserProfile` (the single person served) injected on every turn. Maintained by the `updateUserProfile` tool and refreshed nightly by the curation job. Persisted by a pluggable `UserProfileStore` (markdown `owner.md` or a Postgres table).
* *Facts* - long-term facts, each tagged with a source (`remember-tool`, `semantic-extractor`, `episodic-consolidator`, `transcript`). The store backend is selectable via `qlawkus.cognition.backend`: `markdown` (files plus an in-process embedding index, no database - the default when the pgvector extension is absent), `pgvector` (embeddings in Postgres), or `hybrid` (files mirrored into pgvector). All three retrieve query-relevant top-K through the same RAG path.
* *Working memory* - the rolling 40-message conversation window, a pluggable `WorkingMemoryStore` (markdown `<memoryId>.jsonl` files or a Postgres table) that also serves as the langchain4j `ChatMemoryStore`.
* *Active memory* - before each reply, relevant facts are retrieved and injected (transcripts excluded to keep it clean).
* *Transcripts (session search)* - every message is archived and semantically searchable via the `searchTranscripts` tool, distinct from curated facts.
* *Episodic journals* - a nightly job summarizes each day; the summary is embedded through the fact store (so it is surfaced by active memory) and the journal record is kept by an `EpisodicStore` whose backend follows the same `qlawkus.cognition.backend` switch: `markdown` (dated `<date>.md` files, no database), `pgvector` (the `Journal` table), or `hybrid` (files mirrored into pgvector).

All Postgres backends live in the optional `qlawkus-cognition-pgvector` extension; a build without it is database-free and runs entirely on the markdown stores.

=== Operational notes

* Passive fact extraction (`semantic-extractor`) runs on every channel (REST, Discord, Telegram). It observes `ChatCompletedEvent`, which is fired channel-agnostically by `ChatCompletionEmitter`. Gate it with `qlawkus.agent.semantic-extractor.enabled` (default `true`).
* Before each post-turn generation (facts, reusable skills, achievements), a turn gate decides whether the turn is worth it. The default gate says yes to every turn, so nothing changes until a distribution supplies its own. The gate runs on the batch workload and fails open: if it throws, the generation runs as it would have without a gate. Its decisions are counted by `qlawkus.turn.gate`.
* The optional `decision.nvidia` capability supplies a guarded NVIDIA classifier for the three post-turn questions. It sends the completed turn's user and assistant text only when enabled. See xref:operations.adoc#_nvidia_post_turn_decisions[NVIDIA post-turn decisions].
* The shared conversation (`AGENT_SHARED_CONTEXT=true`) means the owner is continuous across Discord, Telegram, and REST.
* To inspect or reset memory, use `GET` / `DELETE /api/admin/memory` (see xref:config-reference.adoc[Configuration]).

== Scheduled tasks

The agent can schedule reminders and recurring tasks at the owner's request, through `TaskSchedulerTool` (`scheduleTask`, `listScheduledTasks`, `cancelScheduledTask`). Each task is a Quartz job under a `qlawkus-task-` id, kept in a `ScheduledTaskStore` so it is registered again after a restart, and each reply goes to a messaging chat resolved without any id from the owner. The timing forms, destination rules, persistence, logs and limits are described in xref:scheduler.adoc[Scheduler].

== Skills (procedural memory)

Skills are the agent's *procedural* memory: reusable how-to procedures, complementing the *declarative* memory above (facts, owner profile). Each skill is a `SKILL.md` file (YAML frontmatter `name` + `description`, then a Markdown body).

Like memory, the skill index is *injected, not searched*: `SoulEngine` adds a `## Skills` block (name + description only) to the system prompt every turn, capped by `qlawkus.skills.max-injected`. The full body is loaded on demand with the `viewSkill` tool (progressive disclosure).

== Databases

Up to three PostgreSQL databases, Flyway-managed: `qlawkus` (persona, owner profile, chat history, journals, pgvector embeddings - present only when the `qlawkus-cognition-pgvector` extension is on the classpath; a markdown-only build has no default datasource), `qlawkus_google_auth` (OAuth), and `qlawkus_brag` (career brag documents).
