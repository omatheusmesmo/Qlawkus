= Skills
:page-title: Skills
:page-description: Procedural memory the agent writes, uses, and curates itself

Skills are Qlawkus's *procedural* memory: reusable how-to procedures the agent can author, load on demand, and curate over time. They complement the *declarative* memory (facts and the owner profile) described in xref:architecture.adoc#_memory[Architecture]: declarative memory is *what the agent knows*, skills are *how the agent does recurring things*.

Like memory, the skill index is **injected, not searched**. Every turn, `SoulEngine` adds a `## Skills` block (each skill's name and description only) to the system prompt, so the model always knows which procedures exist without having to decide to look. The full body is pulled in on demand with the `viewSkill` tool (progressive disclosure), keeping the prompt small.

See xref:architecture.adoc#_skills_procedural_memory[Architecture > Skills] for the data-flow diagram, and the xref:config-reference.adoc#_skills[Skills configuration reference] for every `qlawkus.skills.*` knob.

== Anatomy of a skill

A skill is a single `SKILL.md` file: YAML frontmatter with a `name` and `description`, followed by a Markdown body. The file follows the https://agentskills.io[agentskills.io] spec and is parsed by the upstream langchain4j skill loaders, so a `SKILL.md` written for Qlawkus is portable to any other agent that speaks the same format.

[source,markdown]
----
---
name: open-a-pr
description: Open a GitHub pull request from the current branch with a clean summary
---

# Open a pull request

1. Confirm the branch is pushed: `git status -sb`.
2. Draft a title that reads well in a changelog (no `feat:`/`fix:` prefix).
3. Open it: `gh pr create --title "<title>" --body "<summary>"`.
4. Never force-push to `main`; only to the feature branch, and only when asked.
----

The frontmatter is the *index*: `name` and `description` are what get injected each turn. The body is the *procedure*: it is loaded only when the agent calls `viewSkill` on that name.

== Where skills live

Skills are read from every directory in `qlawkus.skills.roots` (first match wins on a name clash) but **written only to the first, owned root** (default `~/.qlawkus/skills`).

[cols="1,3",options="header"]
|===
|Root |Role

|`~/.qlawkus/skills` (default, owned) |The agent's own skills. The only place new and auto-distilled skills are written, so self-authored procedures stay isolated.
|`.agents/skills` (opt-in) |The cross-agent project convention shared with other tools. Add it to `qlawkus.skills.roots` to *read* shared skills; it is never written to.
|===

This split is deliberate: running on a host (not a container), the agent should never pollute a shared `.agents/skills` with skills it invented for itself. Path traversal is rejected, so a skill name can never escape its root.

NOTE: Bundled skills (below) are a third, read-only source merged on top of these roots; an owned skill always wins a name clash with a bundled one.

== How the agent uses skills

* *Injection* - `SoulEngine` renders the index (`SkillIndexRenderer`) into the system prompt every turn, capped by `qlawkus.skills.max-injected`.
* *Progressive disclosure* - the `viewSkill` tool loads a single skill's full body when the agent needs the steps. This also records a use (see Lifecycle).
* *Authoring* - the agent creates and removes its own skills with the `createOrUpdateSkill` and `deleteSkill` tools.

== Auto-distillation and curation

Skills grow and stay clean on their own, mirroring the fact-memory subsystem:

* *Auto-distillation* - `SkillExtractorObserver` mines a reusable procedure from each completed turn (`ChatCompletedEvent`, fired channel-agnostically), gated by `qlawkus.skills.extractor.enabled` (default `true`). Passive authoring works on every channel (REST, Discord, Telegram).
* *Curation* - `SkillCurationJob` removes redundant skills. It runs on a schedule and can be triggered with `POST /api/admin/skills/curate`.

== Lifecycle

Using a skill (`viewSkill`) marks it used. `SkillLifecycleJob` then ages unused skills by recency, and any use revives a skill straight back to `ACTIVE`:

++++
<div class="mermaid">
stateDiagram-v2
    [*] --> ACTIVE: created / distilled
    ACTIVE --> STALE: unused 30 days
    STALE --> ARCHIVED: unused 90 days
    STALE --> ACTIVE: viewSkill
    ARCHIVED --> ACTIVE: viewSkill
    note right of ARCHIVED
      Dropped from the injected
      index, still loadable by name
    end note
</div>
++++

* `STALE` skills are unused but still injected; `ARCHIVED` ones leave the injected index (to keep the prompt compact) but stay loadable by name, so nothing is lost.
* Pinned skills never transition. Pin with `POST /api/admin/skills/{name}/pin`.
* The day thresholds and the sweep cron are config: `qlawkus.skills.lifecycle.stale-after-days` (default 30), `archive-after-days` (default 90), and `cron`.

Usage telemetry is stored where the backend lives: Postgres columns (`pgvector`/`hybrid`, migration `V7`) or a `.qlawkus-usage.json` sidecar next to the files (`markdown`).

== Bundled skills

Extensions and apps can ship read-only skills as classpath resources under `META-INF/qlawkus-skills/<name>/SKILL.md`. They are discovered and parsed at **build time** (a `@BuildStep` bakes them into a synthetic bean - no runtime classpath scanning) and merged, read-only, on top of the owned roots. This lets a tool extension contribute the procedures for using it, without writing to the user's filesystem.

== Storage backends

The cognition persistence backend is chosen at **build time** with `qlawkus.cognition.backend`. It governs where skills (and the rest of cognition) are stored:

[cols="1,3",options="header"]
|===
|Backend |Behavior

|`markdown` |`SKILL.md` files only, no database. This is the `@DefaultBean`, so it is what a build **without** the `cognition-pgvector` extension uses - a fully database-free distribution.
|`pgvector` |Skills in Postgres (the `skill` table, migration `V6`, lifecycle columns in `V7`). Durable server-side storage; requires the `cognition-pgvector` extension on the classpath.
|`hybrid` |`SKILL.md` files are the source of truth, mirrored into Postgres. This is what the reference `app` ships.
|===

Because the choice is build-time fixed, a markdown-only distribution carries no datasource or Flyway dependency for skills at all.

== Administration

All endpoints are under `/api/admin/skills` (Basic auth, same as the rest of the API):

[cols="2,3",options="header"]
|===
|Endpoint |What it does

|`GET /api/admin/skills` |List the current skill index.
|`GET /api/admin/skills/{name}` |Fetch a single skill (frontmatter + body).
|`DELETE /api/admin/skills/{name}` |Delete an owned skill.
|`POST /api/admin/skills/curate` |Run curation now (dedup redundant skills).
|`POST /api/admin/skills/lifecycle` |Run the lifecycle sweep now (age unused skills).
|`POST /api/admin/skills/{name}/pin` |Pin a skill so it never ages out (`?pinned=false` to unpin).
|`POST /api/admin/skills/install` |Install the one skill a link or `owner/repo` slug names (JSON `{"source": "..."}`). Requires the optional skill-hub extension.
|`POST /api/admin/skills/install/list` |List the skills a repository folder, repository, archive or gist holds (JSON `{"source": "..."}`), without installing.
|`POST /api/admin/skills/install/selection` |Install a selection from that listing (JSON `{"source": "...", "skills": "all"}` or `"triage,tdd"`), within the per-call cap.
|`POST /api/admin/skills/install/text` |Install a SKILL.md sent as the request body (`text/plain`).
|`POST /api/admin/skills/install/upload/list` |List the skills in an uploaded file: a SKILL.md, or a `.zip` or `.tar.gz` archive (multipart field `file`), without installing.
|`POST /api/admin/skills/install/upload/selection` |Install a selection from an uploaded file (multipart `file` plus `skills`, `all` or comma-separated names), within the per-call cap.
|`POST /api/admin/skills/install/update/{name}` |Re-fetch an installed skill from the source it was installed from. Returns `204`. Refuses a skill with no recorded source and one installed from an uploaded file.
|===

The optional xref:console.adoc[Console] admin UI drives all of these from a `/console/skills` page, so pinning, deleting, curating and running the lifecycle sweep are available without hand-rolling `curl`.

== The install panel

The optional `qlawkus-console-skill-hub` extension (composition capability `console.skill-hub`) adds an install page to the console at `/console/skills/install`. The skills page links to it only when the extension is present, so a distribution without it has no link and no page. The panel is a front end for the endpoints above, not a second install path: it never fetches or writes a skill itself.

* *From a link or repository* - paste a link, an `owner/repo` slug, a folder or a gist. The panel lists the skills found, with checkboxes, and installs the ones you select.
* *Pasted text* - paste a SKILL.md and install it.
* *Upload* - choose a SKILL.md, or a `.zip` or `.tar.gz` archive. An archive is listed, then a selection is installed. The upload is read in memory and held to the same caps as a download: `archive.max-bytes` for an archive, `max-skill-bytes` for a SKILL.md.
* *Installed skills* - each skill with its recorded source and install time. A skill installed from a link or repository offers *Update* (re-fetch from the same source) and *Uninstall*. A pasted skill has no source, so it offers only *Uninstall*. An uploaded skill cannot be fetched again, so it offers *Uninstall* only; upload a newer file to replace it.

Every result states what happened: *Installed*, *Refused* (with the reason), *Over a cap* (the selection exceeds `max-installs-per-call`, or the upload exceeds the upload limit), *Source unreachable* (the host could not be reached), or *Skill hub disabled*. Skill names, descriptions, sources and reasons are shown as text, never as markup.

The panel's per-call cap is `qlawkus.skill-hub.max-installs-per-call` and its upload limit is `qlawkus.skill-hub.archive.max-bytes`; both are shown on the page. An install from the panel is approved by the owner's request, the same as the admin REST endpoints. The panel does not preview in HITL mode.

== Remote Skill Hub

Everything above is *local* and offline. The optional `qlawkus-tools-skill-hub` extension adds the outward-facing side, so the agent can discover, install, update and publish skills mid-conversation, and the owner can install from any link they can copy. It is a separate module: omit it and a locked-down distribution physically cannot reach a registry (stronger than a config flag). The default implementation is plain Java (`java.net.http`), native-friendly, with no external CLI; it is an overridable `@DefaultBean`. Qlawkus never hosts or manages a registry itself.

== Installing from a source

Whatever the owner pastes is normalized to one of these forms before anything is fetched. The owner does not need to know how the registry models a skill.

[cols="1,2,2",options="header"]
|===
|Source |Example |What is installed

|A skill name |`triage` |The registry is searched. One clear match is installed (after approval); several are listed so the agent can ask which one. When several match, an exact name is taken as the clear one.
|An `owner/repo` slug |`acme/skills` |The repository's root `SKILL.md`, as before.
|An `owner/repo/skill` reference |`acme/skills/triage` |That skill folder, found under `skills/<skill>/` or anywhere in the repository tree.
|A repository or folder link |`https://github.com/acme/skills/tree/main/skills` |Every `SKILL.md` under the folder. List them, then install a selection under one approval.
|A file link |GitHub `blob` or `raw` links, GitLab `/-/blob` links, Bitbucket `/src` links, or any https link to a `SKILL.md` |That one skill.
|A skills.sh page |`https://skills.sh/acme/skills/triage` |That skill (the page is normalized to its repository and folder).
|A gist |`https://gist.github.com/<user>/<id>` |The gist's `SKILL.md`.
|An archive |`https://example.com/bundle.zip` or `.tar.gz` |Every skill folder inside it. List them, then select.
|Pasted text |A SKILL.md the owner pastes in chat (`installSkillFromText`) |That skill, after the same validation and approval.
|===

Only the `SKILL.md` text is ever read or saved. Scripts, reference files and other assets beside it are never fetched, extracted or run.

A selection is capped by `qlawkus.skill-hub.max-installs-per-call` (default 10). A larger selection is refused before anything is written, so the owner can split it. A partial failure installs what it can, then reports both the installed names and the failures.

== Safety of every fetch

[cols="1,3",options="header"]
|===
|Rule |What it does

|https only |Plain `http://` links are refused by the outbound policy, on the first request and on every redirect.
|No loopback, private or reserved targets |Every address a host resolves to is checked. Loopback, link-local, private (RFC 1918 and unique-local), carrier-grade NAT, `0.0.0.0/8` and multicast addresses are refused, including after a redirect. A redirect is followed at most three times, each hop resolved and checked again.
|No credentials in URLs |A link carrying `user:password` is refused, and the password is never echoed back.
|Size caps |A SKILL.md is capped at `max-skill-bytes` (default 256 KiB), an archive download at `archive.max-bytes` (10 MiB). Responses are read under the cap and the download stops at it.
|Archive limits |`archive.max-entries` (500) and `archive.max-expanded-bytes` (20 MiB, declared and decompressed). Entries with absolute paths, backslashes, `..` segments, symlinks, hard links or encryption are refused before any skill is read.
|In memory only |An archive is read from memory. Nothing is extracted to disk.
|Name validation |A skill name from frontmatter must use letters, digits, `.`, `_` and `-`, start with a letter or digit, and contain no `..`.
|Per-call timeouts |Each HTTP request uses `request-timeout`. A transient failure (429, 5xx, a network error) is retried up to three times per request, with backoff; permanent statuses are not retried.
|===

A residual risk remains: the host is resolved when the request is checked and again when the connection opens, so a DNS answer that changes between the two could point elsewhere. The check covers the answers the owner's host gives under normal conditions, but it is not a sandbox against an adversarial DNS server.

== Approval

Every install path honors `qlawkus.skill-hub.approval-mode`. In `hitl` the agent's tools preview first (listing the names for a multi-skill install, and the resolved source for a plain name) and write only on a confirmed re-call. In `yolo` they write immediately. The admin REST install endpoints do not preview: the request itself is the owner's approval, since the owner is authenticated and posts it directly. They keep every other limit above.

== Where skills come from later

Each installed skill records its source and install time. The agent's `listSkillSources` tool shows this for every skill, and `updateSkill` re-fetches a skill from its recorded source (approval applies). A skill that was pasted or written by the agent has no recorded source and cannot be updated this way. To remove a skill, use `deleteSkill`.

Provenance is kept in the `.qlawkus-usage.json` sidecar beside the files, so it is recorded for the `markdown` and `hybrid` backends. The `pgvector` backend does not store it yet: installs still work there, but `listSkillSources` shows no source and `updateSkill` refuses. Adding it needs a column in the `skill` table (a migration), which is not part of this change.

A skill installed from an uploaded file records the source `upload:<file name>`. It has no address to fetch from, so `updateSkill` and the update endpoint refuse it with the reason.

== Tools

The agent drives the hub with these tools:

[cols="2,3",options="header"]
|===
|Tool |What it does

|`searchSkillHub` |Searches the registry at `<base-url>/api/search` and, for each configured `well-known-hosts` entry, the `/.well-known/agent-skills/index.json` index (the agentskills.io standard). Results are deduped and capped by `max-results`.
|`installSkill` |Installs one skill from a name, a slug or a link (see the table above). A failed install is an error result for the agent and counts as `outcome=error` in the tool metrics.
|`listSkillsInSource` |Lists the skills a repository folder, repository, archive or gist holds, without installing any.
|`installSkillsFromSource` |Installs a selection (`all` or comma-separated names) from such a source under one approval, within the per-call cap.
|`installSkillFromText` |Installs a SKILL.md the owner pasted, with the same validation and approval.
|`updateSkill` |Re-fetches an installed skill from its recorded source.
|`listSkillSources` |Shows where each installed skill came from and when.
|`publishSkill` |Renders one of your own skills to `<publish.dir>/<name>/SKILL.md`. It never runs `git`: in a container, mount `publish.dir` to a host git working copy and push from the host (credentials stay out of the container).
|===

The admin REST endpoints under `/api/admin/skills/install` (listed above) are the same operations for the console and other admin clients.

[NOTE]
====
Chat attachments on Discord and Telegram are not part of this release. The console install panel is described in <<_the_install_panel>>.
====

[IMPORTANT]
====
The extension defaults to `hitl`, but the reference `app` ships `yolo` - so a stock build installs a skill the moment the agent asks for one. Set `SKILL_HUB_APPROVAL_MODE=hitl` (or `qlawkus.skill-hub.approval-mode=hitl`) to be asked first.
====

All settings live under `qlawkus.skill-hub.*`: `enabled`, `base-url`, `well-known-hosts`, `approval-mode`, `max-results`, `request-timeout`, `max-installs-per-call`, `max-skill-bytes`, `archive.max-bytes`, `archive.max-entries`, `archive.max-expanded-bytes`, `publish.enabled` and `publish.dir`. Publishing is opt-in (`publish.enabled=false` by default). The install panel adds no settings of its own.

== Roadmap

A skill is procedural *text* today. Because it already lives in its own directory (`<root>/<name>/SKILL.md`), a planned extension is *executable* skills that carry sibling scripts the agent runs as part of the procedure (the Anthropic `SKILL.md`-plus-assets model). It is not wired up yet, since skills and the workspace file/shell tools live behind separate confinement boundaries.
