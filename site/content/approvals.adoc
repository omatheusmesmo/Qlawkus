= Owner Approvals
:page-nav-group: Platform
:page-nav-order: 230
:page-title: Owner Approvals
:page-description: Hold selected tool calls for the owner's decision, and resume the task once it is made

An autonomous agent needs a boundary the model cannot cross on its own. Owner approvals are that boundary for the tools you name: a call to one of them is recorded, shown to the owner, and does not run until the owner approves it. The model cannot approve its own request, and a confirmation it writes into the conversation is never treated as one.

The gate is **opt-in**. With no tool named, every tool runs exactly as it did before, so enabling the feature changes nothing until you choose a tool.

== What is gated

Only `@QlawTool` tools are gated, and a tool is gated for one of two reasons: its name is listed in `qlawkus.approval.tools`, or an extension asked for it. Matching is exact on the tool name the model sees:

[source,properties]
----
qlawkus.approval.tools=sendEmail,deleteFile
----

An extension asks for the gate by publishing an `ApprovalRequirement` bean (`boolean requires(String toolName)`). The Skill Hub does so for its writing tools and the MCP client for `configureMcpConnection`, both only while their own `approval-mode` is `hitl` (see <<The hitl modes of Skill Hub and MCP>>). The skill scripts do the same for `runInstalledSkillScript`: every run of a script that a Skill Hub install wrote is gated whatever the hub's mode is (see xref:skills.adoc#_skills_with_scripts[Skills with scripts]). A requirement can only add tools to the gated set, never remove one the operator named. The permission matrix (see <<Tool permissions>>) is a third source: a tool whose cell says `ask` is gated the same way, and like the other two it can only add. The Google Calendar and Drive extensions used to publish a requirement for `updateEvent`, `deleteEvent` and `trashFile`; they now suggest matrix defaults instead, with the same switches (`qlawkus.google.calendar.require-approval` and `qlawkus.google.drive.trash-needs-approval`).

Tools declared directly on the AI service (the memory and skill tools, for example) are **not gated**. The gate sits in the tool chain of each `@QlawTool`, so a tool that must be approved has to be one of those. Gating is by name, not by the kind of action: nothing is gated by default, and reads and reversible local operations stay unguarded unless you name them.

== Access classes

Every `@QlawTool` tool also has an **access class** that says what it does to the world. The class is worked out when the application is built, and the permission matrix (see <<Tool permissions>>) reads it to decide whether a tool runs, asks or is hidden.

|===
| Class | The tool

| `READ` | Looks at something and changes nothing.
| `CREATE` | Makes something new.
| `UPDATE` | Changes something that already exists.
| `DELETE` | Removes or cancels something.
| `SEND` | Delivers something to a third party, or gives a third party access.
| `EXECUTE` | Runs a command or a script.
|===

A tool carries one class: the most consequential effect it can have. A tool that can add, edit and delete files is `DELETE`.

The build reads the class from the verb at the start of the method name, so a tool named for what it does needs nothing written on it:

|===
| Leading verb | Class

| `list`, `get`, `read`, `search`, `find`, `fetch`, `check`, `query`, `download`, `glob`, `grep`, `generate`, `analyze`, `suggest`, `test` | `READ`
| `create`, `add`, `schedule`, `save`, `install` | `CREATE`
| `update`, `set`, `edit`, `rename`, `write`, `untrash` | `UPDATE`
| `delete`, `remove`, `cancel`, `trash` | `DELETE`
| `send`, `share`, `invite`, `post`, `reply` | `SEND`
| `run`, `exec`, `shell` | `EXECUTE`
|===

Only the whole first word counts (`listEvents` is a read, `fileList` and `listing` are not). A method whose first word is none of these is `EXECUTE`: the most restrictive class, so a tool the build cannot place is never treated as harmless.

Where the verb is missing from the table or says something other than what the tool does (`heartbeatStatus` only reads, `sendInput` types into a shell, `uploadFile` creates, `applyPatch` can delete), put `@ToolAccess` on the method, or on the bean when every tool of it agrees. A method annotation wins over the bean annotation, and either wins over the verb:

[source,java]
----
@ToolAccess(AccessClass.EXECUTE)
@Tool("Send keystrokes to an interactive shell session")
public String sendInput(String sessionId, String input) { ... }
----

Two tools with the same name fail the build, naming both beans, because the model and the access lookup address a tool by name alone.

Each build writes the result to `target/qlawkus-tool-access.tsv` (tool, class, how it was reached, and the bean and method) and logs how many tools landed in each class and how many fell back to `EXECUTE`. How it was reached is `DECLARED` (`@ToolAccess`), `INFERRED` (the verb) or `FALLBACK` (no annotation and no known verb). The class of every tool of the shipped extensions is also pinned by a test, so a new or reclassified tool shows in a diff before it merges. Tools that come from a remote MCP server are not `@QlawTool` tools and have no class here.

== Tool permissions

The permission matrix lets the owner say "reads are free, deletes ask, nothing may run a shell" instead of listing tool names. Each cell is one operation (an access class) within one **group** and holds one of three levels:

|===
| Level | Effect

| `allow` | The tool runs.
| `ask` | The call waits for the owner, through the gate described above.
| `deny` | The tool is not offered to the model at all, the same way a quarantined tool is left out of the catalog, so the model does not see it and keep trying.
|===

With nothing configured every cell is `allow`: the extension keeps its behaviour, and the only tools that ask are the ones that already did.

=== Groups

A tool's group comes from where its bean lives. It is the first package segment after `dev.omatheusmesmo.qlawkus` once a leading `tool` or `tools` and a following `google` are dropped: `calendar`, `drive`, `gmail`, `sheets`, `storage` and `auth` for the Google tools, `shell` for the shell, file and patch tools, `skillhub`, `mcp`, `task`, `heartbeat`, `brag` and so on. A tool that has no build-time class, such as one a remote MCP server supplies, is in the `external` group and is treated as `execute`. `/permissions explain <tool>` and the matrix show the group and class of every tool.

=== Precedence

The most specific entry wins:

. the exception for the exact tool name
. the cell for the tool's group and operation
. the default for the operation (a preset fills these)
. what an extension suggests for its own group and operation
. `allow`

Within one level a change made at runtime wins over the configuration. The extension suggestions are the weakest voice: they apply only where the owner has set neither the group's cell nor the operation's default, so any choice made, a preset included, replaces them. That is how the Calendar `update` and `delete` cells and the Drive `delete` cell still ask by default while `require-approval` and `trash-needs-approval` are on.

`qlawkus.approval.tools` and the `ApprovalRequirement` beans of the Skill Hub, the MCP client and the skill scripts keep working and can only add `ask`: a matrix `allow` never lifts a tool they gate.

=== Presets

|===
| Preset | read | create | update | delete | send | execute

| `readonly` | allow | deny | deny | deny | deny | deny
| `ask-writes` | allow | allow | ask | ask | ask | ask
| `trusted` | allow | allow | allow | allow | allow | allow
|===

Applying a preset replaces every runtime change (group cells and tool exceptions included) with its six operation defaults.

=== Configuring it

[source,properties]
----
qlawkus.permissions.preset=ask-writes
qlawkus.permissions.default.delete=ask
qlawkus.permissions.group.calendar.delete=deny
qlawkus.permissions.tool.deleteEvent=ask
----

Operation defaults set explicitly override the preset. A misspelt operation or preset stops the start instead of being ignored. The reference distribution ships `qlawkus.permissions.default.delete=ask` and `qlawkus.permissions.default.send=ask`: the agent asks before it deletes or sends anything, and reads, creates and updates run directly. The full reference is in xref:config-reference.adoc#_tool_permissions[Configuration Reference].

=== Changing it

One service, `PermissionService`, is the only writer, and the surfaces below are thin frontends over it. No tool exposes it, so the model has no path to a change. The owner's changes are kept in `permissions/state.json` under `qlawkus.agent.state.root` and take effect at once, without a restart; they win over the configuration at the same level and survive restarts. They are always stored as files, whichever `qlawkus.cognition.backend` is active.

**Tightening is free, loosening is confirmed.** `allow` to `ask`, `ask` to `deny` and `allow` to `deny` apply at once for everyone. Loosening (`deny` to `ask`, `ask` to `allow`, `deny` to `allow`, or a preset or reset that loosens any cell) is applied at once only when the authenticated admin asks. When it comes from a chat it is recorded as an owner approval request and applied exactly once when the owner decides it, through the same `/approve <id>` and `/deny <id>` as any gated call. The approval re-checks that the cell still holds the level it was asked against (a preset or reset checks the policy revision), so a stale approval changes nothing and is reported as failed.

* **Chat.** `/permissions` shows the matrix, `/permissions calendar delete ask` sets a cell, `/permissions default send ask` sets an operation default, `/permissions tool deleteEvent deny` sets a tool exception, `/permissions preset readonly` applies a preset and `/permissions explain deleteEvent` says why a tool is decided as it is. The command is read before the model runs, and the sender must pass the same allowlist as every other message. The outcome of an approved change is announced in the chat without a model turn.
* **Admin REST**, all `@Authenticated`: `GET /api/admin/permissions` (the matrix), `PUT /api/admin/permissions/cells/{group}/{operation}` and `PUT /api/admin/permissions/tools/{tool}` with `{"level": "ask"}`, `POST /api/admin/permissions/presets/{name}`, `POST /api/admin/permissions/reset`, `GET /api/admin/permissions/explain/{tool}` and `GET /api/admin/permissions/audit`. A rejected change answers `400` with an `error` message. The group `default` in a cell path addresses the operation default.

`explain` names the cell that decided and, when `qlawkus.approval.tools` or an extension also gates the tool, says so.

=== Audit log

Every applied change is recorded in `permissions/audit.json`: who asked (the admin API user or the chat account), when, the channel, what changed, the level before and after, and, for a chat request, which owner decision released it and its approval request id. It keeps the latest `qlawkus.permissions.audit-retention` entries (500 by default) and is returned by `GET /api/admin/permissions/audit`, newest first.

=== What it does not cover

`deny` and the matrix `ask` apply to `@QlawTool` tools. The tools an external contributor supplies (remote MCP tools) can be hidden with `deny` but cannot be gated with `ask`, for the reason given under <<Limits>>. A tool approved earlier and still pending when its cell becomes `deny` does not run: the approval fails with a message saying the policy denied it.

== How a gated call is handled

When the model calls a gated tool:

1. The arguments are canonicalised (keys sorted, whitespace removed) and checked. If they look like a credential, no request is created and the model is told so: pass the secret through the vault instead of an argument.
2. A request is persisted with the exact arguments, a SHA-256 binding over the tool name and those arguments, a bounded redacted preview, and the conversation it came from.
3. The tool does **not** run. The model receives a result saying the action was not run, that approval request `<id>` is pending, and that it must not retry or ask for confirmation in chat.
4. If the conversation has a chat behind it (Telegram, Discord, Slack), the owner is told the id, the tool, the preview, and how to decide. On Telegram and Discord the notice carries Approve and Deny buttons; elsewhere it names the two commands.

== Lifecycle

[cols="1,3"]
|===
| Status | Meaning

| `PENDING` | Waiting for the owner. Survives restarts.
| `APPROVED` | The owner approved; the call is about to run. Brief, and never seen after a restart.
| `EXECUTING` | The approved call is running.
| `EXECUTED` | The call ran and completed. Its bounded, redacted result is kept.
| `FAILED` | The call ran and raised an error, or the arguments no longer matched the binding. It did not complete.
| `DENIED` | The owner refused it. It can never run.
| `EXPIRED` | Nobody decided before `qlawkus.approval.expiry`. It can never run.
| `NEEDS_REVIEW` | A restart found it `APPROVED` or `EXECUTING`. See below.
|===

A decision is a compare-and-set from `PENDING` (or `APPROVED` to `EXECUTING`). A duplicate callback, a second click, or a replayed command finds the request already decided and does nothing, so an approved call runs at most once per request.

Approval recomputes the binding hash from the stored arguments before it runs. Arguments changed after the owner was asked fail the check and the request becomes `FAILED` without running.

== How the owner decides

Decisions are owner-only and never reachable from the model:

* **Chat commands.** `/approve <id>` and `/deny <id>` in any chat the owner's account is allowlisted for (see xref:messaging.adoc[Messaging]). The command is read before the model runs, and the sender must pass the same allowlist as every other message.
* **Admin REST.** `GET /api/admin/approvals` lists requests, `GET /api/admin/approvals/{id}` shows one with its exact arguments, and `POST /api/admin/approvals/{id}/approve` or `/deny` decides it. A decision that takes effect answers `204`; a refused one answers `409`, and an unknown id `404`, each with an `error` message. Every endpoint is authenticated with the admin credential.
* **Console.** The `/console/approvals` page lists the queue and drives the same two decisions over HTMX.

There is no endpoint that runs a tool directly, so a decision can only release a call the owner already saw recorded.

=== Buttons

On **Telegram** and **Discord** the notice for a new request carries Approve and Deny buttons. A button is a convenience for typing the command, not a second decision path: a press becomes the plain `/approve <id>` or `/deny <id>` message from the user who pressed it and goes through the same orchestrator as typed text, so the messaging allowlist applies to the person who pressed, the model is never involved, and the compare-and-set above still decides.

* A press by someone outside the allowlist decides nothing and leaves the buttons for the owner. Telegram answers it with an empty acknowledgement; Discord answers it privately with "Not authorized.".
* A payload this feature did not create, or a malformed request id, is ignored without asking the allowlist.
* After a decision is processed the buttons are removed, so a second press cannot be made. If processing fails, the buttons stay and the owner can try again.
* The payloads are `qa:approve:<id>` and `qa:deny:<id>`, 43 bytes, inside Telegram's 64-byte `callback_data` limit.
* On Telegram a button press arriving through the **webhook** is accepted only when `qlawkus.messaging.telegram.webhook-secret-token` is configured and the `X-Telegram-Bot-Api-Secret-Token` header matches; otherwise the webhook answers `403`. Without that check anyone who knew the owner's numeric id could post a forged press. A press received by long polling is authenticated by the bot token itself.
* If the prompt cannot be posted with buttons (no bot token, a gateway that is down, a failed call), the same notice is sent as text with the commands, so a request is never left without a way to decide.

**Slack** has no buttons. Its adapter has no interactivity endpoint and no signature verification for one, and Slack is not part of the reference distribution, so a Slack chat keeps the `/approve` and `/deny` text fallback. Adding buttons there needs its interactivity endpoint and signing-secret check first.

== The hitl modes of Skill Hub and MCP

`qlawkus.skill-hub.approval-mode=hitl` and `qlawkus.mcp.approval-mode=hitl` used to preview a change and then rely on the model repeating the call with `confirm=true`. That confirmation was written by the model, so it was never an owner decision. Both now use this gate:

* The writing Skill Hub tools (`installSkill`, `installSkillsFromSource`, `installSkillFromText`, `updateSkill`, `publishSkill`) and `configureMcpConnection` are gated while their mode is `hitl`. The call is recorded as a request, the owner decides, and the approved call runs once with the stored arguments.
* The tool itself also refuses to write unless it is running as an approved execution (`ApprovedExecution`, a marker only `ApprovalService` sets around the call). So a path that bypasses the provider, or a model that passes `confirm=true`, still writes nothing.
* The `confirm` parameter is kept so existing tool schemas still validate, and is ignored. Prompts and tool descriptions no longer tell the model to use it.
* `yolo` is unchanged: the tool acts immediately and nothing is gated.
* The admin REST endpoints and the console panels are the owner acting directly and never ask, as before.

If you relied on the old flow: nothing to configure. Set the mode to `hitl` and decisions arrive through the same commands, buttons, REST endpoints and console page as any other gated tool. Listing a tool in `qlawkus.approval.tools` still works on top of this.

== Resuming the task

After the owner approves or denies, the agent resumes the conversation the request came from. It is told the outcome (executed with its result, failed, or denied) and either carries on with the task or reports the outcome. Its reply goes to the same chat. The resumed turn runs on the interactive workload, since the owner is waiting for it.

Expiry and review do **not** resume the agent: the owner is told in the chat, and no model turn is spent while nobody is there.

Requests that came from the REST API or the console have no chat to resume into. Their outcome is recorded and visible in the queue, but the agent is not woken; the owner tells it the outcome in the next message.

== Restarts and NEEDS_REVIEW

Pending requests are stored on disk before the model is told about them, so a restart leaves them decidable. The owner can still approve or deny one after the agent comes back.

A request that was `APPROVED` or `EXECUTING` when the process stopped is different. Whether its external effect happened is unknown, so it is never run again. At boot it becomes `NEEDS_REVIEW`, the owner is told, and the queue shows it until a person looks at it. Nothing is replayed automatically.

Expired requests are swept every 60 seconds and reported to the chat that asked.

== Idempotency

An approved call is executed once, with the request id recorded before the call starts. No `@QlawTool` accepts an idempotency key today, so the request id is not passed to the provider. For a tool that talks to an external service, a crash during the call is therefore the `NEEDS_REVIEW` case above, not an automatic retry. Give a tool an idempotency parameter if the provider supports one.

== Storage

The store follows `qlawkus.cognition.backend`, like the other cognition stores. The default (`markdown`) writes one JSON file per request under `qlawkus.agent.state.root`, in `approvals/`. Each write goes to a sibling file and is moved into place, so a crash mid-write keeps the previous version. A corrupt file is skipped with a warning and never stops boot. Only settled requests are pruned, oldest first, once more than 500 accumulate; pending and `NEEDS_REVIEW` requests are never dropped.

With `pgvector` the requests are rows in the `approval_request` table (created by the optional `cognition-pgvector` extension) and a decision is applied under a row lock, so two callbacks racing for one request still produce a single winner. With `hybrid` the files are the source of truth and the table is a mirror: a decision is taken on the file, and a failure to write the mirror is logged and never undoes or blocks it.

The readiness check probes the approval store with the cognition stores. A failure there is reported as `degraded`, not DOWN, because the agent still answers while it cannot record decisions.

The files hold the exact arguments and the results of executed calls, so they are as sensitive as the tools themselves. Keep the state root on a volume with the same access controls as the rest of the agent's data.

== Configuration

The full reference is in xref:config-reference.adoc#_approval[Configuration Reference] (the permission matrix has its own table under <<Tool permissions>>). The four approval properties:

[cols="2,1,3"]
|===
| Property | Default | Meaning

| `qlawkus.approval.tools` | none | Tool names that need approval. Empty means nothing is gated.
| `qlawkus.approval.expiry` | `24h` | How long a request stays decidable.
| `qlawkus.approval.max-pending` | `50` | Requests that may wait at once. A call beyond this is refused, not queued.
| `qlawkus.approval.preview-max-chars` | `500` | Longest argument text shown in a preview.
|===

== Limits

* Tools declared on the AI service are not gated. Only `@QlawTool` tools are.
* Tools contributed by an external source (the remote tools of MCP servers, through `QlawToolContributor`) are not gated. The resume path can only rebuild a `@QlawTool` executor by name, so an approved remote call could not be released, and a gate that records a request it cannot execute would be worse than none. Control which servers are connected instead: `configureMcpConnection` is gated in `hitl`, and the console and admin API are owner-only.
* Slack has no approval buttons (see <<Buttons>>).
* A tool has one access class, the most consequential thing it can do, so a tool that performs several actions is gated as one (see <<Access classes>>).
* The model cannot approve, and no tool exposes an approval path or the permission service.
* The approval queue is per instance, like the rest of the agent state. Qlawkus is single-instance.
* Redaction protects the preview, the notices and the result summary. It cannot stop a tool that deliberately returns a secret from doing so.

== Telemetry

Four counters, documented in xref:operations.adoc[Operations] and charted on the Approvals row of the reference dashboard:

* `qlawkus_approval_requests_total{outcome}` - `created` or `refused` before any request existed
* `qlawkus_approval_decisions_total{outcome}` - `approved`, `denied`, `expired`, or `refused` (a replayed or mismatched decision)
* `qlawkus_approval_executions_total{outcome}` - `executed` or `failed`
* `qlawkus_approval_needs_review_total` - requests a restart sent to review

The logs carry request ids, tool names and counts. They never carry argument content.
