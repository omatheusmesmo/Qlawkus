= Secrets
:page-title: Secrets
:page-description: Keep secrets in an encrypted keystore on a volume instead of plain environment variables, with no database.

Qlawkus can read secrets from an encrypted PKCS12 keystore on a mounted volume instead of plain environment variables, with no datasource involved. The `qlawkus-client` extension wires this up by convention, so it works in a database-free distribution and inside a container.

== How it works

Each entry (alias) in the keystore is named after the configuration property it supplies. A stored alias transparently overrides the matching property, so consumers keep reading an ordinary `@ConfigProperty` and need no change. For example, an alias `quarkus.langchain4j.openai."primary".api-key` supplies the LLM key that would otherwise come from `LLM_API_KEY`.

Resolution is lenient when the file is absent: with no keystore present the agent boots normally on your `.env`, and the feature stays inert until you drop a keystore in place.

== Precedence

`qlawkus-client` publishes keystore secrets at config ordinal `qlawkus.secrets.keystore-ordinal` (default `350`), so a stored secret is authoritative:

[source,text]
----
system properties (400)  >  KEYSTORE (350)  >  env vars (300)  >  .env (295)  >  application.properties (250)
----

A secret in the keystore therefore wins over the matching environment variable, so the rule is simply: drop it in the keystore and it takes effect, with no stray env default able to shadow it. Only a system property (`-D...`) still overrides, which keeps an emergency operator override available. If you would rather let an environment variable override a stored secret, lower `qlawkus.secrets.keystore-ordinal` below `300`.

== Onboarding a secret

Add a secret with `keytool`, naming the alias after the property it overrides:

[source,bash]
----
keytool -importpass \
  -alias 'quarkus.langchain4j.openai."primary".api-key' \
  -keystore ~/.qlawkus/secrets.p12 \
  -storetype PKCS12
----

`keytool` prompts for the secret value and for the keystore password. Repeat once per secret. List what is stored with:

[source,bash]
----
keytool -list -keystore ~/.qlawkus/secrets.p12 -storetype PKCS12
----

== Onboarding via the admin API

If you would rather not use `keytool`, the agent exposes a basic-auth gated admin API that writes the same keystore (it creates the file on first write, storing each entry exactly the way `keytool -importpass` does). The secret value is never echoed back or logged. This is what an onboarding UI calls.

[source,bash]
----
# Store a secret (alias = the config property it supplies)
curl -u "qlawkus:$ADMIN_PASSWORD" -X PUT \
  http://localhost:8742/api/admin/secrets \
  -H 'Content-Type: application/json' \
  -d '{"alias":"quarkus.langchain4j.openai.\"primary\".api-key","value":"<the-secret>"}'

# List stored aliases (names only, never values)
curl -u "qlawkus:$ADMIN_PASSWORD" http://localhost:8742/api/admin/secrets

# Remove a secret
curl -u "qlawkus:$ADMIN_PASSWORD" -X DELETE \
  "http://localhost:8742/api/admin/secrets?alias=quarkus.langchain4j.openai.%22primary%22.api-key"
----

Writing requires `qlawkus.secrets.keystore-password` to be set; without it the write is refused with `409 Conflict` rather than creating an unprotected store. A written secret takes effect on the next restart, since config sources are read once at startup, so the flow is: write the secrets, then start the agent.

== What to store

The alias is the configuration property the consumer reads, so move a secret out of your `.env` by storing it under the matching property name below. Each entry is otherwise sourced from the environment variable in the last column.

[cols="2,3,2",options="header"]
|===
|Secret |Keystore alias (config property) |Env equivalent

|LLM API key |`quarkus.langchain4j.openai."primary".api-key` |`LLM_API_KEY`
|Embedding API key |`qlawkus.embedding.api-key` |`LLM_EMBEDDING_API_KEY`
|Admin password (Argon2id hash) |`qlawkus.admin.password-hash` |`QLAWKUS_ADMIN_PASSWORD_HASH`
|Google OAuth client secret |`qlawkus.google.auth.client-secret` |`GOOGLE_CLIENT_SECRET`
|Google token-vault passphrase |`qlawkus.google.vault.encryption-passphrase` |`QLAWKUS_VAULT_PASSPHRASE`
|Discord bot token |`qlawkus.messaging.discord.bot-token` |`DISCORD_BOT_TOKEN`
|Telegram bot token |`qlawkus.messaging.telegram.bot-token` |`TELEGRAM_BOT_TOKEN`
|Transcription (Whisper) key |`qlawkus.messaging.transcription.api-key` |`WHISPER_API_KEY`
|TTS provider key |`qlawkus.messaging.tts.providers.<id>.api-key` |`TTS_<ID>_API_KEY`
|Datasource passwords |`quarkus.datasource.password`, `quarkus.datasource."google-auth".password`, `quarkus.datasource."brag".password` |`QUARKUS_DATASOURCE_*_PASSWORD`
|Secret handed to the shell (for example a GitHub token) |`qlawkus.shell.secret-env."<ENV_NAME>"`, such as `qlawkus.shell.secret-env."GH_TOKEN"` |`GH_TOKEN` (the bundled distribution wires it)
|===

The consumer needs no change in every case: the keystore (ordinal 350) outranks the `application.properties` value (250) that otherwise reads the environment variable. The LLM and embedding keys are routed through an internal kind factory that runs below the keystore and reads the stored value back, so they resolve from the keystore exactly like a direct property. The friendly `LLM_API_KEY` / `LLM_EMBEDDING_API_KEY` names also work as aliases if you prefer them over the native property names.

== What reaches the agent's shell

Everything above is invisible to a command the agent runs. `runCommand` and the interactive PTY sessions do not inherit the agent's process environment, because a single `env` would otherwise print the LLM key, the bot tokens and the database passwords, and that output flows to the model provider, working memory, the stored transcripts and the logs. A command starts with an empty environment that is built, in this order, from:

. The names in `qlawkus.shell.env-allowlist` that exist in the process environment. The default is `PATH`, `HOME`, `USER`, `LANG`, `LC_*` (a trailing `*` is a prefix match), `TZ`, `TERM`, `SHELL`, `JAVA_HOME` and `TMPDIR`.
. The workspace env file (`.qlawkus.env`), exactly as before.
. The secrets you deliberately pass through with `qlawkus.shell.secret-env` (below).

[source,properties]
----
qlawkus.shell.secret-env."GH_TOKEN"=${GH_TOKEN:}
qlawkus.shell.secret-env."NPM_TOKEN"=${NPM_TOKEN:}
----

The map is empty by default. The key is the environment variable name the command sees (`[A-Z_][A-Z0-9_]*`; anything else is skipped with a warning). The value resolves like any other config, so it can come from `.env` or from a keystore alias named after the property, and a blank value is skipped, so wiring an entry to a variable that is not set is harmless. These properties are on the secret list: the console config editor never renders or writes them.

The bundled `app/` distribution wires `GH_TOKEN` this way, so putting `GH_TOKEN` in `.env` is all it takes.

=== git credentials with nothing on disk

When `GH_TOKEN` is passed through, commands also get command-scope git configuration through the environment (`GIT_CONFIG_COUNT` and friends): an empty `credential.helper`, which clears every helper any gitconfig lists (`store`, `cache`), then `credential.https://github.com.helper` set to `!gh auth git-credential`, and `GIT_TERMINAL_PROMPT=0`. `git` and `gh` then authenticate to github.com from `GH_TOKEN` without `gh auth login` and without writing `~/.git-credentials`. Nothing is stored; the token exists only in the environment of the commands that need it.

=== Redaction

Every passed-through value of 8 characters or more, and any string shaped like a GitHub token (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), is replaced with `[redacted]` in the output returned to the model (stdout, stderr and PTY output read back) and in the `SHELL_CMD` audit log, command text included.

=== Which token to hand it

Create a fine-grained personal access token, ideally under a dedicated bot account, and keep it as small as it can be:

* Limit it to the repositories the agent works on, not all repositories.
* Give it an expiry, and rotate it.
* Grant the minimum permissions: Pull requests (read and write) and Contents (read). Add Contents (write) only if the agent must push.

=== The honest limit

A process that can use a credential can also read it. Redaction stops accidental leaks (a stray `env`, a verbose error, a pasted log); it does not stop a command that deliberately encodes the value, for example by printing it base64 or one character at a time. The defense is the combination: a minimal and expiring token, an environment that holds nothing else, and redaction.

== Authentication

The admin endpoints (`/api/admin/...`) are `@Authenticated`. The bundled distribution guards them with HTTP Basic over an *Argon2id* credential, verified database-free by `qlawkus-client`'s `Argon2AdminIdentityProvider`. Argon2id is a memory-hard, GPU- and ASIC-resistant password hash: the agent stores only the hash, never the password, and no datasource is involved.

Turn it on at build time (the bundled `app` already does):

[source,properties]
----
qlawkus.admin.argon2.enabled=true
# username defaults to 'qlawkus', role to 'admin' (qlawkus.admin.username / qlawkus.admin.role)
----

The credential is an ordinary secret, so store its Argon2id hash under the keystore alias `qlawkus.admin.password-hash` (or the environment variable `QLAWKUS_ADMIN_PASSWORD_HASH`). It is required when enabled: the app refuses to boot without it (fail-closed).

Generate the PHC hash with the reference `argon2` CLI:

[source,bash]
----
printf '%s' 'your-admin-password' \
  | argon2 "$(head -c 16 /dev/urandom | base64)" -id -t 2 -m 16 -p 1 -l 32 -e
# -> $argon2id$v=19$m=65536,t=2,p=1$<salt>$<hash>
----

Store the resulting `$argon2id$...` string under the alias above. The verifier reads the cost parameters and salt from the hash itself, so any standard Argon2id PHC string is accepted regardless of the parameters it was generated with.

=== Stronger or federated auth

Argon2id is the database-free baseline. For SSO, token-based, or centrally managed auth, add `quarkus-oidc` (or `quarkus-smallrye-jwt`) to your distribution: the endpoints are already `@Authenticated`, so the mechanism swaps with no Qlawkus code. That delegates password storage (Argon2id, PBKDF2) to your identity provider and verifies its RSA/ECC/EdDSA-signed tokens, which is the right home for federated credentials.

== Unlocking the keystore

Provide the keystore password through the environment and never commit it:

[source,bash]
----
export QLAWKUS_SECRETS_KEYSTORE_PASSWORD=...   # the storepass you set above
----

== Path and containers

The keystore lives at `qlawkus.secrets.keystore-path`, default `~/.qlawkus/secrets.p12`. In a container, mount a host directory to that path on a persistent volume so secrets survive restarts, and pass `QLAWKUS_SECRETS_KEYSTORE_PASSWORD` as an environment variable. The keystore file and its password stay out of the image. On POSIX filesystems the keystore is written owner-only (`0600`) and atomically, through a temporary file renamed over the old store, so a secret is never left world-readable or half-written. A keystore file mounted into the container on its own (rather than its directory) cannot be renamed over, so it is rewritten in place instead; mount the directory to keep the atomic write.

== Managed alternative: Vault

For a centrally managed store, put `quarkus-vault` on the classpath. It contributes a `CredentialsProvider` and resolves secrets the same way (as ordinary config), so consumers are unchanged. Use the keystore for a self-contained, offline deployment and Vault when secrets are managed centrally.
