= Voice Setup (STT / TTS)
:page-nav-group: Integrations
:page-nav-order: 350
:page-nav-title: Voice
:page-title: Voice Setup
:page-description: Enable Speech-to-Text transcription and Text-to-Speech replies on the messaging adapters

Qlawkus supports voice interactions on messaging platforms (Discord, Telegram): Speech-to-Text (STT) for transcribing voice messages, and Text-to-Speech (TTS) for spoken replies. Voice works through file attachments (the bot does not join voice channels).

The `WHISPER_*` and `TTS_*` names below are convenience environment aliases wired in the reference `app/` distribution (`app/src/main/resources/application.properties`); they map onto the `qlawkus.messaging.transcription.*` and `qlawkus.messaging.tts.*` config properties. See xref:config-reference.adoc[Configuration] for the full property list and their auto-derived `QLAWKUS_MESSAGING_*` env names.

[NOTE]
====
Defaults below are the ones the `app` itself carries. The Compose stacks (`./run.sh local|prod|native`) raise some of them, since that path ships a TTS service and points transcription at Groq:

[cols="2,1,1",options="header"]
!===
!Setting !`app` !Compose

!`TTS_ENABLED` !`false` !`true`
!`WHISPER_BASE_URL` !`https://api.openai.com` !`https://api.groq.com/openai`
!`WHISPER_MODEL` !`whisper-1` !`whisper-large-v3-turbo`
!`WHISPER_API_KEY` / `TTS_EN_API_KEY` !unset !fed from `GROQ_API_KEY`
!===

Set any of them in `.env` to override the Compose value.

== Speech-to-Text (STT)

Uses an OpenAI-compatible Whisper API (Groq or OpenAI). Transcription is disabled until an API key is set.

=== Environment Variables

[source,bash]
----
export WHISPER_API_KEY=your-groq-or-openai-key
export WHISPER_BASE_URL=https://api.groq.com/openai    # default: https://api.openai.com
export WHISPER_MODEL=whisper-large-v3-turbo             # default: whisper-1
----

*Providers:*

* *Groq* (recommended): Fast, free tier available. Base URL: `https://api.groq.com/openai`
* *OpenAI*: Standard Whisper API. Base URL: `https://api.openai.com`

=== Timeouts and retries

Calls to the transcription endpoint use a Quarkus REST Client named `whisper-api`: 15 seconds to connect and 120 seconds to read, adjustable with `quarkus.rest-client.whisper-api.connect-timeout` and `quarkus.rest-client.whisper-api.read-timeout` (milliseconds). A 429, a 5xx or a network failure is retried up to three times with backoff; any other status (401, 403, 404) fails at once. The API key is sent only in the `Authorization` header and never appears in logs or error messages.

=== How it works

1. User sends a voice message on Discord/Telegram
2. Audio is downloaded and sent to the Whisper API
3. Transcribed text is processed by the agent as a normal message
4. The agent response follows the normal flow (text or voice)

== Text-to-Speech (TTS)

Providers are keyed by the language the agent requests: `TTS_EN_*` is the provider used for English replies, `TTS_PT_*` for Portuguese, and so on. When the agent requests a language with no matching provider, `TTS_DEFAULT_LANGUAGE` is used.

=== Global Settings

[source,bash]
----
export TTS_ENABLED=true                          # default: false (voice requests fall back to text)
export TTS_DEFAULT_LANGUAGE=en                   # default: en
----

=== Provider Variables (per language)

[source,bash]
----
# English provider (kind defaults to openai)
export TTS_EN_BASE_URL=https://api.groq.com/openai
export TTS_EN_API_KEY=your-key
export TTS_EN_MODEL=canopylabs/orpheus-v1-english
export TTS_EN_VOICE=troy

# Portuguese provider (ElevenLabs)
export TTS_PT_KIND=elevenlabs
export TTS_PT_BASE_URL=https://api.elevenlabs.io
export TTS_PT_API_KEY=your-elevenlabs-key
export TTS_PT_MODEL=eleven_multilingual_v2
export TTS_PT_VOICE=your-voice-id
----

Each provider also accepts `kind`, `response-format` (default `mp3`), and `fallback` (another provider key to try on failure). Set them through the config property `qlawkus.messaging.tts.providers.<lang>.<field>` (env `QLAWKUS_MESSAGING_TTS_PROVIDERS_<LANG>_<FIELD>`).

=== Provider Kinds

[cols="1,2,3",options="header"]
|===
| Kind | Description | Base URL Example

| `openai` | OpenAI-compatible `/v1/audio/speech` | `https://api.openai.com`
| `elevenlabs` | ElevenLabs API | `https://api.elevenlabs.io`
|===

=== Timeouts and retries

The `openai` kind uses the REST Client `tts-openai-api` and the `elevenlabs` kind uses `tts-elevenlabs-api`, each with 15 seconds to connect and 120 seconds to read (`quarkus.rest-client.<name>.connect-timeout` and `read-timeout`, milliseconds). A 429, a 5xx or a network failure is retried up to three times with backoff before the provider counts as failed, and only then is its `fallback` tried. Other statuses fail at once.

=== How it works

A voice reply is requested in one of two ways, whichever happens first:

* *The orchestrator detects voice intent in the incoming text.* Before the agent runs, a message matching the voice-intent pattern ("manda audio", "reply by voice", "me responde por voz", English or Portuguese) pre-arms a voice reply in `TTS_DEFAULT_LANGUAGE`. This is a plain regex on the message, not a model decision, so it works even when the model ignores the tool.
* *The agent calls `respondWithVoice`.* Its system prompt tells it to do so when you ask for audio. The tool call carries the ISO 639-1 language code of the reply (e.g. `pt` or `en`), which overrides the language the detector picked.

From there:

1. The provider for the requested language (`TTS_PT_*`, `TTS_EN_*`, ...) synthesizes the audio; when no provider matches, `TTS_DEFAULT_LANGUAGE` is used
2. If the provider fails and defines a `fallback`, the fallback provider is tried
3. The audio is sent as a voice message on the platform (falling back to text if `TTS_ENABLED=false` or synthesis fails)

== Live voice sessions (console)

The console can hold a live, two-way voice conversation with the agent. It is optional: it ships in the `qlawkus-console-voice` extension (composition capability `console.voice`), and a distribution without it has no Voice page and no navigation entry for one. The page is at `/console/voice`, behind the same credentials as the rest of the console.

This is separate from the voice notes above. Voice notes transcribe one complete audio message from a chat channel. A live session streams your microphone from the browser and speaks the replies back as they are produced.

=== Using the page

1. Open *Voice* in the console navigation and press *Start*. The browser asks for microphone permission once.
2. Speak. In hands-free mode the page detects speech and sends the utterance when you stop; after the quiet time (`hangover`, 0.8 seconds by default) the transcript appears and the agent answers. In push-to-talk mode, hold *Space* or the *Hold to talk* button while you speak.
3. The reply is spoken sentence by sentence and typed into the conversation as it streams. Speak, press *Interrupt*, or press *Escape* to stop it.
4. *Mute* keeps the session open without sending audio. *Stop* ends the session: the microphone is released and the server closes it.

The centre of the page is a visual that needs no text to read:

* *Idle* and *muted* breathe quietly.
* *Listening* (warm orange) follows the microphone's frequency spectrum, so your voice shows as it arrives.
* *Hearing you* is brighter, and a ripple leaves the core on each peak.
* *Thinking* is a slow comet orbiting the core, a rhythm distinct from the others.
* *Speaking* (deep teal) sends waves outward, driven by the audio actually playing, and goes quiet when playback stops.
* *Interrupted* deflates and settles back to idle within about 400 milliseconds.

When the operating system asks for reduced motion, the visual becomes a static disc and ring. The ring's thickness and colour still show the state and the level.

Use headphones. Without them the agent's voice can reach the microphone and be taken for an interruption.

If the microphone cannot be used (permission denied, no device, a page that is not served over HTTPS or localhost, or a browser without AudioWorklet), the page says why and keeps the session open for the text box below the conversation.

Turns share the chat's conversation. The live session goes through the same agent as `/api/chat`, so what you say aloud is in the same history as the chat page, and the shared conversation applies when `qlawkus.agent.shared-context` is on.

=== Languages

The *Language* selector offers *Auto (detect)* and every language a speech provider is configured for (the `TTS_<LANG>_*` providers, see the text-to-speech section). The detected language is shown under the status line, and the language each reply is spoken in is shown next to it.

* *Auto* is the default (`qlawkus.console.voice.language=auto`). The speech recognizer reports its detected language with the transcript. Before generating a reply, the decision model selects the reply language once for the whole turn, considering the utterance, recognition result and stable session language. It can also follow a request to answer in another language. The selected code guides both the agent's spoken response and every TTS segment; there is no model call per sentence.
* The displayed session language summarizes recognizer results: the majority of the last five, with at least two votes. It is informational; the shared resolver decides each reply from the current request and recent reply language.
* An explicit code, such as `pt`, forces that language and skips the decision call. It is sent to the recognizer as a hint and used for every reply. A code with no speech provider is refused.

Text and voice use the same core `ReplyLanguageResolver`. In the reference app,
`qlawkus.reply-language.enabled=true` asks the already registered chat model to classify the reply
language once per turn. This is the same registration used by fact extraction: with the NVIDIA profile,
NVIDIA is tried first, then its configured secondary tier, and Ollama remains the last resort.
No additional model provider, API key or decision endpoint is required. Other distributions default to
`false` and keep the shared system-prompt policy without an extra model call.

The classification receives at most 2000 characters of the current request and language codes only.
It has no agent tools, conversation memory or RAG. A separate four-second fault-tolerance deadline,
bulkhead and circuit breaker protect the operation, and the `decision` workload isolates provider
breakers from interactive replies and background extraction. An invalid result or provider failure
leaves the shared language policy in charge; a current speech-recognition code can still guide the
first short Portuguese utterance. Unknown results never force an older language onto a new request.

With language classification enabled and a language selected, the live voice session also checks the
finished reply before showing it or speaking it. The model receives only the draft and target language.
It keeps an already correct draft or translates its prose. This check never repeats the agent's tools.
Tool progress still arrives as it happens, while text and audio wait for the check. If the check fails
or the draft exceeds 16,384 characters, the console shows a notice and presents the original draft.

The reply language is not limited to the configured speech providers. If there is no provider for the
selected language, the TTS router uses its configured provider fallback while retaining the reply text
in the selected language. An explicit selector choice is still offered only for configured providers.

The conversation panel has its own bounded scrolling area on desktop and phone screens. New messages follow the bottom while you are reading the latest reply. Scrolling up to review older messages pauses that automatic movement; scrolling back to the bottom resumes it.

=== Typed messages

The text box sends a message as a turn without speech recognition. Its length is capped by `max-text-chars`. It goes through the same agent turn, interruption and speech as a spoken utterance.

=== Buffered speech and transcription

The speech adapters in the reference build are buffered, and the page says so:

* *Speech-to-text* waits for the whole utterance, then sends it to the Whisper-compatible endpoint configured under `WHISPER_*`. The live session asks for `verbose_json`, so the detected language comes back with the text, and an explicit language is sent as the `language` field. Voice notes keep the plain request. A self-hosted Whisper-compatible server works by pointing `WHISPER_BASE_URL` at it.
* *Text-to-speech* synthesizes each reply sentence in full through the messaging providers (`TTS_<LANG>_*`), then plays it. Each sentence waits for its own synthesis before it plays, so expect a pause before each one. No real-time latency is promised.

A streaming adapter can replace either one. The speech adapter is the `VoiceSpeech` interface, which also lists the languages it can speak; a streaming implementation reports `buffered` as false and the page labels the mode accordingly.

=== Spoken replies and screen text

Live voice turns add presentation instructions to the system prompt: answer in conversational sentences,
in the selected language, without Markdown, lists, code blocks, raw URLs or emoji. The owner's message
is stored exactly as received. This presentation setting belongs to that turn and does not carry over
to ordinary text chat. All channels also ask the agent to follow the language of the current owner's
request, unless the owner requests another language; quoted material and retrieved documents do not
choose the reply language.

The voice extension renders CommonMark into the same plain text for the screen transcript and speech.
Emphasis and list markers disappear, links keep their labels, and fenced or indented code, tables,
HTML blocks, images and emoji are omitted. Headings and list items receive sentence punctuation so
they have a pause when spoken. The original reply is stored in the shared chat conversation.

The renderer waits for complete blocks or the end of the turn. Both the transcript and audio can
therefore wait for a single long paragraph to finish. The renderer accepts up to 65536 source
characters per turn and reports `speech-text-truncated` when it reaches that limit. The existing
sentence and speech queue limits still apply afterwards.

=== How a turn works

* The browser captures 16-bit mono PCM at the audio context's sample rate, through an AudioWorklet, and sends it as binary frames between a `start` and an `utterance-end` message.
* The server wraps the utterance as WAV and transcribes it. Each finished utterance is one turn, numbered in order. A typed message is a turn too, without transcription.
* The agent answers the transcript through the same streamed turn the chat uses. The reply is cut into sentences, and each sentence is synthesized in its language and sent in order.
* Every event carries its turn number. The page ignores audio and text for a turn older than the newest interrupt it has seen.

Protocol, for an integrator writing a different client:

[cols="1,3",options="header"]
|===
| Direction | Messages

| Browser to server
| JSON `{"type":"start","sampleRate":48000}`, binary PCM16 frames, JSON `{"type":"utterance-end"}`, `{"type":"interrupt"}`, `{"type":"language","language":"auto"}` (or an ISO 639-1 code), `{"type":"text","text":"..."}`, `{"type":"stop"}`

| Server to browser
| JSON `ready` (with `language`, `languages`, `defaultLanguage`, `maxTextChars`), `listening`, `language` (language), `transcript` (turn, text, language, sessionLanguage, typed), `text` (turn, chunk), `tool` (turn, phase, name), `audio` (turn, segment, language, mimeType, base64 data), `turn-done`, `interrupted` (turn), `notice` and `error` (code), `closed` (reason)
|===

The socket is `/console/voice/ws`. The browser must send the console's credentials and an `Origin` header matching the page.

=== Interruption

Speaking again, pressing *Interrupt* or *Escape*, or sending `interrupt`, supersedes the active turn:

* The agent's streamed turn is cancelled. Verified with the streaming path: when the cancel lands while a tool is running, no further model round starts and no further tool runs.
* Sentences still waiting for speech are skipped when they reach the front of the queue, and audio the server has not yet sent is dropped.
* The server reports `interrupted` for the superseded turn, and the page stops playback immediately.

Not aborted: a model response already streaming over HTTP is not verified to be closed, and its remaining chunks are discarded rather than shown. A speech synthesis already running cannot be stopped mid-call, because the speech adapters are blocking; its result is thrown away. A cancel that arrives after the agent has already dispatched its next round is not covered by that guarantee.

Completed tool calls are never run again: a superseding turn starts a new message and does not replay the earlier turn's tools.

=== Budgets

The server enforces these limits, all under `qlawkus.console.voice.*` and visible on the config page:

[cols="2,1,3",options="header"]
|===
| Property | Default | Effect

| `max-session-duration` | `PT15M` | The session closes when it elapses.
| `max-utterance-duration` | `PT30S` | Longer audio is discarded; the owner is told to speak again.
| `max-utterance-bytes` | `4194304` | The byte cap on one utterance; the smaller of this and the duration cap applies.
| `max-frame-bytes` | `65536` | A larger binary frame is refused.
| `max-text-chars` | `2000` | A longer typed message is refused.
| `max-queued-segments` | `8` | Sentences beyond this are not spoken and the owner gets a `speech-queue-full` notice.
| `max-sessions-per-owner` | `1` | A second session is refused until the first closes.
| `language` | `auto` | `auto` detects the language; an ISO 639-1 code forces it for recognition and speech.
| `hangover` | `PT0.8S` | Quiet time that ends an utterance in the browser.
| `speech-threshold` | `0.02` | Level above which a frame counts as speech. The browser calibrates below this value to the room and never goes above it.
| `allowed-origins` | unset | Extra origins allowed to open a session.
|===

=== Privacy and security

* Audio is never stored and never logged. The server keeps the utterance only until it is transcribed.
* Logs carry identifiers, counts, durations and language codes. Transcripts, typed messages and reply text are not written to the log.
* The socket requires the console's credentials. The upgrade is refused unless its `Origin` is the console's own origin or one listed in `allowed-origins`, so another site cannot open the owner's microphone with cached credentials.
* A session belongs to the authenticated owner. The default allows one open session per owner; closing the page, losing the connection or stopping releases the slot.
* Model and user text reach the page only as text content, never as HTML.

=== Running the browser check

The Maven build does not run the browser. `integration-tests/console-voice/browser/voice-check.mjs` drives Chromium with fake media devices against a running instance. It writes its own fake microphone clip (a tone, then silence), and it checks a full utterance: the detected Portuguese language, the Portuguese reply, an interruption with the *Interrupt* button, a typed message, and *Stop*. When `SHOTS_DIR` is set it also saves a screenshot of each state at desktop and phone width, in light and dark. The script exits 0 with a skip message when Playwright is not installed.

The instance needs speech-to-text, chat and text-to-speech endpoints. `integration-tests/console-voice/browser/fake-providers.mjs` serves all three, plus the embeddings the agent calls, on port 19999 (`FAKE_PORT` changes it). Start the fakes, then the packaged integration app with the test profile, pointed at them:

[source,bash]
----
node integration-tests/console-voice/browser/fake-providers.mjs &

mvn -o package -DskipTests -pl integration-tests/console-voice

java -Dquarkus.profile=test -Dquarkus.http.port=18080 \
  -Dquarkus.wiremock.devservices.enabled=false -Dquarkus.wiremock.devservices.port=19999 \
  -Dquarkus.langchain4j.devservices.enabled=false \
  -Dqlawkus.messaging.transcription.api-key=fake-key \
  -Dqlawkus.messaging.transcription.base-url=http://localhost:19999 \
  -Dqlawkus.messaging.tts.enabled=true \
  -Dqlawkus.messaging.tts.providers.en.base-url=http://localhost:19999 \
  -Dqlawkus.messaging.tts.providers.pt.base-url=http://localhost:19999 \
  -Dqlawkus.messaging.tts.providers.es.base-url=http://localhost:19999 \
  -Dqlawkus.console.voice.max-utterance-bytes=4194304 \
  -Dqlawkus.console.voice.max-frame-bytes=65536 \
  -jar integration-tests/console-voice/target/quarkus-app/quarkus-run.jar

BASE_URL=http://localhost:18080 QLAWKUS_PASSWORD=qlawkus-test SHOTS_DIR=/tmp/voice-shots \
  mise exec npm:playwright@<version> -- node integration-tests/console-voice/browser/voice-check.mjs
----

The test profile sets small frame and utterance budgets, so the command raises them to what a real microphone sends. A real Whisper or TTS endpoint can replace the fakes by pointing the same properties at it.

== Testing Voice

1. Configure STT and at least one TTS provider, and set `TTS_ENABLED=true`
2. Send a voice message to the bot on Discord/Telegram
3. The bot should transcribe, process, and reply (with voice when either the detector or the tool requests it)

== Troubleshooting

[cols="2,3",options="header"]
|===
| Issue | Solution

| Transcription does nothing | Set `WHISPER_API_KEY` (a blank key disables STT)
| Voice request answered as text | Set `TTS_ENABLED=true` and configure the provider for that language
| TTS provider not configured | Set `TTS_<LANG>_*` for the requested language, or point it at `TTS_DEFAULT_LANGUAGE`
| Wrong language voice | The agent must pass the right language code to `respondWithVoice`. In the live session, leave the Language selector on Auto or choose the language explicitly
| Audio format errors | Set the provider's `response-format` to `mp3`
|===

See xref:config-reference.adoc[Configuration] for all voice-related environment variables.
