# Qlawkus - Agent Instructions

## Dev Mode Start

```bash
mvn install -pl client/deployment -am -DskipTests # builds both runtime and deployment first
mvn -pl app -am quarkus:dev              # from the root: app/ is the only runnable module, and
                                         # capability resolution needs the reactor (see below)
```

Changing `client/` requires re-running `mvn install -pl client/deployment -am` then restarting dev mode. Selecting only `-pl client` installs the aggregator POM, not the extension jars. Hot reload does NOT apply to extension code.

## Worktree and Branch Cleanup

After merging a PR, remove its clean feature worktree and both local and remote feature branches. Verify the merged PR and its head before deleting: rebase merges rewrite commit IDs, so use the merged PR head or patch equivalence when ancestry alone does not establish the merge. A branch already deleted remotely needs no further action.

Preserve active worktrees, open PR branches, uncommitted changes, and ignored files containing configuration or user data. Only clear a worktree lock after confirming its owning process has ended. Generated build outputs may be removed with an otherwise clean worktree.

## Containerized Run

`./run.sh <local|prod|native> [up|build|down|logs|restart|ps|status] [--replace|--recreate|--no-wait]` wraps Docker Compose (`./run.sh --help` for the full list). Unlike dev mode, this needs only Docker: the `app/src/main/docker/Dockerfile.{jvm,native}-build` images are **multi-stage** and compile the whole reactor in-container (build stage = the `ubi10/openjdk-25` builder, which ships Maven; runtime = `ubi10/openjdk-25-runtime`), so there is no host `mvn install` step and no stale-jar trap. Each build Dockerfile has its own `Dockerfile.*-build.dockerignore` so the standard Quarkus `.dockerignore` (for the COPY-target `Dockerfile.jvm`/`.native-micro`) stays intact. The build runs the **full** reactor (`mvn install`), not `-pl app -am`: a fresh local repo needs every `*-deployment` module built so the `extension-descriptor` check on each extension resolves. `local` -> `docker-compose.local.yml`; `prod`/`native` -> `docker-compose.yml` (native via its `native` profile).

**run.sh safety checks.** `up` runs two checks before it builds anything, because a native build is 70 minutes and the failure used to come at the end (`Bind for 0.0.0.0:8742 failed: port is already allocated`). Host ports 8742, 5432 and 3000 must be free, or held by the service of this same compose project that the mode would reuse; the jvm and native app services share 8742, so the other mode's container is reported with the exact `docker stop`, and `--replace` stops only that one (never a container of another compose project). The second check refuses to start when the old PostgreSQL 17 volume `qlawkus_pgdata` holds data and `qlawkus_postgres` does not exist, since booting would create an empty database and the agent would lose its memory: `./run.sh migrate-postgres` (`scripts/migrate-postgres.sh`, dump and restore with row counts compared, old volume only read and kept as the rollback) moves it, and `docker volume create qlawkus_postgres` is the explicit opt-out. After `up` the script waits for `/q/health/ready` (`QLAWKUS_READY_TIMEOUT`, default 300 s), prints service, state and URL, and exits non-zero with the last 40 app log lines on failure. It also reads `/etc/resolv.conf` of every container (through `docker cp`, the native image has no shell) and flags one on a user-defined network whose resolver is not 127.0.0.11, the leftover of a failed `up` that cannot resolve `postgres`; `--recreate` (alias `restart`) force-recreates only the app service. `scripts/test-run-sh.sh` checks all of this against a fake `docker` on the PATH, starting nothing.

**PostgreSQL 19 layout.** The `postgres` service is `pgvector/pgvector:0.8.7-pg19` with volume `qlawkus_postgres` mounted at `/var/lib/postgresql` (18+ keeps the cluster in `/var/lib/postgresql/<major>/docker`, so a later major can be upgraded in place with `pg_upgrade`). A volume written by 17 or older cannot be read by 19. Rollback is the old volume plus the previous compose files.

**Image pins.** Every image in the compose files and the build Dockerfiles is an exact tag (searxng also keeps its digest), so a Dependabot bump is a reviewed change; `.github/dependabot.yml` covers the compose files, `docker/lgtm`, `docker/searxng` and `app/src/main/docker`. Moving `grafana/otel-lgtm` means re-diffing `docker/lgtm/prometheus.yaml` against the image's own (`docker run --rm --entrypoint cat grafana/otel-lgtm:<tag> /otel-lgtm/prometheus.yaml`); at 0.41.1 the image's file matched `docker/lgtm/prometheus.yaml` above `scrape_configs`, so only the tag moved.

**Image variants.** `Dockerfile.jvm-build` takes the build arg `QLAWKUS_IMAGE_VARIANT`, which picks its final stage: `base` (default) or `devtools`, the same runtime plus `git-core` (UBI repos) and `gh` (GitHub's official RPM repo, which serves only its latest release, so `gh` is not pinned: a pin would break the build on the next release). Both compose files pass it through, so `QLAWKUS_IMAGE_VARIANT=devtools ./run.sh prod` builds it. It is a distribution choice, kept out of the base so the base stays lean (measured with `docker image ls`: base 791 MB on disk / 242 MB content, devtools 966 MB / 286 MB, so +175 MB / +44 MB). The `devtools` variant is defined for the JVM Dockerfile, and `./run.sh native` refuses the variant. The native Dockerfiles use UBI minimal with `freetype` and `fontconfig` for headless PDF processing and package the shared libraries emitted beside the native runner. The native image runs as uid 185 with `HOME=/home/default`, like the JVM image, because both services mount the same `workspace` volume at `/home/default`: another uid cannot write what the JVM image created, and `~/.qlawkus` would resolve outside the volume. `scripts/check-image-runtime-user.sh` pins that in the PR build. The code-review tools (`CodeReviewTool`, `ReviewResponseTool`) are what need it, and they check first: `ShellTool.missingExecutable` looks the executable up on the PATH the command would run with (the workspace env file can override the process PATH) and returns a result naming the binary, with the devtools hint for `git`/`gh`, instead of letting `sh` fail with a bare `not found`. `scripts/check-devtools-image.sh <image>` verifies an image actually carries both.

Every stack also runs `lgtm` (`grafana/otel-lgtm`: collector, Prometheus, Tempo, Loki, Grafana on :3000), defined once in `docker/lgtm/compose.yml` and pulled into each compose file with `extends`. The agent services turn the OTel SDK on and export traces and logs to `lgtm:4317`; Prometheus scrapes `/q/metrics` on the agent's **management port 9000**, never published, through the network alias `agent` that the JVM and native services share. Grafana refuses to start without `GRAFANA_ADMIN_PASSWORD` (the image otherwise makes anonymous visitors Admin). `docker/lgtm/prometheus.yaml` is the image's own file plus the scrape job, so a Dependabot bump of the tag means re-copying it. The agent does not depend on `lgtm`: with it down, only telemetry is lost.

## Architecture

Multi-module Maven monorepo with a Quarkus extension pattern (`client/deployment` + `client/runtime`):

- **`composition-model/`** - Thin, **Quarkus-free** module (plain records + Jackson YAML) holding the `agent.yml` composition manifest model: `CompositionManifest`/`BuildTime`/`Posture`, the single `CompositionManifestParser`, the policy+exceptions `isEnabled` logic, and the path conventions (`CompositionPaths`). Shared by the (future) pom generator that reads `build-time` before the build and the running app that reads `runtime` each boot, so the schema and policy never drift (same single-source-of-truth discipline as `KeystoreSecrets`). The `qlawkus.composition.*` location config (`CompositionConfig`, BUILD_TIME) lives in `client`. At runtime `client` also exposes an authenticated composition control plane (`rest.CompositionAdminResource` + `compose.CompositionAdminService`): `POST /api/admin/composition/manifest` validates a new `agent.yml` (via the shared `CompositionManifestParser`) and stages it under `qlawkus.agent.state.root`; `GET /api/admin/composition` returns the active (baked, read from the classpath `agent.yml`) + staged pair; `DELETE .../manifest` discards it. It only records intent (validate + write), never builds - the seam to an external builder is HTTP, not a shared volume, so even a leaked admin credential can at most stage a validated manifest. The same admin surface generalizes to arbitrary config values via `config.metadata.ConfigMetadataIndex` (reads the `quarkus-config-doc` metadata bundled in every extension jar - the same source that generates `config-reference.adoc` - so the property list is never hand-maintained): `RUN_TIME` properties go through `config.RuntimeToggleWriter` + `PUT`/`DELETE /api/admin/runtime-toggles` (writes straight into the `runtime:` override file, applies on restart); `BUILD_TIME`/`BUILD_AND_RUN_TIME_FIXED` properties go through `compose.ConfigOverridesAdminService` + `PUT`/`POST`/`DELETE /api/admin/config-overrides`, staging a `.properties` document that is fetched and promoted into `config-overrides.properties` alongside `agent.yml` by the same redeploy loop - parallel files, never merged, so the pom generator never has to reconcile `application.properties` lines. The same surface also records what the external redeploy loop reports: `POST /api/admin/composition/redeploys` (body `dto.RedeployReport`, validated at the API layer: start instant, `success`|`failure`, `failedPhase` required on a failure, per-phase milliseconds for the closed set `fetch|promote|build|restart|verify`, durations capped at a day, an optional message capped at 200 chars with no control characters) stores it through `compose.RedeployHistoryService`, and `GET .../redeploys` reads it back. It is data only: no field is ever interpreted as an instruction, so a leaked admin credential can at most write a bounded history entry. `redeploy.sh` times each phase and reports once when the run ends (an EXIT trap names the failing phase), never altering its own exit status if no instance answers. The history (last 20 runs, plus running totals and the last success, which a failure streak cannot evict) is written atomically to `redeploys.json` under `qlawkus.agent.state.root`; a corrupt file is treated as empty rather than stopping boot. The console schedule page shows the last run read-only. `secrets.SecretPropertyCatalog` excludes known-secret property names from the index entirely, so a secret is never rendered or writable through either endpoint.
- **`composition-maven-plugin/`** - Maven plugin (`qlawkus-maven-plugin`, goal prefix `qlawkus`) that turns the manifest into the pom **before** the build (`mvn qlawkus:generate`). Quarkus resolves dependencies before augmentation and Maven does no tree-shaking, so a manifest can only decide the dependencies from a generator that runs ahead of the build, not a `@BuildStep`. `GenerateMojo` reads `agent.yml` (via `composition-model`), resolves the selected capabilities against a `CapabilityCatalog`, and uses the Maven Model API to decide which top-level dependency entries to add or remove and the XML parser's source offsets to edit them in place. Comments, formatting, and other sections survive composition. Idempotent. Added deps carry no version (BOM-managed, like `quarkus extension add`). **Quarkus-free** at runtime; needs an ASM>=9.8 override for the plugin descriptor on Java 25. The catalog (#74) is decentralized: each extension module self-describes its capability name in its own `quarkus-extension.yaml` under `metadata.qlawkus.capability`, and the default `ReactorCatalog` reads that key from every reactor module (`${reactorProjects}`), reading the source descriptor template so it works before any module is built. `CapabilityCatalog` stays an interface so a published-artifact strategy (external consumer, outside the monorepo) can be added without touching the generator. Capability names ship namespaced where natural (`messaging.discord`, `cognition.pgvector`) and several modules may share one (`google-workspace` = the 6 google modules); `qlawkus-client` is the always-present skeleton and declares none. Each run logs the **resolved capability set** (selected/excluded) so the policy-and-exceptions shorthand never hides the full state, and an `except` name no module declares **fails the build** (opt-out `-Dqlawkus.composition.fail-on-unknown-capability=false`) - the anti-typo guard, since an unannounced name otherwise silently resolves to nothing. When `qlawkus.composition.fail-on-pom-drift` is true (the `env.CI` profile on the reactor root), a pom that disagrees with the manifest fails instead of being rewritten, listing dependencies it would add or remove (#463); `ReferenceAppCompositionTest` pins the reference `app` pair in unit tests. The goal's default phase is `generate-sources`, wired as an `<execution>` in the app pom, so every Maven build reconciles the pom from `agent.yml` before Quarkus resolves dependencies. **It does not re-run inside a live `quarkus:dev` session**: dev mode notices the changed `agent.yml` and logs "Files changed but restart not needed" without re-entering `generate-sources`, so a manifest edit applies on the *next* build - restart dev mode, or run `mvn qlawkus:generate`. Capability resolution reads `${reactorProjects}`, so the generator needs the reactor visible (`mvn -pl app -am quarkus:dev` from the root, not a lone `cd app && mvn quarkus:dev`). End-to-end proof is the `maven-invoker` IT under `src/it/` (a real two-capability reactor + agent app), gated by the `composition-invoker-it` profile (off under `-Pnative`, honors `skipITs`); its post-build hooks are **BeanShell** (`.bsh`), not Groovy, because Groovy's shaded ASM cannot read Java 25 class files.
- **`client/`** - Quarkus extension (core agent, cognition, REST, tools). Not a runnable app. **Database-free**: depends on no datasource/JDBC/Flyway/pgvector - the markdown stores are its `@DefaultBean` backend.
- **`attachments/`** - Optional Quarkus extension (`deployment/` + `runtime/`, capability `attachments`). The core `AttachmentChat` SPI accepts request-scoped `ChatAttachment` handles. The console uploads through multipart `/api/chat` and consumes the existing SSE format. Discord and Telegram resolve their own provider media only after the messaging allowlist accepts the turn. Telegram document and photo webhook updates also require its Bot API shared-secret header before dispatch. The attachment extension bounds file size, PDF extraction and image type checks before sending labelled text and LangChain4j `ImageContent` to the model. Attachment analysis calls the model outside the persistent conversation and tool loop. Operators select a tier for LangChain4j `ImageContent` via `qlawkus.attachments.image-model` and a tier for `PdfFileContent` via `qlawkus.attachments.pdf-model`. The PDF tier defaults to local text extraction. The local parser uses the Quarkiverse PDFBox extension for resources and native AWT support, with per-file limits on the extraction itself. See `site/content/messaging.adoc`.
- **`cognition-decision/`** - Optional capability `decision.nvidia`. When enabled at runtime it supplies a `TurnGate` using an NVIDIA NIM adapter for LangChain4j's yes/no `DecisionModel`. The gate sends user and assistant text, applies per-question thresholds, and reuses the core fail-open policy. It has its own timeout, bulkhead and circuit breaker. See `site/content/operations.adoc`.
- **`cognition-pgvector/`** - Optional Quarkus extension (`deployment/` + `runtime/`) holding the entire Postgres/pgvector backend for the cognition stores (the `store.pg` package, the Flyway migrations, and the datasource/pgvector config as `META-INF/microprofile-config.properties`). Present in `app/`; absent in a markdown-only distribution. `requires` the `dev.omatheusmesmo.qlawkus.agent` capability.
- **`console/`** - Optional Quarkus extension (`deployment/` + `runtime/`, capability `console`) serving a server-rendered admin UI at `/console` (Qute + HTMX, no Node, `@Authenticated` reusing the app's Basic+Argon2id mechanism). Read views inject the `client` SPIs directly; every mutating action is driven from the page by HTMX against the existing `/api/admin/*` endpoints, never re-implemented in a console resource. The shared layout (`templates/console/base.html`) groups the navigation into Agent, Knowledge and System (`data-nav-group`; each group always holds a core page, so none is ever empty, and optional entries stay gated by `ConsoleFeature` beans) with `aria-current` on the active page and a skip link; below 900px the sidebar is a top bar and the nav a drawer driven by `console.js` (focus trap, Escape, backdrop; `ConsoleShellTest` pins the structure). Theme is a `system|light|dark` radiogroup in the layout nav (`data-theme-choice`, driven by `console.js`, stored in `localStorage` key `qlawkus-theme`): the synchronous (non-deferred) `theme.js` in the head sets `data-theme` before the stylesheet loads (never an inline script: the console serves none, and `ChatConsoleTest` pins that), the tokens already carry the `[data-theme]` selectors, and one `:is(a, button, input, select, textarea, summary, [tabindex]):focus-visible` rule is the only focus ring. `ThemeToggleTest` pins the markup and `browser/a11y-check.mjs` runs axe-core (`AXE_PATH` to `axe.min.js`) in both themes, so a new page or colour that drops under 4.5:1 fails it. Action feedback is shared in `console.js` and the `base.html` layout: the `#qk-toasts` polite live region with `window.qlawkusToast(text, "ok"|"error")` (the one announced channel, the inline result nodes carry no live role), an `htmx:beforeRequest`/`afterRequest` pair that disables the used control and marks it `.is-busy` + `aria-busy`, and a server error body `{error, field}` that sets `aria-invalid`, `aria-describedby` and focus on the named field (or the only text field of the form); scripts that do not use HTMX call `qlawkusToast` themselves. `FeedbackComponentsTest` pins the parts and `browser/feedback-check.mjs` the behavior. Forms use one component set in `console/app.css` (`.field`/`.field-label`/`.field-hint`, the controls `.input`/`.select`/`.textarea`, `.field-check`, `.field-group`, `.actions`) and buttons use `.btn` with `btn-primary|secondary|danger` (+ `btn-sm`), including the ones `mcp.js` builds; per-page field rules are not allowed, and `FormComponentsTest` fails on a control or button without the shared classes and on a surviving per-page rule, while `integration-tests/console/browser/forms-check.mjs` checks for horizontal overflow down to 320px. Destructive actions never use `hx-confirm` or the native `confirm`: the layout holds one `<dialog id="qk-confirm">` driven by `confirm.js`, which holds an HTMX request on `htmx:confirm` until a control's `data-confirm-action`/`data-confirm-target`/`data-confirm` are agreed to, and offers `window.qlawkusConfirm(...)` (a promise) to scripts that build their own controls; `ConfirmationDialogTest` fails on any `hx-confirm` or on a `hx-delete` missing the three attributes, and `integration-tests/console/browser/confirm-check.mjs` exercises focus, Escape, backdrop and confirm in a browser. Pages: the onboarding wizard (first-run setup), management (`/console/memory`, `/console/skills`, `/console/cognition`; the skills page links the install panel of the optional `console-skill-hub` extension only when that extension is present), the full configuration editor (`/console/config`, see the `composition-model/` bullet above), whose search, changed and phase filters, collapsible sections and section index are the client-side `console/config.js` over rows the server already rendered (the page marks each row `data-changed`, `data-owner` and `data-phase`, and `ConfigSourceLabel.isOwnerSource` decides which sections start open, so the distribution's own defaults never open one; a saved override counts at once through `RuntimeToggleWriter` and the staged document, since the running value only moves after a restart; the state lives in the URL hash; `integration-tests/console/browser/config-check.mjs` is the browser check), and the schedule page (`/console/schedule`, listing agent-created tasks from `DynamicTaskScheduler` with status, destination and next run, and cancelling through `DELETE /api/admin/scheduled-tasks/{id}`; also listing the 5 background jobs - memory review/curation, episodic consolidation, skill curation/lifecycle - with cron/last-run/next-run read from the live `io.quarkus.scheduler.Scheduler`, so they always match what is actually registered; each job carries an explicit `@Scheduled(identity = ...)` for this lookup. The job registry itself - label, cron property, trigger endpoint - is static in `ScheduleConsoleResource` by necessity: no framework metadata links a job to the config property holding its cron, so it cannot be derived from `ConfigMetadataIndex`). Cron is `RUN_TIME` like every other scheduler property, so editing it reuses the same `/api/admin/runtime-toggles` endpoint the config editor uses (applies on next restart, not live - `@Scheduled` resolves its cron property expression once at boot); triggering a job now hits its existing `/api/admin/*` endpoint, including a new `POST /api/admin/memory/consolidate` added alongside `/review` and `/curate` so all 5 jobs are triggerable uniformly. The overview's Observability card is the only outbound reference: `ConsoleConfig` (`qlawkus.console.grafana-url`, `Optional<String>`, `RUN_TIME`) feeds `ObservabilityLinks`, which turns a plain http(s) Grafana base URL into the dashboard link (uid pinned to `examples/observability/grafana/qlawkus-agent.json` by a test) plus Explore on the `prometheus`/`tempo`/`loki` datasource uids `grafana/otel-lgtm` provisions, and yields nothing for an unset or non-http(s) value. The overview's cards (`OverviewConsoleResource`, one `/console/overview/*` fragment per card, each polled by HTMX only while the tab is visible) read what the agent already exposes and add no admin endpoint: Health lists every `@Readiness` check through `ReadinessSource` (the only class touching the health API, registered by `ConsoleProcessor` only when `Capability.SMALLRYE_HEALTH` is present, so health stays `<optional>`; `ConsoleResource` hides the card when the bean is not resolvable); `ReadinessViews` reads only an `error`/`*Error` entry, the `degraded` store list and the pending-migration count from a check's data, never the rest, bounds the reason through `FailureSummary`/`SecretRedactor`, and turns a throwing check into its own `DOWN` row; Upcoming merges the `ScheduleConsoleResource.JOBS` registry with active `DynamicTaskScheduler` tasks (`UpcomingRuns` keeps the earliest three); Last redeploy reuses `RedeployRunView`; Memory reads journal count, skill count and fact sources from the store SPIs; Model renders `client`'s `ModelChainStatus` (each tier's breaker through the read-only `CircuitBreakerMaintenance.currentState`, the permanent-failure streaks from `PermanentFailures`, and the interactive tier that answered last from `ServedTier`) through `ModelChainView`. Every card goes through one wrapper that turns a failed read into a 200 `data-card-error` fragment with a bounded, redacted reason, because HTMX keeps the last good content when a poll fails. The chat page (`/console/chat`, `ChatConsoleResource` + one vanilla `chat.js`, no library) does not re-implement chat either: the browser POSTs to the existing `/api/chat` SSE endpoint with `fetch` + a stream reader (HTMX's SSE extension cannot POST) and so shares whatever conversation that endpoint resolves (the shared one while `qlawkus.agent.shared-context` is on). Model text is only ever inserted with `textContent`, never `innerHTML`; the minimal markdown is built node by node. `/api/chat` keeps its unnamed text `data:` events and adds named `tool-start` / `tool-end` / `done` events produced by `agent.AgentStream` (built on the AI service's `Multi<ChatEvent>`, so it sees tools declared on `@RegisterAiService` as well as `@QlawTool` ones, never their results); each tool event is also a `ToolActivityEvent` CDI event with the conversation id for channels that only observe. The detail level is the shared `agent.ToolProgress` vocabulary (`off|status|preview|verbose`), sent by the page from `qlawkus.console.chat.tool-progress` (`ConsoleConfig`, `RUN_TIME`) so the endpoint itself omits what a mode hides. `console/deployment`'s `ConsoleProcessor` registers the runtime's `@Path` resources via `AdditionalBeanBuildItem` since the jar is not an implicit CDI bean archive on its own. It also asks Qute for a value resolver for every record in the console package (`TemplateDataBuildItem`): a template reads a record by reflection in a JVM but a native image has none, so an unresolved view answers 500 there; `ConsoleTemplateTypesTest` pins it. The visual tokens (light and dark values, between the `qlawkus-tokens` markers) are one block copied byte for byte into `console/.../console/app.css` and `site/web/app.css`, with Manrope self-hosted under each `fonts/` directory (no CDN, the console may run air-gapped); `DesignTokensTest` fails on drift, on a text pair under 4.5:1 in either theme, and on any remote font or import.
- **Owner approvals (`client/runtime/.../approval`)** - Opt-in gate for the `@QlawTool` tools named in `qlawkus.approval.tools` (empty by default, so nothing changes until one is named). `ApprovalToolExecutor` sits in `QlawToolProvider`'s chain under the context bridge and under the meters: a gated call is recorded as an `ApprovalRequest` (canonical arguments, SHA-256 binding over tool name and arguments, redacted preview, requester and conversation) and the model is told it has NOT run. `ApprovalService` owns the state machine: every transition is a compare-and-set through the `ApprovalStore` SPI, an approval re-checks the binding before running the stored arguments exactly once, a restart turns an `APPROVED` or `EXECUTING` request into `NEEDS_REVIEW` without replaying it, and a 60s sweep expires pending requests. The default `FileApprovalStore` writes one JSON file per request under `qlawkus.agent.state.root/approvals`; `store.pg.PgApprovalStore` (the `approval_request` table, `V11`; the decision is a compare-and-set under a row lock in `ApprovalRequestRepository`) and `store.pg.HybridApprovalStore` (files decide, the table mirrors, and a mirror failure never undoes a recorded decision) follow `qlawkus.cognition.backend`. `ApprovalGate.pendingCount()` is the read the console overview uses. Decisions are owner-only and never reachable from a tool: `/approve` and `/deny` in messaging (read before the model, allowlisted), `/api/admin/approvals` (`@Authenticated`), and the console page. Approval outcomes resume the originating conversation through `ApprovalResumeListener` on the interactive workload; expiry and review notify the chat without a model turn. Tools declared on `AgentService` and remote MCP contributor tools are not gated (resume rebuilds `@QlawTool` executors by name only). A tool is gated by `qlawkus.approval.tools` or by any `ApprovalRequirement` bean (`ApprovalPolicy` combines both); `qlawkus-tools-skill-hub` (`SkillHubApprovalRequirement`: install, update, publish) and `qlawkus-tools-mcp-client` (`McpApprovalRequirement`: `configureMcpConnection`) request it while their `approval-mode` is `hitl`, and those tools write only inside `ApprovedExecution` (a thread-local marker `ApprovalService.runTool` sets), so a model-supplied `confirm` is ignored. Buttons: `CdiApprovalNotifier` fires `ApprovalPromptEvent` for PENDING requests, `messaging`'s `ApprovalPromptDeliveryListener` calls `MessagingProvider.sendApprovalPrompt` (Telegram inline keyboard, Discord `ActionRow`; default false falls back to the text notice), and a press becomes the typed `/approve <id>` or `/deny <id>` from the pressing user through `MessagingOrchestrator` (`ApprovalCallbacks`), so the allowlist and the compare-and-set apply and the model is never involved. A Telegram webhook callback needs the configured secret header (403 otherwise). Slack has no buttons (no interactivity endpoint). Documented in `site/content/approvals.adoc`.
- **Scheduled tasks** (`client/runtime/.../task`) - `TaskSchedulerTool` (`@QlawTool`: `scheduleTask`, `listScheduledTasks`, `cancelScheduledTask`) lets the agent schedule owner-requested reminders. `DynamicTaskScheduler` keeps each agent-created task as a record in a `store.ScheduledTaskStore` (`store.markdown.MarkdownScheduledTaskStore` by default, one JSON file per task under `scheduled-tasks` in the state root; `store.pg.PgScheduledTaskStore` on the `scheduled_task` table for pgvector; `store.pg.HybridScheduledTaskStore` keeps files plus a table mirror) and each task is a Quartz job under a namespaced `qlawkus-task-` id, cancellable only by those ids. A save happens before the task is reported as scheduled, and a cancel or one-time retirement removes the record. `DynamicTaskRestorer` (`@Startup`, after `InstanceLock`) registers the stored tasks again at boot: a one-time task that was due while the agent was down is marked `MISSED` and never run, a cron the scheduler cannot run is `INVALID`, and both stay listed until cancelled, never retried. A firing restores the origin conversation and the destination around `AgentRunner` on the interactive workload, then fires `WorkflowResultReadyEvent`. Tasks carry no chat ids on the tool surface: the destination is the origin chat from a messaging conversation, else a provider name resolved through `task.OwnerChatDirectory` (the owner's most recent accepted messaging chat per provider, fed by `MessagingOrchestrator`, persisted by `store.OwnerChatStore`: a `<provider>.json` under `owner-chats` for markdown, the `owner_chat` table for pgvector, and both in hybrid. Pgvector imports legacy files. The file stores map `ScheduledTask` and `OwnerChat` field by field through Jackson's tree model (`ScheduledTaskJson`, `OwnerChatJson`), so those records need no native reflection registration; `PersistedStateJsonTest` pins that every component is carried and that files the reflective mapper wrote still read. Hybrid reconciles each provider’s latest observation on startup. Accepted Discord `/qlawkus verbose` commands record the chat too). REST and console callers with no provider deliver to the most recent chat on any provider, and get a plain-words refusal when there is none. The user-facing page is `site/content/scheduler.adoc`.

- **`tools/qlawkus-tools-web-fetch`** - Optional page-reading extension (`deployment/` + `runtime/`, capability `web-fetch`, config root `qlawkus.web-fetch.*`, `enabled` default `false`; `app/` turns it on). `WebFetchTool.fetchUrl(url, format)` is the `@QlawTool`; the pair of web tools is deliberate: `web-search` finds links and never fetches them, this one fetches and never searches. `PageFetcher` is hand-written on the Vert.x HTTP client for a stated reason: the URL is the model's, so each hop of a redirect chain must pass `FetchPolicy` before a connection opens, which a REST Client interface cannot express. The client never follows redirects and sends no `Accept-Encoding`, so the hop limit, the byte cap and the absence of decompression bombs are enforced here, and `@Retry` covers one HTTP call (a `TransientHttpException`: 429, 5xx, network failure), never the redirect chain; a timeout is permanent (`FetchFailure`) because retrying a slow page multiplies the wait. The connection is pinned: `FetchPolicy.resolve` returns the addresses it validated and the request connects to one of them through `RequestOptions.setServer` while the URL's host still supplies `Host`, SNI and the certificate check, so nothing is resolved twice and DNS rebinding is closed (`PinnedConnectionTest`; the JDK client cannot connect to a chosen address and keep the host name for TLS, which is why it is not used). `FetchPolicy` (`@DefaultBean`, a protected constructor for a test `@Alternative` that reaches a loopback server, as `TestingFetchPolicy` does) refuses non-http(s) schemes, credentials in the URL, `blocked-domains` (suffix match for names, exact for address literals) and any resolved address that is loopback, link-local (cloud metadata included), private, carrier-grade NAT, multicast, unique-local, reserved, or an IPv4 carried in NAT64 or 6to4. `HtmlText` (jsoup, BOM-managed) renders markdown or plain text, drops scripts, chrome and non-http(s) links; `WebFetchFrame` frames the result as `<web-fetch-data>` untrusted data in the `TelemetryFrame` style, defusing marker lookalikes in the page, the preamble and the source. Only `text/*`, JSON and XML bodies are read; any other content type is refused unread. See `site/content/web-fetch.adoc`.

## Cognition & Memory

The memory subsystem (`client/runtime/.../cognition` + `.../store`) is the core of the agent. Its guiding principle: **relevant memory is injected into the prompt automatically each turn, so recall never depends on the model remembering to search** - and the stores stay fully searchable on demand (RAG feeds the automatic injection; the `session_search` tool lets the model deliberately query transcripts). Automatic injection is the reliable default; tool-based search is available on top. Understanding it means reading several files together:

Three layers, all injected each turn via `SoulEngine` (the agent's `systemMessageProviderSupplier`) and the retrieval augmentor:

- **Persona** - `Soul` (a plain singleton domain object) rendered into the system message by `SoulEngine`. Persisted behind the `SoulStore` SPI, backend selected by the same `qlawkus.cognition.backend` switch: `store.markdown.MarkdownSoulStore` (`@DefaultBean`, a `soul.md` file seeded from `META-INF/qlawkus/default-soul.md`, no DB), `store.pg.PgSoulStore` (the `soul` table via `SoulEntity`), `store.pg.HybridSoulStore` (reuses pg).
- **Owner** - `UserProfile` (a plain singleton domain object; the single user this agent serves) injected every turn by `SoulEngine`. Maintained by `UpdateUserProfileTool`, refreshed by `MemoryCurationJob`. Persisted behind the `UserProfileStore` SPI: `MarkdownUserProfileStore` (`@DefaultBean`, an `owner.md` file), `PgUserProfileStore` (the `user_profile` table via `UserProfileEntity`), `HybridUserProfileStore`. Roots for the markdown soul/profile files: `qlawkus.agent.state.root` (default `~/.qlawkus/state`).
- **Facts** - `FactStore` SPI, backend selected at **build time** via `@IfBuildProperty` on `qlawkus.cognition.backend` (`markdown` | `pgvector` | `hybrid`): `store.markdown.MarkdownFactStore` (`@DefaultBean`; `.md` files + in-process `InMemoryEmbeddingStore` with a JSON embedding cache, no DB; shared file logic in `MarkdownFactFiles`), `store.pg.PgFactStore` (pgvector; `@IfBuildProperty pgvector enableIfMissing`, only present when the `cognition-pgvector` extension is on the classpath), `store.pg.HybridFactStore` (files source-of-truth + pg mirror). Root: `qlawkus.agent.facts.root` (default `~/.qlawkus/facts`). The markdown stores are `@DefaultBean` across the module split, so they win whenever the pgvector extension is absent (database-free) and the non-default pg/hybrid beans override them when it is present - regardless of the `backend` value. Every embedding is tagged with a `MemorySource` (`remember-tool`, `semantic-extractor`, `episodic-consolidator`, `transcript`) - the enum exists so producers and purges never drift. **Facts are chunked before embedding** (`store.FactChunker`, char-budget `qlawkus.agent.facts.chunk-*`, default ~1200 chars ≈ 400 tokens): a fact over the embedding model's token limit (512 for `nv-embedqa-e5-v5`) is split into overlapping segments, so one fact becomes N vector rows sharing a parent `factHash` (in metadata; segment 0 also carries the whole `factText` for pg→files reconstruction). Identity/dedup is the `factHash`, not the row text - the pg `embeddings.content_hash` is generated from `metadata->>'factHash'` (not unique, since N segments share it), so `existsByContentHash` dedups at fact granularity. Without this, an oversized fact fails to embed: in `hybrid` the `.md` is written before the embed, so it orphans file-only and `CognitionReconciler.reconcileFacts` aborts the whole 6-store union every boot (the reconcile now also try/catches per fact, so one bad fact never aborts the union).

Stores & retrieval:

- **Active Memory** - `ActiveMemoryAugmentor` is the AiService `retrievalAugmentor`; it runs an `EmbeddingStoreContentRetriever` before each reply and injects query-relevant facts. The index comes from `FactStore.embeddingStore()` on the resolved `FactStore` (markdown: its in-process index; pgvector/hybrid: the pg table), never from a lookup of a concrete store class: in hybrid the `@DefaultBean` `MarkdownFactStore` stays in the build whenever anything keeps it (`@Unremovable`, `quarkus.arc.remove-unused-beans=false`), and recall would then read its in-process index, which never sees a fact `HybridFactStore` writes after it loads (pinned by `HybridActiveMemoryTest`). It filters OUT `source=transcript` so curated facts stay clean.
- **Working memory** - `WorkingMemoryStore` SPI (also a langchain4j `ChatMemoryStore`), windowed to 40 messages. `updateMessages` is append-only (preserves `createdAt`; never reset it) and fires `MessagesAppendedEvent` for every new message on any channel. Backends: `store.markdown.MarkdownWorkingMemoryStore` (`@DefaultBean`, one append-only `<memoryId>.jsonl` per conversation under `qlawkus.agent.working-memory.root`, default `~/.qlawkus/working-memory`), `store.pg.PgWorkingMemoryStore` (the `chat_message_entity` table), `store.pg.HybridWorkingMemoryStore` (reuses pg - the rolling chat log is transient, not file-versioned). The markdown store is the `@DefaultBean`; because upstream ships a `@DefaultBean InMemoryChatMemoryStore`, `ClientProcessor` vetoes it (`ExcludedTypeBuildItem`) so there is a single default and the non-default pg/hybrid beans still override when the pgvector extension is present.
- **Transcripts (session_search)** - `TranscriptArchiveObserver` embeds each message as `source=transcript`; `SearchTranscriptsTool` searches only those.
- **Episodic** - `EpisodicConsolidatorJob` (nightly) summarizes each day into journals (also embedded through the `FactStore` as `source=episodic-consolidator`). The journal record is an `EpisodicStore` SPI, backend selected at build time by the same `qlawkus.cognition.backend`: `store.markdown.MarkdownEpisodicStore` (`@DefaultBean`; dated `<date>.md` files, one per day, no DB; file logic in `MarkdownEpisodicFiles`), `store.pg.PgEpisodicStore` (the `Journal` table), `store.pg.HybridEpisodicStore` (files source-of-truth + pg mirror). Pg/hybrid share Panache access via `JournalRepository` and live in the `cognition-pgvector` extension. Root: `qlawkus.agent.episodic.root` (default `~/.qlawkus/journals`).

Scheduled background jobs, each with a manual `POST /api/admin/memory/*` trigger:

- `MemoryReviewJob` - semantic dedup of near-duplicate facts (`/review`).
- `MemoryCurationJob` - folds facts into the owner profile, reconciling contradictions; leaves facts untouched (`/curate`).
- `SemanticExtractorObserver` - extracts facts from a conversation on `ChatCompletedEvent`. The event is emitted channel-agnostically by `ChatCompletionEmitter`, which observes the store-level `MessagesAppendedEvent` and fires once per turn (when a final assistant message - one without tool-execution requests - is appended). **Passive fact extraction works on every channel** (REST, Discord, Telegram); gate it with `qlawkus.agent.semantic-extractor.enabled` (default `true`). The same event also drives the Brag `AchievementProcessor`, so both run on all channels.
- **Turn gate** - each post-turn observer (`SemanticExtractorObserver`, `SkillExtractorObserver`, `AchievementProcessor`) asks `cognition.gate.TurnGates` before its generation, with a yes/no `TurnQuestion`. The SPI is `TurnGate`; the `@DefaultBean` `PassThroughTurnGate` answers yes to everything, so behaviour is unchanged. `TurnGates` calls the gate on the `batch` workload and fails open (a throw runs the generation, logged by exception class only), counting each decision in `qlawkus.turn.gate{question,outcome}` (`pass`|`skip`|`error`). Only the `onChatCompleted` path is gated; the public `extractAndStore` methods are not.

Config knobs: `qlawkus.agent.memory.*`, `qlawkus.agent.active-memory.*`, `qlawkus.agent.transcript-*`, `qlawkus.agent.semantic-extractor.*`, `qlawkus.memory-review.*`, `qlawkus.memory-curation.*`. Admin REST: `GET/DELETE /api/admin/memory` (summary / purge), `POST /api/admin/memory/{review,curate}`. End-to-end check: `scripts/memory-benchmark.sh` (needs a running instance + real LLM).

Gotcha when testing recall: working memory and the system prompt are both sources, so to prove a fact came from the vector store, `TRUNCATE chat_message_entity` first. The NVIDIA embedding model scored a relevant query/passage pair around 0.88 and an unrelated one around 0.61 (langchain4j's `(cos+1)/2`) when it was `nemotron-3-embed-1b`, so `0.7` is the default margin; the current default, `nemotron-3.5-embed-1b`, has not been re-measured. Re-measure that gap whenever the embedding model changes: a new model with a lower distribution silently stops recall.

## Skills (procedural memory)

Skills are the agent's **procedural** memory (how to do a recurring task), complementing the declarative memory above. Each skill is a `SKILL.md` file (YAML frontmatter `name` + `description` + Markdown body). Same discipline as memory: the index is **injected, not searched** - `SoulEngine` adds a `## Skills` block (name + description only, via `SkillIndexRenderer`, capped by `qlawkus.skills.max-injected`) every turn; the full body is loaded on demand with the `viewSkill` tool (progressive disclosure).

- **SPI**: `skill.SkillStore` (interface) with `Skill`/`SkillSummary` records. SKILL.md **parsing is delegated to the upstream `dev.langchain4j.skills` loaders** (`FileSystemSkillLoader`, agentskills.io spec, BOM-managed `dev.langchain4j:langchain4j-skills`); `SkillFrontmatter` owns only the **write** side (rendering a `Skill` back to frontmatter + body), which upstream does not provide. The backend is selected at **build time** via `@IfBuildProperty` on `qlawkus.cognition.backend` (`markdown` | `pgvector` | `hybrid`): `MarkdownSkillStore` (`@DefaultBean`, no DB, shared file logic in `MarkdownSkillFiles`), `store.pg.PgSkillStore` (the `skill` table, `V6` migration), `store.pg.HybridSkillStore` (files source-of-truth + pg mirror). Reads from all `qlawkus.skills.roots` (first wins); writes only to the first, owned root (default `~/.qlawkus/skills`).
- **Tools** (in `AgentService`): `ViewSkillTool` (load body), `ManageSkillTool` (`createOrUpdateSkill` / `deleteSkill`).
- **Auto-distill**: `SkillExtractorObserver` mines a reusable skill from each `ChatCompletedEvent` (gate `qlawkus.skills.extractor.enabled`), mirroring `SemanticExtractorObserver`.
- **Curation**: `SkillCurationJob` removes redundant skills (scheduled + `POST /api/admin/skills/curate`).
- **Lifecycle**: `viewSkill` calls `recordUse`; `SkillLifecycleJob` ages unused skills `ACTIVE -> STALE -> ARCHIVED` (config `qlawkus.skills.lifecycle.*`, scheduled + `POST /api/admin/skills/lifecycle`). Archived skills leave the injected index but stay loadable; pinned skills (`POST /api/admin/skills/{name}/pin`) never transition. Telemetry: pg columns (migration `V7`) for pgvector/hybrid, a `.qlawkus-usage.json` sidecar for markdown. `SkillUsageJson` maps the sidecar field by field through Jackson's tree model, so it needs no native reflection registration (a reflective read fails every time in the native image); `SkillUsageJsonTest` pins that every record component is covered and that files the reflective mapper wrote still read.
- **Admin REST**: `GET/DELETE /api/admin/skills`, `GET /api/admin/skills/{name}`, `POST /api/admin/skills/{curate,lifecycle}`, `POST /api/admin/skills/{name}/pin`.
- **Bundled skills (build-time)**: extensions/apps ship read-only skills as classpath resources under `META-INF/qlawkus-skills/<name>/SKILL.md`. `ClientProcessor.bundledSkills` (a `@BuildStep` + `SkillsRecorder`) scans and parses them (via the same `FileSystemSkillLoader`) at **augmentation** and bakes them into the synthetic `BundledSkills` bean - no runtime classpath scanning. Stores merge bundled (read-only) with owned skills; owned wins on a name clash. The bundling **machinery** lives in `client`; curated default skill **content** is a distribution concern and should ship from `app`, not `client`.
- **Remote registry (Skill Hub)**: everything above is **local** (read/write SKILL.md files, offline). The **outward-facing** registry client lives in the optional `qlawkus-tools-skill-hub` extension (package `tools.skillhub`), kept out of `client` so a locked-down distribution can omit the network capability at the module level (not just a config flag). SPI `SkillHub { search(query, limit); install(source); discover(source); installCandidate(candidate); publish(skill) }`, default impl `HttpSkillHub` (`@DefaultBean`; plain `java.net.http` + Jackson, **no external CLI** - jskills/skills.sh both need extra tooling installed, so the behavior is replicated natively instead). Tools `searchSkillHub`/`installSkill`/`listSkillsInSource`/`installSkillsFromSource`/`installSkillFromText`/`updateSkill`/`listSkillSources`/`publishSkill` are `@QlawTool` (discovered cross-module by `ClientProcessor`'s `@QlawTool` scan). Config root `qlawkus.skill-hub.*`.
  - **Search**: hits `<base-url>/api/search` plus, for each `well-known-hosts` entry, the `/.well-known/agent-skills/index.json` index (agentskills.io standard, fallback to legacy `/.well-known/skills/`). Best-effort across sources, deduped by source, capped by `max-results`.
  - **Install**: resolves an `owner/repo` slug to the raw GitHub SKILL.md (tries `main`/`master`), an `owner/repo/skill` reference (skills.sh hits carry the skill folder name as `skillId`; tries `skills/<skill>/SKILL.md`, `<skill>/SKILL.md`, then one GitHub tree lookup per branch for a nested `<skill>/SKILL.md`, and the root SKILL.md last, only when it declares the named skill) or takes a direct URL (well-known hits are direct URLs), validates the name against path traversal, saves via `SkillStore` into the owned root - so it enters the injected index next turn. Search drops hits with no installable source (a bare host). A failed install throws, so the tool returns an error result and `MeteredToolExecutor` counts `outcome=error`; `HttpSkillHub` logs the source and the paths tried at WARN. Only the SKILL.md text is fetched; executable assets are never pulled or run (inert by omission).
  - **Sources**: `SkillSourceParser` normalizes whatever was pasted into a `SkillSource` (a name, a slug, a GitHub blob/tree/raw/repo link, a GitLab or Bitbucket file or folder link, a skills.sh page, a gist, a `.zip`/`.tar.gz` archive, or any https SKILL.md). `discover` lists the skills a folder, repository, archive or gist holds; `installCandidate` saves one; `install` is the single-skill path and refuses a source that holds several. `ArchiveSkillReader` reads zip (central directory, symlinks refused) and tar.gz entirely in memory and returns only SKILL.md text; caps come from `qlawkus.skill-hub.archive.*`, `max-skill-bytes` and `max-installs-per-call`. Pasted text goes through `SkillMarkdown.parsePasted`. Every network path passes `OutboundPolicy` (https only, no credentials, every resolved address public, checked again on each of up to three redirect hops); a `@DefaultBean` with a protected lenient constructor that test profiles swap in with a `@Alternative` (WireMock is plain http on loopback). The response is read under a size cap through one `@Retry`-annotated `exchange` call.
  - **Provenance**: `SkillStore.recordOrigin`/`originOf` (defaults are no-ops) store `SkillOrigin(source, candidate, installedEpochMs)` in the `.qlawkus-usage.json` sidecar for markdown and hybrid (`MarkdownSkillFiles`). `pgvector` stores none yet: it needs a `skill` column (a migration, not written). `save` clears the origin, so an agent-authored rewrite drops the recorded source.
  - **REST**: `SkillInstallResource` (`@Authenticated`, `/api/admin/skills/install[/list|/selection|/text|/upload/list|/upload/selection|/update/{name}]`) is the admin install path; the request is the approval (no HITL round-trip), with the same caps. Uploads are multipart and read in memory; the hub's `discoverUpload` applies `archive.max-bytes` and `max-skill-bytes`. Failures carry a `kind` (`refused`, `limit`, `unreachable`, `disabled`); a cap refusal is `SkillLimitException`. `SkillUpdates` is the one update path, shared by the `updateSkill` tool and the REST endpoint; an uploaded skill (`upload:` source) is refused. The console never calls these in-process: its install panel is the separate `console-skill-hub` extension (below), which depends on the hub and the console, never the reverse.
  - **Publish**: `publishSkill` renders an owned skill to `<publish.dir>/<name>/SKILL.md` (reusing `SkillFrontmatter.render`, now `public`). It **never runs git** - in a container, mount `publish.dir` to a host git working copy and the owner pushes from the host (keeps credentials out of the container and honors the manual-push rule). Opt-in via `publish.enabled` (default false).
  - **Approval**: install (every path, including a plain name and pasted text), update and publish honor `qlawkus.skill-hub.approval-mode` (`yolo` acts immediately; `hitl` holds the call as a durable owner approval, see Owner approvals; the `confirm` argument is ignored). The approval notice names the tool and arguments before anything is written.

Config knobs: `qlawkus.cognition.backend`, `qlawkus.skills.*`, `qlawkus.skill-hub.*`. Facts, episodic journals, skills, working memory, the persona (`Soul`) and the owner profile (`UserProfile`) are all pluggable on this same switch, and the entire Postgres backend now lives in the optional `cognition-pgvector` extension - so a build without it is database-free (validated by `integration-tests/markdown-only`). The remote-registry side of skills is the optional `qlawkus-tools-skill-hub` extension (above).

Backend migration (in `cognition-pgvector`, so only in pgvector/hybrid builds): `store.pg.reconcile.CognitionReconciler` does a bidirectional, idempotent **union** of files <-> pgvector across all six stores (collections keyed by content hash/date/name/conversation id; singletons filled only when one side is empty, never clobbered). It runs once at hybrid boot via `HybridReconcileStartup` (gate `qlawkus.cognition.reconcile-at-start`, default `true`) and on `POST /api/admin/cognition/reconcile`. `CognitionMigrator` (`POST /api/admin/cognition/migrate?direction=files-to-pg|pg-to-files`) is the explicit one-directional copy that **does** overwrite the destination singletons. This is a Qlawkus capability, not an upstream langchain4j one - it's only possible because every store keeps a parallel markdown representation as the bridge. Covered by `CognitionReconcileTest`.

```bash
# Native ITs (enable with -Pnative)
mvn verify -Pnative

# Composition maven-invoker IT (real reactor + qlawkus:generate). Needs qlawkus-composition-model

mvn -pl composition-model install -DskipTests
mvn -pl composition-maven-plugin install -DskipTests -DskipITs=false
```

- `client/deployment/src/test/` - Extension build-time tests with WireMock-mocked LLM
- `integration-tests/*/src/test/` - QuarkusTest integration tests; some call real LLMs, some use `@InjectMock`
- LLM-dependent tests use `@EnabledIf("dev.omatheusmesmo.qlawkus.testing.QlawkusTestUtils#usesLLM")` - auto-skip when `LLM_API_KEY` is absent or "dummy", or when the module forces `qlawkus.test.mock-mode`
- Smoke tests (`integration-tests/smoke/`) hit real LLM: can take 5+ minutes per test
- Every `integration-tests/*` module that declares a `@QuarkusIntegrationTest` class must bind `maven-failsafe-plugin` (`integration-test` + `verify`, as `brag` does), or its `*IT` classes compile and never run, JVM or native. Their runtime config (file roots, `qlawkus.startup-thought.enabled`) is unprefixed rather than `%test`, because the packaged artifact boots in the prod profile.
- `integration-tests/live-provider/` is the only module that calls the real provider: one embedding call (asserting the configured dimension), one minimal call to the primary chat model and one to the `secondary` tier (called directly, not through the fallback chain; skipped unless `qlawkus.model.secondary-enabled` is true for the resolved kind), with no WireMock and no `mock-mode`, so a model the provider retires fails it where every WireMock-backed test stays green (#359). It reads the provider from the `LLM_*` environment and skips unless `LLM_API_KEY` is a real key (`LLM_KIND` and the model overrides when not on the default provider). The push and nightly builds run it in a step of its own that exports the `NVIDIA_API_KEY` repository secret as `LLM_API_KEY` (with `LLM_KIND: nvidia`), after the main build, which keeps `LLM_API_KEY: dummy`: the `LLM_*` variables are read by every module's provider resolution (`LlmKindConfigSourceFactory`), so exporting them for the whole job re-points the WireMock-backed modules at the real provider and breaks them. While that secret holds `dummy` the test skips. JVM-only: it keeps jar packaging under `-Pnative`.

## Adding Tools

Create a CDI bean annotated with `@QlawTool` + `@ApplicationScoped`. Methods annotated with `@Tool` are auto-discovered at build time by `ClientProcessor` (which also registers DTO records in `dev.omatheusmesmo.qlawkus.dto` for reflection). No manual registration needed.

New tool modules must also be added as dependencies in `app/pom.xml`.

A tool that makes outbound HTTP calls follows the retry contract in **Resilience & Health** below: throw `TransientHttpException` for transient failures, and annotate the single HTTP call rather than the tool method.

A tool sees the caller's context on both paths. On `chatSync` it runs on the caller's thread, so the `AgentDeliveryContext` ThreadLocal and the request context are already there. On the streaming path (`AgentStream`) it runs on the model client's callback thread, so `StreamedToolContext` captures the caller's delivery values and request context when the turn starts (keyed by conversation) and restores them around each call: `ContextBridgingToolExecutor` for `@QlawTool` tools (inside `QlawToolProvider`'s metering) and `StreamedToolWrapper` for the tools declared on `@RegisterAiService(tools = ...)`, the seam quarkus-langchain4j exposes for them. With no caller request context a fresh one lives for that call only. A new tool that reads request-scoped state or the delivery context needs nothing more; a new tool seam must go through this bridge, not read the ThreadLocal directly.

## Extension Development

Every module here (`client`, `tools/*`, `messaging/*`) is a full Quarkus extension: a `runtime/` + `deployment/` pair. Rules that keep that pattern correct:

- **Dependency direction is one-way.** `deployment/` depends on `runtime/` (plus other extensions' `*-deployment` artifacts); `runtime/` must NEVER depend on any `deployment` artifact. The Maven plugin validates this and fails the build if a required deployment dependency is missing.
- **Three bootstrap phases.** Build-time *augmentation* runs `@BuildStep` processors (e.g. `ClientProcessor`) - it reads the Jandex index, never loads app classes, and records bytecode. `@Record(STATIC_INIT)` bytecode runs in a static initializer (framework boot, bean wiring; do NOT open ports, start threads, or read runtime config here). `@Record(RUNTIME_INIT)` bytecode runs in `main` (ports, runtime config, service start). Push work to STATIC_INIT when possible.
- **Build steps talk via build items, not fields.** A build-step class is instantiated per invocation and discarded; share state only through immutable `*BuildItem`s. Always produce a `FeatureBuildItem`. A step runs only if something consumes what it produces.
- **Recorders bridge build to runtime.** `@Recorder` methods in `runtime/` are *recorded* (not executed) at build time; their calls replay at runtime. Parameters must be bytecode-serializable (primitives, strings, config objects, `RuntimeValue<T>`). Wrap complex objects in `RuntimeValue<T>`.
- **Config is `@ConfigMapping` interfaces.** `@ConfigRoot(phase = RUN_TIME)` + `@ConfigMapping(prefix = "qlawkus...")`, JavaDoc on each accessor (it becomes the generated config-reference description), `@WithDefault` for defaults, `Optional<T>` for optional, `Map<String, X>` for keyed/dynamic config (see `MessagingConfig`). Choose phase by need: `BUILD_TIME` (build only), `BUILD_AND_RUN_TIME_FIXED` (read at build, immutable at runtime), `RUN_TIME` (re-read each run, overridable).
- **CDI registration.** Register extension beans with `AdditionalBeanBuildItem`; use `@DefaultBean` for anything app code should be able to override; `SyntheticBeanBuildItem` for beans built through a recorder.
- **Native image.** Reflection needs registration - `ClientProcessor` already registers `dev.omatheusmesmo.qlawkus.dto` records via `ReflectiveClassBuildItem`; new reflective types (DTOs, models) must be added the same way (or `@RegisterForReflection`). Use `NativeImageResourceBuildItem` to bundle resources. Verify with `mvn verify -Pnative`.
- **A new optional extension must declare its composition capability.** Add `metadata.qlawkus.capability` to the module's `src/main/resources/META-INF/quarkus-extension.yaml` (create the source template if the module only relied on the generated one). That single key is what the `qlawkus-maven-plugin` `ReactorCatalog` maps to the module's coordinates, so the `agent.yml` manifest can compose the extension in or out. A module with no key is treated as always-present skeleton and is never toggled - so forgetting it means the capability silently cannot be selected. Name capabilities namespaced where natural (`messaging.discord`, `cognition.pgvector`); several modules may share one name to move as a unit (`google-workspace`). Keeping it in `quarkus-extension.yaml` (not the pom) is deliberate: that metadata rides into a published Quarkus platform catalog, so the same key serves both the in-repo `ReactorCatalog` and a future published-artifact catalog for consumers building from `agent.yml` without cloning.
- **Before inventing a build item, check the catalog**: [all build items](https://quarkus.io/guides/all-builditems).

## Secrets

Database-free secret store, owned by `client` (no separate module, no custom crypto). Secrets live in a PKCS12 keystore named by the convention `qlawkus.secrets.keystore-path` (default `~/.qlawkus/secrets.p12`), unlocked by `qlawkus.secrets.keystore-password`. The built-in SmallRye keystore source is fixed at ordinal 100 (below env) with no knob to raise it, so `client` ships its own `secrets.KeystoreSecretConfigSourceFactory` (a `ConfigSourceFactory` registered via `META-INF/services`) that reads the keystore with the plain JDK `KeyStore` API (`getKey().getEncoded()` as UTF-8 - exactly how `keytool -importpass` stores it) and republishes every entry at `qlawkus.secrets.keystore-ordinal` (default 350). Knobs are documented by `SecretsConfig` (`@ConfigMapping(prefix="qlawkus.secrets")`), rendered into the config reference under "Secrets".

- **Alias = property name.** Each keystore alias is the config property it supplies; consumers read a plain `@ConfigProperty` (no code change). Onboard with `keytool -importpass -alias '<config.property.name>' -keystore <path> -storetype PKCS12`.
- **Write side (no keytool).** `secrets.KeystoreSecretWriter` (`@ApplicationScoped`) onboards a secret programmatically via the JDK `KeyStore` API, creating the file on first write and storing entries identically to `keytool -importpass` (PBE `SecretKeyEntry`). The read/write PKCS12 convention is centralized in `secrets.KeystoreSecrets` (the `ConfigSourceFactory` now delegates its read to it, so reader and writer can't drift). REST surface `rest.SecretsAdminResource` (`@Authenticated`, `/api/admin/secrets`): `PUT` (body `{alias,value}`, never logs the value), `GET` (alias names only), `DELETE ?alias=`. A missing `keystore-password` returns `409` (won't create an unprotected store); a written secret takes effect on next boot. Covered by `markdown-only` `SecretWriteEndpointTest` (the read-back asserts keytool-compatibility) + `SecretWriteNoPasswordTest` (the 409 guard).
- **Auth is fail-closed and pluggable.** `app/` drops the old `${API_USER_PASSWORD:qlawkus}` fallback - the bundled distro refuses to boot without a real credential (env, or the matching keystore alias); `%dev` keeps a known password for local dev only. Auth mechanism is the integrator's choice via standard Quarkus security: endpoints use `@Authenticated`, so adding `quarkus-oidc` / `quarkus-smallrye-jwt` to the consuming app swaps the mechanism with zero Qlawkus code (no custom auth extension - that would reinvent `quarkus-oidc`).
- **Authoritative precedence.** Published at ordinal 350: `sysprops (400) > keystore (350) > env (300) > .env (295) > application.properties (250)`. A stored secret wins over the matching env var, so the rule is "drop it in the keystore and it takes effect" with no stray env default able to shadow it; only `-D` system properties still override. Lower `qlawkus.secrets.keystore-ordinal` below 300 to let env override instead. Validated by `integration-tests/markdown-only` `KeystoreSecretTest` (`keystoreSecretOutranksApplicationProperties` + the absent-keystore leniency contract), which boots with no datasource.
- **Lenient.** Resolves the keystore on the filesystem then the classpath; absent file contributes nothing, so a fresh install boots on `.env` and the feature stays inert until a keystore exists.
- **Migrating consumers.** No consumer change is needed: the alias is the property the consumer already reads, and the keystore (350) outranks the `application.properties` `=${ENV:}` line (250). The catalog of secret properties lives in `site/content/secrets.adoc` ("What to store"). The one non-obvious case is the LLM/embedding key: `model.LlmKindConfigSourceFactory` runs at ordinal 90 and reads `quarkus.langchain4j.openai."primary".api-key` / `LLM_API_KEY` back from the context (it only honours sources out-ranking 90), so a keystore-stored key flows through it unchanged. `KeystoreSecretTest.llmApiKeyResolvesFromKeystoreThroughKindFactory` pins this end to end (the value reaches the real OpenAI client's Authorization header).
- **Container.** Mount the keystore path on a persistent volume; pass `QLAWKUS_SECRETS_KEYSTORE_PASSWORD` via env. File and password stay out of the image.
- **The agent's shell never inherits the process environment.** `tool.shell.ChildEnvironment` is the single builder both `ShellTool` and `PtySessionManager` use: it starts from an empty env and adds only `qlawkus.shell.env-allowlist` names (trailing `*` = prefix, default `PATH,HOME,USER,LANG,LC_*,TZ,TERM,SHELL,JAVA_HOME,TMPDIR`), then the workspace env file, then the `qlawkus.shell.secret-env."<NAME>"` pass-through. That map is `Map<String, Optional<String>>` on purpose: the app wires `GH_TOKEN=${GH_TOKEN:}`, and a plain `String` value makes an unset variable an empty-string boot failure (SRCFG00040). Passing `GH_TOKEN` also sets command-scope git config through `GIT_CONFIG_COUNT` (an empty `credential.helper` to drop `store`/`cache`, then `!gh auth git-credential` for github.com), so nothing is written to disk. `tool.shell.SecretRedactor` masks every pass-through value of 8+ chars and any GitHub-token-shaped string in command output, PTY output read back and the `SHELL_CMD` audit log; use it for any new path that returns command output. `SecretPropertyCatalog` treats the whole `qlawkus.shell.secret-env` prefix as secret. Redaction stops accidental leaks only: a process that can use a credential can read it, so the token must be minimal and expiring (see `site/content/secrets.adoc`, "What reaches the agent's shell").
- **Managed alternative.** `quarkus-vault` on the classpath contributes a `CredentialsProvider` and resolves secrets the same way (ordinary config); use it when secrets are managed centrally.
- **Gotcha.** The `.p12` test fixture is a real PKCS12 keystore. The global `pre-commit` hook strips trailing whitespace on non-blacklisted files and will corrupt it (DER `EOFException` at boot); commit keystore binaries with `git commit --no-verify`.

User-facing guide: `site/content/secrets.adoc`.

## Databases

Up to 3 PostgreSQL databases, all managed by Flyway:
- **`qlawkus`** (default) - Main: persona, owner profile, chat history, episodic journal, pgvector embeddings, agent-created scheduled tasks. **Only present when the `cognition-pgvector` extension is on the classpath** (it owns the default datasource, the 8 `V1..V8` migrations, and the pgvector config, contributed via its `META-INF/microprofile-config.properties`). A markdown-only build has no default datasource and never connects to Postgres.
- **`qlawkus_google_auth`** - OAuth credentials + state (Google tools extension)
- **`qlawkus_brag`** - Career brag documents (Brag tool extension; its own named `brag` datasource, independent of cognition)

## Documentation

One source, one generated mirror. **Edit only `site/content/`** - everything else is built from it.

**Every PR documents its own change, in the same commit.** A feature PR ships the user-facing page or section under `site/content/` (mirrored to `docs/modules/ROOT/pages/`, see below), a `config-reference.adoc` include for each new `qlawkus.*` config root, and the matching bullet in this file's Architecture inventory when it adds a subsystem or changes how an existing one is wired. A fix updates the page that already describes the behavior it changes. Documentation is part of the definition of done, never a follow-up PR; a reviewer can ask for it before merge.

- **`site/content/*.adoc`** - hand-written pages (the Roq site): `index`, `architecture`, `config-reference`, `quickstart`, `messaging`, `voice`, `google-workspace`. This is the source of truth.
- **`site/content/includes/*.adoc`** - **generated** config reference. `docs/pom.xml` runs `quarkus-config-doc-maven-plugin` (build-time augmentation, no datasource, depends on every `*-deployment` artifact) which writes one file per config root from the `@ConfigMapping` JavaDoc into `site/content/includes/`. Never edit these by hand - they are overwritten every build.
- **`site/public/images/`** - committed images served at the site root: `diagrams/*.svg` (hand-written SVG with `<title>`, `<desc>` and a dark palette via `prefers-color-scheme`, no build-time diagram toolchain) and `console/<page>-{light,dark}.png`, one pair per sidebar page. Pages reference them as `../images/...` because Roq serves each page at `<name>/index.html`. Regenerate the screenshots with `scripts/docs-screenshots.mjs` against a throwaway instance (not run in CI, so the build stays deterministic); `scripts/check-docs-content.sh` fails when a console page lacks its section or image, a diagram lacks its accessible text, an image or `xref:` target does not exist, or a task guide is missing. A new console page needs its section in `console.adoc` and both images in the same PR.
- **`docs/modules/ROOT/pages/*`** - the Antora copy. The `sync-site-to-antora` execution in `docs/pom.xml` (`maven-resources-plugin`, `verify` phase) copies all of `site/content/` here. It is a generated mirror; **never edit `docs/` directly** (the next build overwrites it). If you must commit the mirror without a full build, copy the changed file from `site/content/` to the matching `docs/modules/ROOT/pages/` path.

Regenerate after a config change:

```bash
mvn install -DskipTests                  # build extensions so config metadata is available
mvn -f docs/pom.xml verify -DskipTests   # generate includes/ into site/, then mirror site/ -> docs/
```

**`config-reference.adoc` is hand-written**, not generated. It surfaces each generated table with an `include::` directive. A `@ConfigMapping(prefix = "qlawkus.foo")` interface produces `qlawkus-client_qlawkus.foo.adoc`; the aggregate `qlawkus-client.adoc` holds **only** the `quarkus.*`-rooted properties. So **adding a new `qlawkus.*` config root requires adding a matching `include::includes/qlawkus-client_qlawkus.foo.adoc[]` line** under "Core agent" in `config-reference.adoc`, in **both** trees, or the new properties never render. (This is exactly how the entire `qlawkus.*` surface was silently dropped after the `@ConfigMapping` migration.)

## LLM Configuration

Two named model configs via `@ModelName`, both provider-agnostic:
- **`primary`** - Primary model (any OpenAI-compatible provider; default endpoint: NVIDIA NIM, default chat model `nvidia/nemotron-3-ultra-550b-a55b`; the previous default, `z-ai/glm-5.3`, reached its end of life on NIM on 2026-10-28). Pointed via the neutral `LLM_*` env vars (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_CHAT_MODEL`, `LLM_EMBEDDING_MODEL`, `LLM_TIMEOUT`).
- **`secondary`** - Same-provider chat model (openai provider, chat only). For the NVIDIA kind it is `nvidia/nemotron-3.5-lightning-30b-a3b` on the primary's endpoint and key (chosen over faster candidates for its rate limit: a tier that takes every turn while the primary fails must not throttle first), emitted by `LlmKindConfigSourceFactory` from `ProviderKind.secondaryChatModel()`, which also sets `qlawkus.model.secondary-enabled`. Overridable via `LLM_SECONDARY_CHAT_MODEL`, `LLM_SECONDARY_BASE_URL`, `LLM_SECONDARY_API_KEY`. A kind with no same-provider model leaves the tier disabled. It has its own breaker per workload (`SecondaryChatGuard`, one retry).
- **`fallback`** - Ollama, the local last resort, unchanged from before the secondary existed. Reached through `PrimaryChatGuard`/`EmbeddingGuard` once the primary has exhausted its retries and the circuit breaker opens, and through `SecondaryChatGuard` when the secondary fails. A same-provider tier does not survive a provider outage, which is why Ollama stays last; see **Resilience & Health**.
- The chain is primary, then secondary (when enabled), then Ollama. `fallback-on-reject=false` (batch) stops the chain at the primary when the bulkhead rejects; a permanent (#358) failure on the primary still moves to the next tier.

Dev mode: Dev Services auto-provisions Ollama (no `.env` needed).
Prod: Requires `LLM_API_KEY` in `.env`.

Embedding dimension comes from the provider kind (`ProviderKind`; NVIDIA `nemotron-3.5-embed-1b` is 2048, the others 1024) and can be overridden with `EMBEDDING_DIMENSION`. The pgvector column follows it: the repeatable `R__embedding_dimension` migration is keyed on the dimension and the model name through Flyway placeholders (a repeatable migration is checksummed after placeholder replacement, so either change re-applies it), records the model that produced the vectors in `embedding_model_marker`, keeps vectors that still match both and clears the rest (a new model at the same dimension included, #527), and `store.pg.EmbeddingBackfill` re-embeds the cleared rows from their text after boot, on the `batch` workload. The markdown backend keys its `.embeddings.json` cache on the model name (`.embeddings.model` sidecar), so a model change re-embeds instead of loading incomparable vectors. NVIDIA retired the previous default, `nv-embedqa-e5-v5`, on 2026-08-25 (#357): every turn failed with 410, since active memory embeds the query first. Its successor `nemotron-3-embed-1b` was retired on 2026-11-23 and failed the same way (#527).

Cost estimation is opt-in via `qlawkus.cost.enabled`. `model/TokenPriceCostEstimator` prices the token counts quarkus-langchain4j already reports, which is what turns on its `gen_ai.client.estimated_cost` metric. Off by default on purpose: an estimate is indistinguishable from a measurement once it reaches a dashboard, so a default price would be a confident wrong number. A distribution with tiered or committed pricing supplies its own `CostEstimator` at the default priority and is consulted first.

### Dependency versions (do NOT conflate the two langchain4j namespaces)

| What | Version | Where set |
|------|---------|-----------|
| Quarkus platform | `3.40.1.1` | `quarkus.platform.version` in root `pom.xml` |
| quarkus-langchain4j (Quarkiverse extension) | `1.14.2` | root `pom.xml` property `quarkus-langchain4j.version`, ahead of the platform (see below) |
| Upstream `dev.langchain4j` core (transitive) | `1.20.2` | same BOM - do not set |
| Upstream beta modules (`langchain4j-skills`, `langchain4j-pgvector`, `langchain4j-agentic`) | `1.20.2-beta30` | same BOM - do not set |

The Quarkiverse **extension** version (`1.14.2`) and the upstream **library** version (`1.20.2`) are different namespaces: `1.14.2` is NOT a langchain4j-core version. The `quarkus-bom` manages neither. The root pom imports `io.quarkiverse.langchain4j:quarkus-langchain4j-bom` at `quarkus-langchain4j.version` first, so it wins over the platform's copy (the platform ships `1.13.3` with `3.40.1.1`); the platform's `quarkus-langchain4j-bom` import stays after it for everything else the platform aligns. That Quarkiverse BOM transitively imports the `langchain4j-bom`, which pins every `dev.langchain4j:*` artifact. So when adding an upstream module (e.g. `langchain4j-skills`, or `dev.langchain4j:langchain4j` for `InMemoryEmbeddingStore`), add it with **no `<version>`** - the BOM resolves it.

The override is temporary: drop the Quarkiverse import (and the property) once the Quarkus platform ships quarkus-langchain4j >= 1.14.2. To move ahead again, bump `quarkus-langchain4j.version`; declaration order decides which BOM wins. Re-verify any time with:


## Resilience & Health

Fault tolerance is `smallrye-fault-tolerance` throughout; no hand-written retry or breaker remains in the reactor. Where a guard is applied matters far more than which annotation it uses, and there is one hard rule.

**Never put `@Retry`, `@CircuitBreaker` or `@Fallback` on `AgentService`.** The upstream quarkus-langchain4j fault-tolerance guide shows exactly that pattern, and it is wrong for a method that declares `tools`: the annotation wraps the whole ReAct loop, so a transient failure on a later turn replays tool calls that already succeeded on an earlier one, silently duplicating their side effects (quarkiverse/quarkus-langchain4j#2744). Guards belong on the underlying `ChatModel`/`StreamingChatModel`, where a retry replays only the one failed model call. The rule is repeated in the `AgentService` javadoc, but that copy only reaches someone already editing the file the annotation must stay out of.

**Model resilience is programmatic, not annotated.** `model/PrimaryChatGuard` and `model/EmbeddingGuard` build a `TypedGuard` instead of using `@CircuitBreaker`, because a CDI interceptor cannot serve the streaming path: it is callback-based, so the failure never crosses the interceptor boundary. Both are `@Startup`, so the breaker is registered before first use, and both name their breaker through `ModelFallbackConfig.CIRCUIT_BREAKER_CHAT` / `_EMBEDDING`. That name is the lookup key `ModelReadinessCheck` reads.

The programmatic API is also the only caller of `SpiAccess.get()`, and that has a native-image consequence worth knowing before touching either guard. `SpiAccess$Holder` resolves the fault-tolerance SPI through `ServiceLoader` and keeps only an implementation whose `applies()` returns true, which the CDI one answers by calling `CDI.current()`. Quarkus runs `STATIC_INIT` (Arc startup included) at image build time in native, so the holder usually initializes there and the instance is baked in - but whether the analysis reaches it before Arc is up varies between builds, which showed up as an intermittently red native build. `ClientProcessor` therefore pins the holder to runtime initialization **and** registers the `Spi` service provider; both are required, since deferring it without the registration moves the lookup into an image that resolves services only from explicit registrations, and the app then fails at boot. The annotation-driven path never hits any of this: it compiles to generated interceptors that do not call `SpiAccess`.

**Outbound HTTP goes through Quarkus REST Client by default.** A REST Client interface (`@RegisterRestClient`, typed request and response records, Jackson) gives timeouts, TLS, proxy, redirects, metrics and tracing through `quarkus.rest-client.<key>.*`, and maps statuses with a `@ClientExceptionMapper` that returns `HttpRetryClassifier.classify(response)`. Hand-written HTTP (`java.net.http`, a raw Vert.x client) needs a stated reason in the code or here, such as a per-call URL policy that REST Client cannot express. Still on hand-written HTTP only where a thin policy layer must run before connect and on each redirect hop: `OutboundPolicy` for skill-hub fetches (the GET itself is `SkillHubFetchClient` via `@Url`) and `TelemetryHttp` until the REST Client migration lands. Inbound messaging media uses `MediaDownloadClient`. Telegram Bot API calls (including `sendAudio`) go through `TelegramBotClient`. A base URL that is configuration per call (each TTS provider has its own) is passed with `@Url`; the interface's configured URL is then only the mandatory default.

**HTTP clients retry on one exception type.** Every outbound client (the 6 Google modules, Skill Hub, the messaging clients and media downloader, code review) throws `http.TransientHttpException` for a 429, a 5xx, or a network-level failure, and retries only that:

```java
@Retry(maxRetries = 3, delay = 500, delayUnit = ChronoUnit.MILLIS,
       jitter = 200, jitterDelayUnit = ChronoUnit.MILLIS,
       retryOn = TransientHttpException.class)
@ExponentialBackoff(maxDelay = 8000, maxDelayUnit = ChronoUnit.MILLIS)
```

Two rules keep that correct rather than decorative. It goes on **one HTTP call, not one logical operation**, so a multi-request `install` cannot re-run its first request because the third failed. And a permanent status (401, 403, 404) propagates immediately, since retrying something that will never resolve only delays surfacing it.

**Health checks go through the store SPIs, not through storage.** `health/CognitionReadinessCheck` reads through the SPIs and calls each store's `verifyWritable()`, so one check is correct on `markdown`, `pgvector` and `hybrid` with no conditional: each backend resolves its own store. Only the turn path blocks (persona, owner and skill index reads, working-memory write); the other writes report `degraded` and stay UP, because the agent is single-instance and DOWN means nobody answers. Skill probes run only while `qlawkus.skills.enabled` is on, and an instance already DOWN skips the write probes (they cannot change the verdict, and against a hanging database each would wait out a connection timeout). `verifyWritable()` must prove a write without making one, since readiness polls it every few seconds: markdown writes one byte to a fixed-name dotfile and deletes it (`store.markdown.WriteProbe`; fixed so a root where deletes fail keeps one file, not one per poll), pg asks the catalog (`store.pg.PgWriteProbe`: `transaction_read_only` plus `has_table_privilege`) rather than running a zero-row `INSERT`, which still takes a `RowExclusiveLock` and fires statement triggers. Each `PgWriteProbe.Table` lists exactly the DML its store issues (working memory and journals are INSERT/DELETE only): demanding more takes a correctly least-privileged instance DOWN, and on a single instance that means nobody answers. Never give a real store an empty `verifyWritable()`: that is the vacuous pass this check exists to remove (only the in-memory test doubles may). `health/ModelReadinessCheck` reads both breaker states through `CircuitBreakerMaintenance.currentState`, a read-only lookup, so polling readiness can never promote a breaker state as a side effect; it reports DOWN only when a breaker is OPEN **and** no fallback is configured. A check that is meaningful on only one backend belongs in that backend's own module, never as an `if` inside a shared check.

**A permanent model error is invisible to the breaker, so readiness reads it from `model/PermanentFailures`.** A 401, 403, 404 or 410 from the primary (a revoked key, a wrong model name, a retired model) is on the `abortOn`/`skipOn` list of both guards on purpose: retrying cannot heal it and a fallback would hide it. The same choice keeps the breaker CLOSED while every turn fails, so `ModelReadinessCheck` used to stay UP on a provider that answered 410 forever (#358). `PermanentFailures.observe` wraps each attempt against the primary, inside the guard and also on the fallback-disabled path (`callPrimaryOnly`), and counts consecutive failures per surface and workload, classified by the `HttpException` status langchain4j keeps as a cause. A success resets the streak, a transient failure neither counts nor resets, and the statuses are `qlawkus.model.permanent-failure.statuses` (default `401,403,404,410`; a plain 400 describes one request, not the provider). After `qlawkus.model.permanent-failure.threshold` (default 3) consecutive failures on the **interactive** workload the check reports DOWN with a `chatError`/`embeddingError` naming the status, whatever the fallback setting, since a permanent failure never reaches the fallback. The verdict lapses after `qlawkus.model.permanent-failure.window` (default 300s) without a new failure, so an instance held out of rotation can receive the traffic whose success clears it; one more permanent failure takes it straight back DOWN. Other workloads are reported as data and never flip the status, and reading the streak has no side effect. A permanent **embedding** failure also never reaches the fallback: its vector would come from another model and land in another vector space, so it fails loudly instead of degrading recall silently. Pinned by `ModelReadinessPermanentFailureTest`, `PermanentFailureWindowTest`, `FallbackEmbeddingModelTest` and `EmbeddingGuardTest`.

**Readiness and liveness answer different questions.** Liveness deliberately does not consult the model: killing the pod because the provider is down would turn their incident into an outage here, and the restarted pod would meet the same provider. `examples/redeploy/k8s/deployment.yaml` carries the probe trio (the startup probe absorbs the order-of-magnitude gap between JVM and native boot), and the Compose stacks poll the same `/q/health/ready`, so both deploy paths agree on what "serving" means.

## Model workloads

`ReplyLanguageResolver` is the single language policy for text and voice. `AgentStream`,
`AgentRunner`, direct `AgentService` calls and the voice session share it. `PromptReplyLanguageDecision`
uses the same registered `ChatModel` as fact extraction when `qlawkus.reply-language.enabled` is true
(the reference app enables it; other distributions default to prompt-only inference). The existing
NVIDIA/secondary/Ollama chain remains authoritative; no parallel provider or credential is registered.
Classification has no tools, chat memory or RAG, uses the isolated `decision` workload, and has its own
timeout, bulkhead and breaker. The resolver's bounded 256-conversation cache stores language codes only.
Explicit language choices bypass classification; an already prepared voice turn never classifies twice.
TTS provider availability must not constrain the language of the answer. See `site/content/voice.adoc`.

`AgentReplyStyle` is presentation metadata on `AgentTurn`, never text appended to the owner's message.
`SoulEngine` applies it to the system prompt for a streamed voice turn and applies the current-request
language policy on every channel. `console-voice` alone owns CommonMark speech rendering: the screen
keeps the original response, while the TTS path removes formatting and omits code blocks, tables and
images. It buffers complete blocks up to 64 KiB, so a long single paragraph can delay its first audio.
The transcript has a bounded scroll area that follows new text only while the reader is at the bottom.

The agent talks to one provider for two different reasons: answering the owner, and doing background work about the owner. Sharing fault-tolerance state between them is the defect - a nightly job that trips the provider's rate limit opens the breaker the owner's next message goes through, so the agent answers from the fallback because it was busy talking to itself.

Workloads are named in configuration (`qlawkus.model.workload.<name>.*`, `RUN_TIME`, so reachable from `/api/admin/runtime-toggles`), keyed like `MessagingConfig`. `interactive` and `batch` always exist; more can be declared without code. `PrimaryChatGuard` and `EmbeddingGuard` build **one `TypedGuard` per workload** at startup, and that is what makes the isolation structural rather than conventional: SmallRye gives each guard object its own instance of every strategy, so two guards cannot share breaker state.

**A `TypedGuard`, not `@ApplyGuard`.** The reusable-guard mechanism is the more elegant fit for named policies, but `Guard` has no `withFallback()` - only `TypedGuard` does - and the fallback to the secondary provider is why these guards exist.

**A thread-scoped marker, not a CDI qualifier.** `WorkloadContext.runAs("batch", ...)` selects the workload. A qualifier member has to be known when beans are wired, which would fix the set of workloads at build time and defeat declaring them in config. The marker is safe for the same reason the per-call fallback bridge is: SmallRye runs a synchronous action and its fallback handler on the calling thread. Work that hops threads must set the marker on the thread that actually calls the model.

**A synchronous bulkhead rejects; it does not queue.** SmallRye queues excess callers only for asynchronous actions, and a chat completion is synchronous here, so exceeding `max-concurrent` raises `BulkheadException` immediately. That is why `fallback-on-reject` exists and is `false` for batch: without it, every throttled job would quietly re-target the fallback provider and do the work anyway, which is the opposite of throttling. Abandoning the run is safe because the jobs are re-runnable, audited when shutdown began abandoning them. `@Scheduled(concurrentExecution = SKIP)` covers the other half - a job overlapping *itself* - which the bulkhead does not address.

**Readiness stays tied to `interactive`.** Other workloads' breakers are reported as data but never flip the status. Letting a background breaker take the instance out of rotation would rebuild, in the health layer, exactly the coupling this removes.

Two findings behind this are recorded as executable tests in `BulkheadSemanticsProbeTest`, because the documentation does not state them: a bulkhead does not offload the fallback off the calling thread, and **duplicate circuit breaker names are accepted silently** on smallrye-fault-tolerance 6.11.2. The second corrects an earlier assumption in this project that the library rejects them; uniqueness is our invariant, which is why `WorkloadGuards.breakerName` derives it instead of accepting one.

## Shutdown

A SIGTERM has to drain what the process is holding, and the drain has to be *waited on*. Both messaging adapters already had `@Observes ShutdownEvent` before this was addressed, and neither waited: Discord called `logout().subscribe(...)` and returned, Telegram interrupted its poll thread without joining it. Code that looks like a drain but returns immediately is worse than none, because it reads as solved.

Drains are registered as `ShutdownListenerBuildItem` from each module's `*-deployment`, never as CDI observers. The platform then supplies what would otherwise be hand-written per subsystem: two ordered phases, an acknowledgement callback, and a single budget (`quarkus.shutdown.timeout`) covering all of them. A `@Observes ShutdownEvent` would need its own timeout in every bean, and they would drift.

The phases carry meaning. `preShutdown` refuses new work (Telegram stops polling); `shutdown` releases resources (PTY sessions closed, Discord logout awaited, poll thread joined). Two rules keep this correct: **`done()` belongs in a `finally`** - a listener that throws before acknowledging costs the full timeout on every rollout, silently - and each listener swallows its own exception, so one broken drain cannot stop the others.

The listener instance is built during augmentation, before any container exists, so it holds no bean reference and resolves what it needs from `Arc.container()` at shutdown, guarded by `isRunning()`.

**Running jobs are abandoned, not awaited.** A nightly consolidation makes model calls and cannot fit any sane grace period, so the scheduler simply stops. That is only safe because the jobs are re-runnable, which was audited rather than assumed: purge, curation, skill lifecycle and cleanup all converge on a second run. `EpisodicConsolidatorJob` was the exception and was fixed here - it wrote the journal *before* embedding it while `existsForDate` guarded on the journal alone, so anything landing between the two steps (a SIGTERM, or an embed failure that only warned) left an entry unreachable by retrieval and skipped that day for good. The guard now re-asserts the embedding, which the fact store dedups by content hash.

The budget is chosen end to end, not per layer: `quarkus.shutdown.delay=3s` plus `quarkus.shutdown.timeout=20s` in `app/`, against `terminationGracePeriodSeconds: 30` in `examples/redeploy/k8s/deployment.yaml`. Raising one without the other converts a clean drain into a kill. The timeout also caps in-flight HTTP, and `/api/chat` is an SSE ReAct turn that can run for minutes, so it deliberately cuts a long turn rather than holding the rollout; working memory is append-only, so a cut turn loses a reply, not state.

## Single instance

Qlawkus is single-instance by product decision (#297): one agent, one owner, and the scheduled jobs assume they are the only writer. `instance.InstanceLock` (`@Startup`) enforces it with an exclusive `FileChannel` lock on `<qlawkus.agent.state.root>/.instance.lock`, so a second process on the same state fails at boot naming the holder; the reference k8s Deployment uses `strategy: Recreate` because a surge rollout is exactly that second process. Two traps behind its shape: POSIX locks are per process and **closing any descriptor of the file drops them all**, so a refused instance in the same JVM is turned away by a claim in `System.getProperties()` before it ever opens the file (otherwise its close would release the lock it was refused) - not a static field, which exists once per Quarkus app classloader; it is also `@Startup(PLATFORM_BEFORE)` so no other startup observer runs in a refused instance; and every test app needs its own `%test.qlawkus.agent.state.root`, or it collides with a running agent. The lock is per host, so it does not cover instances on different hosts sharing only a database.

## Telemetry

Model and AI-service meters come from upstream and need no code: they appear whenever a registry is present (see the `observability` capability). What `client` instruments itself is the cognition subsystem, which nothing upstream can see.

`metrics/AgentMeters` is the only class that touches a `MeterRegistry` and the one place every metric name is written down. Names are constants there because a metric name is a public contract - it becomes a time series, then a panel, then an alert - so a literal spread across call sites would drift. `client` depends on `io.micrometer:micrometer-core`, which is API plus in-memory accumulators: it opens no socket, so it is not egress and does not belong behind the capability. The registry and exporter that do leave the machine stay in `qlawkus-observability`. With that extension absent the `Instance<MeterRegistry>` is unsatisfied and every meter call is a no-op.

Where each measurement attaches, and why, is the part worth knowing before adding more:

- **Retrieval** - `MeteredContentRetriever` wraps the retriever built in `ActiveMemoryAugmentor.get()`. Scores come from `ContentMetadata.SCORE`. This is the meter that answers "did memory work this turn?", which otherwise requires reading a log.
- **Tools** - decorated in `QlawToolProvider`, **not** intercepted. That provider calls `ClientProxy.unwrap` before building each `DefaultToolExecutor`, so tool calls never cross a CDI proxy and no interceptor, including the project's own `@Logged`, can observe them. `MeteredToolExecutor` overrides *both* `execute` and `executeWithContext`, since `DefaultToolExecutor` implements each separately. Only `@QlawTool` extension tools flow through here; the tools declared on `@RegisterAiService(tools = {...})` are not counted. The same seam gives each call its span: `tracing.TracedToolExecutor` wraps the metered executor whenever a `Tracer` bean resolves (the `observability` capability), copying the name (`langchain4j.tools.<name>`) and GenAI attributes of upstream `ToolSpanWrapper`, which only wraps its own `QuarkusToolExecutor` and so never sees these tools. Keep the two in step: a different name would split one ReAct loop across two queries. `client` declares only `opentelemetry-api`, for the micrometer-core reason.
- **Stores** - the opposite case: stores are injected as their SPI and reached through a proxy, so interception works. `ClientProcessor.meterCognitionStores` adds `@Metered` at build time to every implementor of the six store SPIs, which covers the `cognition-pgvector` backends without that extension knowing telemetry exists. Annotating by hand would mean a new backend silently reporting nothing. `StoreMeterInterceptor` derives the `backend` tag from the implementation's name prefix, reporting `Pg*` as `pgvector` to match `qlawkus.cognition.backend`.
- **Jobs** - `AgentMeters.timeJob` wraps the body of each `@Scheduled` method. The `job` tag reuses the existing `@Scheduled(identity = ...)`, so metric and console schedule page name the same thing.
- **Fallback** - counted in the guards' fallback handler, which is the exact moment the primary is abandoned, so a switch is recorded even when the breaker never opens. Breaker state is a gauge bound to the `@ApplicationScoped` guard, because Micrometer holds only a weak reference to the gauged object.
- **Redeploy** - the loop restarts the very process that receives its report, so in-memory counters would reset to zero exactly when a successful run should increment them. `RedeployHistoryService` therefore keeps the totals in the persisted history and `AgentMeters.redeployRuns` / `redeployPhase` / `redeployLastSuccessAge` publish them as function meters and a gauge over it: `qlawkus.redeploy.runs` (`outcome`, `failed_phase`; `none` on a success), `qlawkus.redeploy.phase.duration` (`phase`, `outcome`, where `outcome` is that phase's own, so a build that failed is not a slow successful one), and `qlawkus.redeploy.last.success.age` (seconds, `NaN` before the first success). Every series is registered at boot, so a restarted instance publishes the totals its predecessor reached.
- **Embedding** - `AgentMeters.embedFact` wraps the embed loop in each of the three `FactStore` implementations, so the outcome recorded is the embed's own. `FactChunker` stays a pure function: chunking runs before anything reaches the model and has no outcome to report, so metering there could only ever record a success. The convenience store constructors used by tests pass `AgentMeters.disabled()`.

**Logs.** `qlawkus-observability` brings `quarkus-logging-json`, so the console is JSON in prod; its `microprofile-config.properties` turns that off for `%dev` and `%test`. It also sets `quarkus.otel.logs.enabled=true` (fixed at build time, inert while the SDK is disabled), so a deployment that turns the SDK on ships log records over OTLP next to its spans. Correlation needs no code: quarkus-opentelemetry writes `traceId`/`spanId` into the MDC and the formatter emits it. Note that `quarkus.otel.sdk.disabled=true` (the extension default; the Compose stacks turn it off) still creates valid spans and fills the MDC; it only stops export, so a test that compares MDC ids to a span's must also assert the span is valid, or two all-zero ids would pass it. At INFO the agent logs one `Agent turn` line per turn (from `AgentTurn`, bound by `AgentLogInterceptor`, `AgentRunner` and `AgentStream`), one `Tool call` line per `@QlawTool` call (from `MeteredToolExecutor`), and job start/end lines (`JobLog`), with `channel`, `conversation`, `workload` and `tool` in the MDC; message, fact, prompt, skill and tool content is logged at DEBUG only, so a new INFO line must carry identifiers and counts, never text. The failure fields are the one exception to that rule and are bounded and redacted: an `outcome=error` `Agent turn` line ends with `error` (root cause class) and `cause` (root message, one line, 200 characters at most, passed through `SecretRedactor` via `FailureSummary`), a throwing tool call is a WARN `Tool call` line with the same two fields and no stack trace, and `MessagingOrchestrator`'s fallback warning carries them too. A failed reply delivery adds `httpStatus`, `providerCode` and `providerMessage` when the platform reported them (`DeliveryFailure`, read through `MessagingProvider.deliveryFailure`, Discord implemented). Existing field names are a contract: add fields, never rename them. Messaging adds one line per accepted or rejected inbound message, per reply delivered or failed, and per voice transcription or synthesis; its Uni stages hop threads, so `MessagingLog` sets `channel` and `conversation` on each line rather than once per message. The `dev.langchain4j.agentic.agent.AgentInvocationHandler` category is held at ERROR in `client`'s `META-INF/microprofile-config.properties`, pinned by `AgentInvocationHandlerLogLevelTest`. The operator-facing field reference is the "How to read an agent turn" section of `site/content/operations.adoc`.

**Metrics stay off the public port.** `app/` enables the management interface and keeps health on the main one (`quarkus.smallrye-health.management.enabled=false`), so `/q/metrics` is served only on 9000, unauthenticated, and the public port answers 404. The same port serves plain HTML at `/q/dashboard` (tool catalog and a small metrics slice via `ops.OpsDashboard`). Not basic auth on the scrape: every authenticated identity is the admin, so a scrape credential would be the admin password in plaintext. Health stays public because the Compose healthcheck, the k8s probes and the redeploy loop read it without credentials.

**The `io.opentelemetry.usage` logger is silenced for an upstream bug.** OpenTelemetry API 1.62 logs one WARNING per process when a null context reaches `Span.fromContext`, and on Quarkus 3.x the Prometheus exemplar sampler and the MicroProfile context propagation provider both do that whenever no span is current, which includes boot (quarkusio/quarkus#55855; fixed on main for 4.0 only). `qlawkus-observability` therefore sets the category to `ERROR`, pinned by `OpenTelemetryUsageWarningIT` on the packaged artifact. Because that also hides a misuse of ours, `TracedToolExecutorTest.aToolCallReportsNoOpenTelemetryApiUsageIssue` captures the logger at `ALL` around the tool span: new code that drives the OpenTelemetry API directly needs the same guard. Drop the silencing once the platform carries both fixes. To see the stack traces, set the category `level` and `min-level` to `ALL`.

**Reading it back.** `qlawkus-tools-self-observe` (package `tools.selfobserve`, config root `qlawkus.self-observe.*`, `enabled` default `false`) gives the agent four read-only `@QlawTool`s over the backends the telemetry lands in: `queryMetrics` (Prometheus), `findTraces` / `getTrace` (Tempo), `queryLogs` (Loki). Its rules are the point of the module, each pinned by a test in its `deployment/`: `TelemetryHttp.get` is the only HTTP call, a `GET` that never follows redirects, with the `TransientHttpException` retry contract below, except that a request **timeout is permanent** (against a query API it means the query is too expensive, so retrying multiplies the load); base URLs come only from config and the model's query is one URL-encoded parameter value, a trace id must be hex; `QueryWindow` clamps the lookback to `max-window` and `QueryRangeGuard` refuses a PromQL/LogQL `[range]` or `offset` longer than it (and the `@` modifier), since those read past any request window; results are capped at `max-results`, a log line at 1000 chars, output at `max-chars`, a response at 4 MiB. Every result is wrapped by `TelemetryFrame` in a `<telemetry-data source="...">` block that opens with a treat-as-data warning, with any frame marker inside the data defused, because logs carry text from chat channels; reuse it for any tool that returns third-party text. `getTrace` summarizes spans through an attribute allow-list (`TempoResults.ATTRIBUTES`), so tool arguments never reach the model even when tracing records them. The Compose stacks turn it on against the `lgtm` service.

User-facing catalog: `site/content/operations.adoc` under "What the agent measures about itself" and "The agent reading its own telemetry". The reference Grafana dashboard is `examples/observability/grafana/qlawkus-agent.json`; `DashboardMetricsTest` fails when a panel queries an unpublished series or a `qlawkus.*` constant in `AgentMeters` is charted nowhere, so **adding a meter means adding a panel**.

## CI / Release

7 GitHub Actions workflows:

- **`build-pull-request.yml`** - On PR: quick build → JVM test matrix (per module) → native IT matrix (per IT module) → build report. No API key passed → LLM tests auto-skip
- **`build-push.yml`** - On push to main: full `mvn clean install` with `LLM_API_KEY: dummy`, then a separate step running only `integration-tests/live-provider` with the `NVIDIA_API_KEY` secret
- **`build-nightly.yml`** - Cron seg-sex 02:00 UTC + dispatch: JVM + native build, same `NVIDIA_API_KEY` secret
- **`pre-release.yml`** - On PR that changes `.github/project.yml`: validates version is not SNAPSHOT, blocks forks
- **`release-prepare.yml`** - On PR merge that changes `.github/project.yml`: sets POM version, tags (no `v` prefix), pushes tag, bumps to next SNAPSHOT
- **`release-perform.yml`** - On tag push: builds artifacts, creates draft GitHub Release with PR-based changelog, then calls `publish-images.yml`
- **`publish-images.yml`** - Reusable (`workflow_call` from release, `workflow_dispatch` for a dry run, `push` defaults to false): builds the JVM, `-devtools` and `-native` images in-container and pushes them to `ghcr.io/<owner>/qlawkus` with the version tag, plus `latest` variants on a release

Release flow: edit `current-version` in `.github/project.yml` → open PR (triggers `pre-release` validation) → merge triggers `release-prepare` → tag push triggers `release-perform` → edit/publish draft release.

Tags have no `v` prefix (e.g. `0.7.2`, not `v0.7.2`). Dependabot enabled for GitHub Actions + Maven dependencies (daily, ignores `io.quarkus:*`).
